# Phase 10 Gmail Connector Design

**Status of this document:** planning artifact only. Unlike every prior phase's own design doc, there is no pre-existing `PHASE-010` spec this document resolves named gates on — Phase 10 was never part of the original Phase 0-9 set `docs/phases/PHASE-REVIEW.md` reviewed, so `docs/phases/PHASE-010-gmail-connector.md` was written alongside this document, in Draft status, as this phase's own first artifact. This document resolves the five decisions that spec's own scope depends on; per this repo's own governance pattern (`docs/ROADMAP.md`'s approval gates), Phase 10 implementation may not begin until these decisions and `PHASE-010-gmail-connector.md` itself are reviewed and accepted by the repository owner and its status moves from Draft to Approved for Implementation.

## Outcome

Design a Gmail connector that composes two mechanisms this codebase has never combined before: Phase 6's connector/OAuth/sync framework (`ConnectorAdapter`, `connector_accounts`, `sync_runs`/`sync_cursors`) for *how data gets in*, and Phase 7's consent/encryption/deletion framework (`personal_domains`, `domain_consents`, field-level Fernet encryption, `deletion_jobs`) for *how it's governed once in*. Neither framework alone fits: Phase 6's existing adapters are all PAT-based and write into ordinary workspace-visible resource tables; Phase 7's existing domains are all user/AI-authored with no live external connection to manage. This document resolves five decisions arrived at through direct discussion with the repository owner, each one settled by first checking what actually exists in this codebase (or, for the OAuth-verification questions, in Google's own current documentation) rather than assumed by architectural analogy alone.

## Why this isn't a green field

- Phase 6 Decision 2's credential-encryption reasoning (a dedicated key, distinct from `session_secret`, decrypted value never logged/returned/audited) is reused verbatim for the Gmail OAuth token itself — no new key, no new reasoning.
- Phase 7 Decision 3's identical reasoning (a dedicated `ECC_PERSONAL_DATA_ENCRYPTION_KEY`, separate from the connector-token key, because the two keys' rotation triggers are unrelated events) is reused verbatim for synced email *content* — the two already-approved keys are simply each used for the purpose they were already built for, composed rather than a third key invented.
- Phase 4's evaluation-floor discipline (`EVALUATION-CONTRACT.md`'s versioned dataset/rubric/required-floor pattern, already proven by `attention.explain_item`, `meeting.prep_summary` and `personal.generate_insight`) is the template the new action-detection tool's safety rubric reuses, not a new safety framework.
- Phase 3's own architecture — `attention_items` are created by deterministic domain ingestion logic, and Phase 4's AI runtime only ever *explains* an already-computed item, never decides whether one exists — settles what could have been a much larger open question (does email attention-scoring need a new AI-runtime task type?) in favor of reusing the exact ingestion pattern tasks/commitments/risks already use.
- `recommendations` (migration `0009`, Phase 1) already has the full propose→confirm/reject/defer/pin lifecycle, versioning and a target-type-agnostic UI this design needs — confirmed by direct code read, not assumed from the table's existence alone, and confirmed to be missing exactly one capability (creating a new row rather than editing an existing one) before extending it.
- No prior connector in this codebase has needed true 3-legged OAuth2 — confirmed by reading `github_adapter.py`'s `authorize(credential: str)` directly: every existing adapter is PAT-based. The `ConnectorAdapter` Protocol's `authorize` shape was never exercised against a redirect/callback/token-exchange flow before this phase.
- Google's OAuth scope-tier classification was verified against Google's own current developer documentation before being asserted here, after an earlier draft of this reasoning turned out to be wrong: `gmail.metadata` is itself a restricted-tier scope, the same tier as `gmail.readonly`, not a lighter "sensitive" tier — corrected here rather than left as an unverified assumption in a document meant to gate real implementation.

## Decision 1 (approval gate): connector mechanics and Protocol extension

**`ConnectorAdapter`'s `authorize()` is split into `get_authorization_url()` and `handle_oauth_callback(code)`**, the first true OAuth2-authorization-code-grant shape any adapter in this registry has used. Every existing adapter (`github`, `gitlab`, `jira`, `datadog`, `sandbox.github`) keeps its current PAT-based `authorize(credential: str)` signature unchanged — this is an additive Protocol extension, not a breaking one, matching how Phase 6 Task 4 itself extended the registry without touching Task 2/3's already-shipped adapters. Google's OAuth2 token endpoint and the Gmail REST API are both called via the already-approved `httpx`, matching every existing adapter's own no-per-provider-SDK precedent — no new RFC-005 dependency (default; not yet explicitly re-confirmed by the repository owner in this exact form, see `PHASE-010-gmail-connector.md`'s own "not yet decided" note).

**`backfill()` gains an optional bounded window parameter**, since no existing adapter re-invokes backfill after initial connect — GitHub/GitLab/Jira/Datadog backfill once, then rely entirely on forward-only `incremental_sync`. Gmail's own backfill is deliberately narrow on first connect (last 30 days) and re-invocable later with an explicit, narrower or wider window, each re-invocation re-verifying `domain_consents` is still active at call time (not merely at original connect time) — the same "re-verify at use time, not proposal time" discipline that recurred as a genuine bug class across all four Phase 8 review rounds, applied here proactively rather than found later by a fifth.

**Rate-limit handling reuses the existing GitHub adapter's `_request_with_rate_limit_retry` pattern**, not a new mechanism — Gmail's own API quotas are comparably tight, and a 30-day backfill for an active mailbox is easily thousands of messages.

## Decision 2 (approval gate): privacy/consent model and encryption

**A new `personal_domains` entry, `domain_key='email'`**, classified at Phase 7's `high_stakes` tier (the same tier `health`/`finance` use) — gated by `domain_consents`, encrypted per Phase 7's existing "encrypt the narrative, not structural fields" convention. **Storage is a dedicated `email_threads`/`email_messages` table pair, not the generic `domain_records` shape** — matching Phase 6's own precedent of dedicated tables (`incidents`, `engineering_decisions`, `engineering_work_items`) once a domain's structure (threads, messages, participants, labels) outgrows a generic JSON payload.

**Two already-approved keys, each used for the purpose it was already built for — no third key.** The Gmail OAuth access/refresh tokens use `ECC_CONNECTOR_TOKEN_ENCRYPTION_KEY` (Phase 6 Decision 2's key — a credential-leak rotation trigger). Synced email *content* uses `ECC_PERSONAL_DATA_ENCRYPTION_KEY` (Phase 7 Decision 3's key — a personal-data rotation trigger). These are different operational events on different tables, and this phase is the first to need both keys active over related data at once — composing them is the resolution, not a reason to invent a `ECC_EMAIL_ENCRYPTION_KEY` the way a green-field read might assume.

**On-demand-fetched and proactively-fetched bodies are both cached**, once fetched, as normal Phase-7-governed encrypted records — with a per-thread "forget this" action extending Phase 7's existing deletion granularity. This was an explicit repository-owner call against the alternative (never persist, always re-fetch): caching aligns with this repo's stated local-first architecture (ADR-0002) more than transient-only storage would, since a user opening or the system reading a thread is deliberate engagement, not bulk background sync — but it does mean decision 3's scope-minimization intent doesn't reduce *stored* footprint the way it might first appear to (see decision 4).

## Decision 3 (approval gate): OAuth scope, verification reality and rollout gating

**`gmail.metadata` requested broadly for all synced mail; `gmail.readonly` used both on-demand (per opened thread) and proactively (by the new AI-runtime tool, at sync time, to detect implied actions before a human has read the mail) — this second, proactive use case reopened and superseded this decision's own earlier, narrower framing during this brainstorm.** Once action-detection needs to read a body before a human has opened it, `gmail.readonly` is exercised broadly, not merely per-thread-on-demand; combined with decision 2's caching resolution, this means most of the synced 30-day window ends up with cached, encrypted body content regardless of what a user actually opens. That is disclosed here rather than left implied: **decision 2's consent/encryption model is what actually protects this data; the scope split no longer meaningfully reduces stored footprint**, though it still shapes exactly which Google API surface is called for which purpose.

**Verified directly against Google's current OAuth verification documentation** (not assumed by earlier analogy to a "sensitive vs. restricted" tier split that turned out not to exist for this pairing): `gmail.metadata` and `gmail.readonly` are **both restricted-tier scopes**. Restricted-tier scope usage — regardless of whether it's broad or narrow, proactive or on-demand — requires Google's CASA third-party security assessment once an app serves users beyond Google's OAuth consent-screen test-user cap (roughly 100 explicitly-added accounts, no audit required within that cap).

**Resolution: ship to an explicit internal-user allowlist only, enforced entirely within this application** (not merely relying on Google's own test-user list as the sole gate) via a config-driven check inside `get_authorization_url()`/`authorize()` — an env var or settings field, deliberately not a new database table or admin UI, since this gate is explicitly temporary and this repo's own discipline argues against building permanent infrastructure for a known-provisional need (the same reasoning `scripts/bootstrap_dev.py`'s `ECC_ENV=development` check already applies to a different provisional gate). **This allowlist is the actual mechanism keeping Phase 10 out of CASA-assessment territory — not a staged-rollout nicety, a hard requirement** disclosed in `PHASE-010-gmail-connector.md`'s own "Out of scope" line: any expansion beyond the allowlist is future work blocked on a real, external, paid, non-negotiable audit this document does not attempt to schedule or fund.

## Decision 4 (approval gate): recommendations extension and AI-tool safety rubric

**`recommendations`' `execute_target()` gains a `"create"` operation, added to the existing per-target-type operation whitelist (`set_status`/`set_priority`/etc.) rather than a parallel `target_type` space (`"new_task"`/`"new_commitment"`).** `target_id` becomes `UUID | None`, valid `None` only when `operation="create"`. The create branch calls the same internal creation function `POST /api/v1/tasks`/`POST /api/v1/commitments`/`POST /api/v1/risks` already use — one function every caller goes through, not a second insert path living inside `execute_target` itself. **`proposed_fields` reuses the existing `TaskCreate`/`CommitmentCreate`/`RiskCreate` Pydantic models** as the create-recommendation's payload shape, rather than a fourth schema invented per target type. This is the first real populator of `recommendations.source="ai"`, a value the schema has carried since migration `0009` with nothing writing it until now.

**Evidence linking goes through `pkos_evidence`, the existing mechanism claims/relationships already use** — a synced email becomes a registered evidence row, and the new tool's output is grounded against it exactly the way `personal.generate_insight`/`meeting.prep_summary` are already grounded against their own evidence, not a new grounding mechanism.

**The new AI-runtime tool's safety rubric, concrete:**

1. Pydantic-enforced output schema (`has_action: bool`, `target_type: Literal["task","commitment","risk"] | None`, `operation: Literal["create"]`, the relevant `*Create` model's fields, `rationale`, `confidence`) — an output that can't populate a required field fails validation and is never returned, the same fail-closed shape every other Phase 4 tool already has.
2. A grounding check against the source email's own content, reusing `PersonalInsightOutput`'s established grounding-check pattern — a proposed task's due date or a proposed commitment's counterparty must trace to something the email actually says, not an inference the model added.
3. Real evaluation floors before any prompt version is promoted (schema validity rate, grounding rate, prohibited/hallucinated-fact count, latency), matching `attention.explain_item`/`meeting.prep_summary`/`personal.generate_insight`'s existing bar exactly, not a lower one for being "just" a new task type.
4. An adversarial evaluation dataset with both positive examples (clear task/commitment language) and negative examples (newsletters, FYI-only mail, already-resolved threads) — `has_action: false` is a first-class, required-to-clear-the-floor outcome, not merely the absence of a positive result.
5. **Nothing this tool proposes is ever written without the existing `recommendations` confirm step** — this rubric governs what a *proposal* is allowed to assert, not a bypass of the human-confirmation requirement decision 4's own first paragraph already establishes structurally via `execute_target`'s versioned, explicit confirm call.

## Decision 5 (approval gate): attention and knowledge integration

**A deterministic "awaiting reply" heuristic** (last message in a thread is inbound, no outbound reply since, sender resolves to a known `pkos_nodes` contact) **feeds `attention_items` via the exact ingestion mechanism tasks/commitments/risks already use** — no new AI-runtime task type for attention-scoring itself, consistent with Phase 3's own architecture (deterministic ranking; AI runtime only explains an already-computed item, via `attention.explain_item`, extended here to cover Gmail-sourced items rather than given a sibling tool). **Sender/recipient resolution into `pkos_nodes` is a hard dependency of this heuristic**, not an optional enhancement — it is Phase 2's existing entity resolution, reused as-is.

## Scope for this activation

Per `PHASE-010-gmail-connector.md`'s own "In scope"/"Out of scope" sections, resolved above:

- `ConnectorAdapter` Protocol extension (OAuth split, windowed backfill) and the Gmail adapter itself, PAT-free, using `httpx` directly against Google's OAuth2 and Gmail REST endpoints.
- `personal_domains`' `email` entry, `email_threads`/`email_messages` tables, both keys reused per decision 2, internal-allowlist enforcement per decision 3.
- `recommendations`' `"create"` operation and the new AI-runtime tool, evaluated per decision 4's rubric, evidence-linked via `pkos_evidence`.
- The deterministic attention heuristic and `pkos_nodes` sender/recipient resolution per decision 5.
- `GmailPanel` inside `PersonalWorkspace`; `RecommendationPanel` extended for create-type recommendations.

Explicitly deferred, named rather than silently dropped: any Gmail write action; rollout beyond the internal allowlist (blocked on Google's CASA assessment); push-notification-based incremental sync (polling assumed, not yet reconfirmed); Google Calendar or any other Google Workspace product; `cross_domain_grants` sharing of the `email` domain.
