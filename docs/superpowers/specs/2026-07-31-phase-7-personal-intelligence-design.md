# Phase 7 Personal Intelligence Design

**Status of this document:** planning artifact only. It does not by itself change `docs/phases/PHASE-007-personal-intelligence.md`'s status, and does not close Phase 6's own open exit gate (`docs/phases/PHASE-006-engineering-workspace.md`'s exit criteria -- "production-like sandbox sync, restore and operational runbooks pass," "non-surveillance review and browser acceptance complete" -- not yet independently signed off, per `docs/ROADMAP.md`'s own current Phase 6 status line). Per `docs/ROADMAP.md`'s approval gates, Phase 7 implementation may not begin until this document's decisions are reviewed and accepted by the repository owner and `docs/phases/PHASE-007-personal-intelligence.md`'s contracts move from Draft to Approved for Implementation. This document resolves the four approval-gate items `docs/phases/PHASE-REVIEW.md:138` names for Phase 7 ("Per-domain schema/retention; privacy impact assessment; encryption fields; high-stakes safety rubric"). The repository owner's request to begin Phase 7 work now is treated as the same kind of parallel-start exception every prior phase (2, 3, 4, 5, 6) received to begin work before its predecessor's exit gates closed -- it does not itself close Phase 6's exit gate.

## Outcome

Design and begin the first slice of Phase 7: a generic domain/consent/vault framework (`personal_domains`, `domain_consents`, `domain_records`, `domain_sources`, `goals`, `routines`, `check_ins`, `cross_domain_grants`, `personal_insights`, `deletion_jobs`) that every personal domain is built against, field-level encryption for sensitive payloads, purpose-bound revocable consent, export/deletion propagation, and **one reference domain** proving the framework end to end before the two highest-stakes domains (health, finance) are attempted. This document resolves the phase's four named decision gates and lays out the task sequence; it does not implement every domain in one slice -- **Task 1 (domain/consent/vault framework and the `habits` reference domain)** is this activation's engineering-delivery scope. Later tasks (learning, travel, relationships, health, finance, cross-domain grants and AI-generated insights) are queued, not attempted here.

## Why this isn't a green field

- Finding F-05 (`PHASE-REVIEW.md`) already draws Phase 7's own boundary: "Phase 7 excludes diagnosis, treatment, regulated advice and transactions; domains are opt-in compartments with purpose-bound cross-domain grants, local-first operation, export and deletion propagation." This design does not reopen that boundary, it makes it concrete.
- The cross-phase invariant "Work and system risk may be ranked; people may not be scored" (finding F-04) binds the `relationships` domain specifically when it ships (Decision 1 below): no relationship-health score, no interaction-frequency leaderboard, ever.
- `ecc.domains.engineering.crypto`'s Fernet pattern (Phase 6 Decision 2: dedicated key, distinct from `session_secret`, decrypted value never logged/returned/audited) is reused in kind for personal data, not reinvented -- a second dedicated key, because a personal-data key rotation and a connector-token key rotation are unrelated blast radii, the exact same reasoning that already separates the connector-token key from `session_secret`.
- Phase 5's approval semantics (`ecc.domains.automation`) already govern every state-changing action; a reminder or planning-proposal that would take an external effect (e.g. a calendar write) is not a new authority mechanism this design invents, it is a Phase 5 `ActionAdapter` like every other phase's write actions.
- Phase 4's evaluation-floor discipline (`EVALUATION-CONTRACT.md`'s versioned dataset/rubric/required-floor pattern) is the template Decision 4 below reuses for insight safety -- proposing a *structural* rubric now and explicitly deferring the first AI-generated insight to a later task, mirroring how Phase 4's own first activation was deliberately narrow (one local model, no remote provider, one evaluated task type) rather than shipping every capability named in the phase spec at once.
- Phase 2's `resolution_candidates` entity-linking machinery is **not** reused here -- personal-domain data is deliberately not entity-resolved into the shared knowledge graph by default (`PHASE-007-personal-intelligence.md`'s own line: "Default global search, meeting prep and engineering views exclude personal domains"). Cross-domain or cross-phase visibility only ever happens through an explicit, purpose-scoped `cross_domain_grants` row (Decision 2 below), never through the identity-resolution path Phase 2/6 use for work entities.
- No personal-domain vault, consent-grant, or per-field-encryption precedent exists anywhere in this codebase yet (confirmed by direct repo survey before writing this document) -- the schema below is new, matching how Phase 6's connector/OAuth/token-encryption mechanism was new relative to its own dependencies.

## Decision 1 (approval gate): per-domain schema/retention

**`habits` ships first, as the reference domain; `learning`, `travel`, `relationships`, `health` and `finance` are explicitly sequenced next within this phase, not descoped.** All six remain in `PHASE-007-personal-intelligence.md`'s scope ("health, finance, learning, travel, habits and relationships") -- this decision only orders delivery, the same shape as Phase 6 Decision 1's GitHub-first ordering. `habits` is chosen as the reference domain specifically *because* it is the phase's lowest-stakes domain: it needs no `high_stakes` classification tier, no diagnostic/financial-advice safety rubric, and its natural shape (a habit definition plus dated check-ins) directly exercises `goals`/`routines`/`check_ins` -- the three tables `PHASE-007-personal-intelligence.md`'s own "In scope" line names as domain-agnostic constructs, not habit-specific ones. Building the generic vault framework against the domain least likely to surface a safety-rubric gap keeps that framework's own correctness bugs separable from a health/finance-specific safety bug, the same separation-of-concerns reasoning `EVALUATION-CONTRACT.md`'s reflection-engine section already uses ("enabling an unproven second... layer now would confound whether a future failure is a base-pipeline defect or a[nother] layer['s]").

Task sequence:

1. Domain/consent/vault framework and the `habits` reference domain (this activation) -- `personal_domains` registry, `domain_consents`, generic `domain_records`/`domain_sources`, `goals`/`routines`/`check_ins`, `deletion_jobs`, and deterministic (non-AI) insights only. No `cross_domain_grants` consumer yet (no second domain exists to grant into), no AI-generated insight yet (Decision 4 below).
2. `learning` domain (structured records: courses/resources/progress; still `standard` classification).
3. `travel` domain (structured records: trips/itineraries; still `standard` classification; first domain with meaningfully time-ranged records, exercising retention-by-date-range).
4. `relationships` domain (`sensitive` classification; first domain the F-04 non-scoring invariant binds directly -- no relationship-health score, no contact-frequency ranking, ever).
5. `cross_domain_grants` (now that 4+ domains exist to grant between) plus the first AI-generated insight types (`trend`/`correlation`) via a new Phase 4 evaluated task type, gated on Phase 4's own evaluation-floor discipline the same way `attention.explain_item`/`meeting.prep_summary` are.
6. `health` domain (`high_stakes` classification; the safety rubric from Decision 4, already proven structurally on `habits`/`learning`/`travel`/`relationships`, now enforced against real diagnostic-language risk for the first time).
7. `finance` domain (`high_stakes` classification; same rubric, adapted prohibited-language set for regulated-advice/guaranteed-return risk).
8. Executive UX and browser acceptance across all six domains.

A domain that cannot pass the common framework contract or its classification tier's safety rubric by its scheduled task is explicitly descoped at that point, in the implementation-status document, rather than silently dropped -- the same discipline Phase 6 Decision 1 already committed to for GitHub/GitLab/Jira.

**Schema, concrete.** `personal_domains`: `domain_key` (closed enum: `habits|learning|travel|relationships|health|finance`), `classification` (closed enum: `standard|sensitive|high_stakes` -- `habits`/`learning`/`travel` are `standard`, `relationships` is `sensitive`, `health`/`finance` are `high_stakes`), `enabled` (per-user, default `false` for every domain, per `PHASE-007-personal-intelligence.md`'s own functional requirement), `enabled_at`. `domain_records`: `domain_key`, `record_type` (per-domain closed enum, e.g. `habit_definition|habit_check_in` for `habits`), `payload` (JSONB; sensitive/high_stakes-classified fields inside `payload` are individually Fernet-encrypted per Decision 3, not the whole column, so a `standard`-classified field on an otherwise `sensitive` record -- e.g. a relationship record's non-sensitive `contact_name` -- stays queryable), `domain_source_id`, `effective_at`, `retention_policy_id`. `domain_sources`: `source_type` (`manual|imported_file` -- no connector-based personal-domain source exists in this activation; a future connector, e.g. a fitness tracker, is explicitly deferred, matching `PHASE-007-personal-intelligence.md`'s "Deferred backlog": no clinical integrations, no bank-account write access this activation touches at all). `goals`/`routines`/`check_ins`: `domain_key`-scoped, FK to the `domain_records` row they track progress against where applicable.

**Retention, concrete, by classification tier.** `standard`: retained indefinitely until the user deletes the record or disables the domain (disabling a domain does not delete its data by default, matching `PHASE-007-personal-intelligence.md`'s rollback plan: "retain local authoritative data for export or delete on request" -- the same disconnect-vs-delete separation Phase 6 Decision 2 already established for connector data). `sensitive`: same indefinite-until-deleted default, plus a non-blocking UI nudge (Decision 4/`UX-STATES.md`'s existing "calm, non-judgmental" requirement governs its wording) surfaced after 18 months of no access to a record, prompting an explicit keep/export/delete decision -- not an automatic deletion, since silently deleting a user's own data on a timer would itself be a data-loss risk this design does not take on. `high_stakes`: same nudge at 12 months (shorter, given the elevated sensitivity), plus every `high_stakes` record's `domain_records` row includes a mandatory `retention_acknowledged_at` set at creation time (the user affirmatively saw and accepted the domain's retention terms for *this* record, not just once at domain-enablement time) -- a stronger consent-at-point-of-capture requirement than `standard`/`sensitive` records need, matching the extra weight `PHASE-REVIEW.md` finding F-05 already puts on health/finance specifically.

## Decision 2 (approval gate): privacy impact assessment

**Data inventory.** Six domains, three classification tiers (above). No domain's data is visible to any other domain, to Phase 2/3/6's shared knowledge/attention/engineering surfaces, or to global search by default (`PHASE-007-personal-intelligence.md`: "Default global search, meeting prep and engineering views exclude personal domains") -- enabling a domain grants access to that domain's own UI surface only, never a second domain, matching `DOMAIN-PRIVACY-CONTRACT.md`'s existing "Enabling one does not grant another access."

**Who can access what.** Within a workspace, only the record's own owning user -- no admin override exists for personal-domain content anywhere in this design, extending finding F-04's "Phase 9 enterprise administration does not bypass private-content boundaries" from a stated future constraint into this activation's actual access-control code path from day one, not a later hardening pass. A future multi-user Phase 8 sharing feature is out of scope (`PHASE-007-personal-intelligence.md`'s own out-of-scope line: "public sharing").

**Cross-domain and cross-phase leakage risk.** The primary risk this framework exists to prevent: a `health` insight's evidence text accidentally reaching a `meeting.prep_summary` prompt, or a `finance` record surfacing in a lexical/embedding search result outside its own domain surface. Mitigated structurally, not by convention: `domain_records`/`personal_insights` are never inserted into Phase 2's `retrieval_documents`/`embedding_projections` tables (no indexing pipeline for this activation touches personal-domain tables at all -- "local retrieval" per `PHASE-007-personal-intelligence.md` means a domain-scoped query against `domain_records` directly, not participation in the shared retrieval index), and Phase 4's `execute_run` prompt-assembly code path (`runtime.py`) has no personal-domain tool in its `TASK_PORTS`/`eligible_tools` registry until Decision 4's later cross-domain-insight task explicitly adds one, narrowly scoped to an active grant's exact fields.

**Third-party/remote egress risk.** None from this activation -- Phase 4's only active model is local (`qwen2.5:1.5b-instruct-q4_K_M` via Ollama, RFC-005's current registry state); no remote provider is activated by Phase 4 or by this document, and `DOMAIN-PRIVACY-CONTRACT.md`'s existing "Sensitive data never leaves the device unless a named provider and exact data class are explicitly allowed" stays a forward-looking constraint this activation does not need to exercise, since Task 1 ships zero AI-generated insights (Decision 4 below) and therefore makes zero model calls over personal-domain data at all.

**Residual risk, disclosed rather than silently accepted.** (1) A user with direct database access (an operator, not this application's own access-control surface) can read `standard`-classified fields in plaintext -- accepted, matching Phase 6's own equivalent disclosure for non-credential projection data, since encrypting every field regardless of classification would break server-side filtering/sort for no threat-model gain over a low-sensitivity field. (2) Backup/restore of `sensitive`/`high_stakes` records is not yet independently exercised against this activation's data (Phase 6's own backup-restore CI job covers engineering tables only) -- tracked as an explicit Task 1 follow-up in the implementation plan, not silently assumed to already work. (3) No dependent/minor-profile safeguarding exists (`PHASE-007-personal-intelligence.md`'s own out-of-scope line covers this already) -- a single adult user's own data only, this activation included.

**Outcome.** Reviewed against `DOMAIN-PRIVACY-CONTRACT.md`'s existing requirements and finding F-05's boundary; no residual risk above blocks Task 1 specifically, since Task 1 (habits, `standard` classification, zero AI calls, zero cross-domain grants) does not yet exercise the `sensitive`/`high_stakes`/cross-domain/AI-insight surfaces those residual risks describe. Each later task in Decision 1's sequence re-triggers this assessment for its own domain's specific classification tier before it ships, per `PHASE-007-personal-intelligence.md`'s own exit criterion ("Each released domain has explicit scope/schema/retention and test fixtures").

## Decision 3 (approval gate): encryption fields

**A dedicated `ECC_PERSONAL_DATA_ENCRYPTION_KEY`, distinct from both `session_secret` and `ECC_CONNECTOR_TOKEN_ENCRYPTION_KEY`.** Same reasoning `ecc.domains.engineering.crypto`'s own docstring already gives for keeping the connector-token key separate from `session_secret` (an unrelated rotation should not have an unrelated blast radius): a personal-data key rotation and a connector-credential key rotation are two different operational events with two different triggers (a user requesting re-encryption of their own vault vs. a suspected connector-token leak), and sharing one key would couple them. Uses the same Fernet primitive (`cryptography` package) already approved by `RFC-005` v1.4.0 -- no new RFC-005 amendment needed, this is a second key for an already-approved primitive, not a new technology.

**What gets field-level encrypted, concrete, by classification tier.** `standard`-classified `domain_records.payload` fields: plaintext (queryable/filterable server-side; e.g. a `habits` check-in's `completed_at` timestamp or a `travel` record's destination city). `sensitive`/`high_stakes`-classified fields: the specific free-text/narrative fields most likely to contain the actual sensitive content are Fernet-encrypted individually within `payload` before write (e.g. `relationships`' `notes` field, `health`'s `symptom_description`/`condition_name` fields, `finance`'s `account_notes`/transaction-memo-style free text) -- structured, low-sensitivity fields on the same record (a `relationships` record's `contact_name`, a `finance` record's transaction `amount`/`category` enum, needed for basic list/filter UI) stay plaintext, the same "encrypt the narrative, not the whole row" tradeoff Decision 1's schema section above already states for query-ability reasons. The exact per-domain field list is finalized in each domain's own `DATA-MODEL.md` addition when that domain's task lands (Decision 1's sequence) -- this decision fixes the *mechanism and the tier-based default*, not a frozen enumeration of every field across all six domains upfront, matching how Phase 6 Decision 2 fixed the credential-encryption mechanism without enumerating every future connector's own token shape in advance.

**Decrypted value never logged, returned by an unrelated API response, or written into an audit/outbox payload** -- the same discipline `crypto.py`'s own docstring states for connector credentials, extended verbatim to personal data. `GET /personal/records` responses include the decrypted field only in the single request that legitimately needs it (viewing/editing that specific record); list/summary views return a redacted placeholder for any encrypted field, never the plaintext, matching `RFC-005`'s general "sensitive source content MUST NOT be logged" discipline applied at the API-response layer instead of the log layer.

## Decision 4 (approval gate): high-stakes safety rubric

**Structural rubric now; the first AI-generated insight explicitly deferred to a later task (Decision 1's sequence, item 5).** Task 1 ships zero AI-generated insights -- every insight in this activation is deterministic, computed directly from a domain's own records with no model call at all (e.g. `habits`: "you haven't logged this habit in N days," a threshold comparison, not a generated sentence). This mirrors Phase 4's own first-activation narrowness (one local model, one evaluated task type, no remote provider) rather than shipping `INSIGHT-CONTRACT.md`'s full `observation|trend|correlation|reminder|planning_suggestion` type set against a real model in the same activation that also stands up the vault framework itself -- the same "don't confound a base-framework bug with a[nother] layer's bug" separation Decision 1 above already gives for choosing `habits` first.

**The rubric itself, made concrete for when a later task does add AI-generated insights:**

1. **Schema-level requirement, not a prompt-only instruction.** `INSIGHT-CONTRACT.md`'s existing "Each shows source period, missing data, confidence and limitations" becomes a Pydantic-enforced required-field set on the insight output schema (mirroring `attention.explain_item`'s own `ExplainItemOutput`/Decision 4-of-Phase-4's "the model cannot omit a required field and still validate" guarantee) -- an insight response that omits `limitations` fails schema validation and is never returned, the same fail-closed shape `execute_run` already gives every Phase 4 task type.
2. **A closed, per-classification-tier prohibited-language fixture set**, evaluated the same way `EVALUATION-CONTRACT.md`'s `must_not_state` hallucination probe already works for `attention.explain_item` -- not a runtime content filter (too brittle, easily bypassed by phrasing) but an *evaluation-floor* requirement: before any `health`/`finance`-domain prompt version is promoted, it must clear a dedicated adversarial fixture set (diagnostic claims, prescriptive treatment language, guaranteed-return language, credit/employment/insurance-decision language, sensitive-trait inference) at the same 100%-floor rigor `EVALUATION-CONTRACT.md` already holds `attention.explain_item`'s `must_not_state` probe to, not a lower bar for being "just" personal data.
3. **`relationships`-domain insights are bound by the F-04 non-scoring invariant structurally**: no insight `kind` in `INSIGHT-CONTRACT.md`'s enum computes or surfaces a numeric relationship-health score, ranking or frequency leaderboard -- the same schema-level closed-enum constraint Phase 6 Decision 3 already used to make "no person-ranking field exists in this schema" a hard guarantee rather than a UI-layer convention a later task could quietly work around.
4. **High-stakes insights always name a qualified-professional referral where relevant**, per `INSIGHT-CONTRACT.md`'s existing "High-stakes decisions direct the user to qualified professionals" -- made concrete as a required, non-empty `professional_referral_note` field specifically on `health`/`finance`-classified insight types (absent/empty on `standard`/`sensitive` domains' insights, where it would be noise).
5. **Feedback cannot convert correlation into causation**, per `INSIGHT-CONTRACT.md`'s existing text -- the `trend`/`correlation` insight kinds are the only ones a future cross-domain task (Decision 1, item 5) may generate via an actual model call; `POST /personal/insights/{id}/feedback` never rewrites an insight's own `kind` field, only records separate feedback metadata, so user feedback cannot silently upgrade a `correlation` insight into something that reads as an `observation` of settled fact.

No Phase 4 dataset/prompt work is required for Task 1 itself (zero AI calls); this rubric exists now so the later task that does add AI-generated insights has an approved target to build against rather than deferring the safety design to the same moment as the highest-risk feature.

## Task 1 scope for this activation

Per the sequence above, this activation delivers:

- `personal_domains`, `domain_consents`, `domain_records`, `domain_sources`, `goals`, `routines`, `check_ins`, `deletion_jobs` -- the framework tables this task's own scope needs, workspace/user-scoped with the same FK/audit conventions every prior-phase table uses. `cross_domain_grants` and `personal_insights` (beyond the deterministic kind below) are added by the task that first needs them (Decision 1, item 5), matching Phase 6 Task 1's own "not every `DATA-MODEL.md` table upfront" precedent.
- `ecc.domains.personal.crypto` -- Fernet-based encrypt/decrypt helpers over `ECC_PERSONAL_DATA_ENCRYPTION_KEY`, mirroring `ecc.domains.engineering.crypto`'s shape exactly (new dedicated key, decrypted value never logged/returned/audited).
- `ecc.domains.personal.domains` -- domain enablement/disablement, consent grant/revoke, generic record CRUD enforcing per-field encryption by classification tier.
- `ecc.domains.personal.habits` -- the one reference domain: habit definitions, check-ins, and deterministic (non-model-call) insights only (streak/gap observations).
- `ecc.domains.personal.export_deletion` -- export (human- and machine-readable) and deletion-job propagation for the `habits` domain, proving the mechanism `DOMAIN-PRIVACY-CONTRACT.md` requires of every domain before a second domain reuses it.
- `GET|POST /personal/domains`, `POST .../{id}/enable|disable|export|delete`, `GET|POST /personal/records`, `GET|PATCH /personal/records/{id}`, `GET|POST /personal/goals|routines|check-ins`, `GET|POST /personal/consents`, `POST /personal/consents/{id}/revoke`, `GET /personal/insights`, `POST /personal/insights/{id}/dismiss` per `API-SCHEMAS.md` (`feedback` deferred with the AI-insight task it applies to).
- Cross-workspace isolation, encrypted-field-never-returned-in-list-view, disabled-domain-blocks-all-access, and export/deletion-propagation coverage tests, plus the `habits`-specific adversarial fixtures Decision 4 names as *always* in scope even for a `standard` domain (no diagnostic/scoring language leaking in even where the safety rubric's higher tiers don't yet apply).

`learning`/`travel`/`relationships`/`health`/`finance`, `cross_domain_grants`, and every AI-generated insight kind remain out of this activation's scope, tracked as "Not started" in `docs/phases/phase-007/IMPLEMENTATION-STATUS.md` until their own task lands.
