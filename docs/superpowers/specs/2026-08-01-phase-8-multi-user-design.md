# Phase 8 Multi-user Workspaces Design

**Status of this document:** planning artifact only. It does not by itself change `docs/phases/PHASE-008-multi-user.md`'s status. Per `docs/ROADMAP.md`'s approval gates, Phase 8 implementation may not begin until this document's decisions are reviewed and accepted by the repository owner and `docs/phases/PHASE-008-multi-user.md`'s contracts move from Draft to Approved for Implementation. This document resolves the four approval-gate items `docs/phases/PHASE-REVIEW.md:139` names for Phase 8 ("Identity migration; complete authorization matrix; invitation verification; revocation propagation SLO"). Phase 7 exited with PR #99 (whole-phase deep review round 1, merged) and no outstanding open finding; per the repository owner's standing direction to proceed once a prior phase's review round converges (mirroring the parallel-start exception every phase 2-7 received relative to its predecessor), Phase 8 work begins now.

## Outcome

Design the identity/membership/authorization core every later Phase 8 capability (sharing, delegation, notifications, ownership transfer) depends on, and sequence the full task list. This document resolves the phase's four named decision gates; it does not implement every capability in one slice -- **Task 1 (account/membership/session framework)** is the first activation's engineering-delivery scope, mirroring Phase 7's own "framework first, one reference slice, then breadth" shape.

## Why this isn't a green field

- The codebase already has a real `users` table (`backend/migrations/versions/0001_foundation.py`: `id`, `workspace_id`, `email`, `password_hash`, `created_at`, `UNIQUE(workspace_id, id)`, `UNIQUE(workspace_id, email)`) and a real `sessions` table (`token_hash`, composite FK to `users.(workspace_id, id)`, `expires_at`, `revoked_at`) -- this is not built from nothing. But there is **no registration or login flow that creates a second real identity**: the only account-provisioning path today is `scripts/bootstrap_dev.py` (dev-only, `ECC_ENV=development`-gated, inserts one workspace + one user with a placeholder `password_hash`). `RFC-005.md`'s Authentication baseline says so explicitly: "Phase 0 uses: one local owner account per installation" and reserves OAuth2 for "future multi-user identity."
- `owner_id` already exists and is already a real composite FK to `users.(workspace_id, id)` on 14 tables across Phase 1 (`tasks`, `commitments`, `notes`, `risks`/`attention_items`) and Phase 7 (`personal_domains`, `domain_consents`, `domain_sources`, `domain_records`, `goals`, `routines`, `check_ins`, `personal_insights`, `cross_domain_grants`, `personal_insight_feedback`). Every existing query on these tables filters `WHERE workspace_id = ... AND owner_id = auth.user_id` -- i.e. `owner_id` today only ever equals the requesting user, because only one real user exists per workspace. This design reinterprets, not reinvents, that column.
- Roughly 60 further tables across engineering, knowledge, attention, automation, AI runtime and calendar/scheduling have `workspace_id` and audit `created_by`/`updated_by` columns (an actor field, not an accountable-owner/visibility field) but no `owner_id` at all -- these need the "existing records receive explicit accountable owner/visibility migrations" treatment `PHASE-008-multi-user.md` names in its own "Data changes" section.
- There is no role/permission engine anywhere in the codebase today (confirmed by direct grep survey before writing this document, same discipline Phase 7 Decision 1 used) -- authorization today is entirely tenant isolation by `workspace_id`, nothing more granular. `personal.domains.require_enabled_domain` is a Phase-7-specific consent gate, not a general authorization primitive, and does not generalize to a second real user.
- Finding F-04 (`PHASE-REVIEW.md`) already draws this phase's boundary: "Phase 8 roles do not grant private-vault access." This design does not reopen that boundary -- it makes it structurally impossible, not merely a documented policy, the same "structural, not conventional" discipline Phase 7 Decision 2 used for cross-domain leakage.
- RFC-003's DP-017 ("Every concept has exactly one owner... ownership should never be ambiguous") is the design principle this phase's accountable-owner requirement makes concrete for every existing table, not a new invention.
- Phase 6's `ecc.domains.engineering.crypto`/session-secret separation precedent and Phase 7's `ECC_PERSONAL_DATA_ENCRYPTION_KEY` precedent are not reused here directly -- Phase 8 introduces no new encryption key, since membership/role/grant data is not itself a narrative-content encryption target the way Phase 6/7's credentials/personal-domain payloads are. What Phase 8 does reuse: `RFC-005`'s already-approved `cryptography`/session-token-hashing pattern (`sessions.token_hash`, SHA-256) for the new `invitations.token_hash` column, and the same HttpOnly-cookie/CSRF-double-submit shape `backend/ecc/auth.py` already implements, extended rather than replaced.

## Decision 1 (approval gate): identity migration

**A new, workspace-independent `accounts` table becomes the thing a person authenticates as; the existing `users` table keeps its exact current FK role (the composite `(workspace_id, id)` anchor every `owner_id`-style column already points to) and gains an `account_id` column instead of being restructured.** This is the central architectural choice this gate exists to make, so it is made explicit and justified here rather than left implicit in a migration diff.

**Why not make `users` itself workspace-independent.** `PHASE-008-multi-user.md`'s own frontend requirement ("Add workspace switcher") means one person must be able to belong to more than one workspace -- but `users.id` is only unique per `(workspace_id, id)` today, and roughly 14 existing tables' `owner_id` columns are composite-FK'd to exactly that pair specifically *because* it makes a cross-workspace FK reference structurally impossible at the database level (the same "cross-workspace leakage tolerance is zero" cross-phase invariant every prior phase has held to). Collapsing `users` to a single global-identity table would require rewriting every one of those 14 FKs and every hand-written query built against `(workspace_id, owner_id)` -- a wide, high-risk migration with no correctness benefit, since the composite-FK safety property is exactly what Phase 8 needs to keep.

**The chosen shape.** `accounts`: `id` (UUID), `email` (globally `UNIQUE`, case-insensitively normalized at write time), `password_hash` (Argon2id, `RFC-005`'s already-approved algorithm, not yet exercised anywhere in the codebase), `display_name`, `created_at`, `disabled_at` (nullable; a disabled account can authenticate to no session anywhere, the account-level kill switch this phase's "revocation propagation" gate item needs at the identity layer, distinct from a single workspace's own membership-level suspension). `users` keeps its existing `id`/`workspace_id`/`created_at`/`UNIQUE(workspace_id, id)` exactly as-is (zero change to any of the 14 existing `owner_id` FKs or the queries built against them) and gains `account_id` (FK to `accounts.id`, `NOT NULL` after backfill, `UNIQUE(workspace_id, account_id)` so one account cannot get two `users` rows in the same workspace). `email`/`password_hash` move off `users` onto `accounts` (dropped from `users` in the same migration, not left duplicated) -- migrated forward, not editing an already-shipped migration file, the same "new migration supersedes old data" discipline `0060_phase7_insight_eval_v2.py` used for Phase 7's own review-round fix.

**A person's actual membership state (role, invited/active/suspended/removed, joined/removed timestamps) is not stored on `users` at all -- it lives on a new `workspace_memberships` table** (`id`, `workspace_id`, `account_id`, `users_id` FK to the `(workspace_id, id)` anchor, `role`, `status`, `invited_by`, `created_at`, `updated_at`, `removed_at`). Splitting membership state from the `users` FK anchor this way means removing a member never deletes or invalidates the `users` row every `owner_id`/`created_by` column across the whole system points to -- a removed member's historically owned/authored records stay attributable and un-orphaned (`PHASE-008-multi-user.md`'s own "Member removal resolves ownership... before completion" and "Removal cannot orphan resources or active accountability" requirements), while `workspace_memberships.status = 'removed'` is what every future authorization check actually gates on.

**Migration for the 14 existing `owner_id` tables.** No schema change to these tables at all -- `owner_id` keeps meaning exactly what it always has (the `users.(workspace_id, id)` row that owns the record), which after this migration transitively resolves to a real `account_id` through the `users` row. What changes is only that a second real `workspace_memberships` row can now exist for a second real account in the same workspace, so a query that used to be able to assume "the one user in this workspace" can no longer do so -- Decision 2 below is what makes that assumption's removal safe rather than a silent authorization gap.

**Migration for the ~60 tables with `workspace_id`/`created_by` but no `owner_id`.** Add `owner_id` (FK to `users.(workspace_id, id)`, backfilled to the workspace's sole pre-existing `users` row, `NOT NULL` after backfill) and `visibility` (closed enum `private|shared_explicitly|workspace`, per `PHASE-008-multi-user.md`'s own `DATA-MODEL.md` sketch, backfilled to `workspace` for every one of these tables -- engineering work items, meetings, plans, automation workflows, knowledge entities and AI-runtime artifacts are inherently team/workspace-collaborative surfaces in every phase's own spec, not personal-by-default, the opposite default of Decision 2's Phase 7 carve-out below). This closes `PHASE-008-multi-user.md`'s own exit criterion ("All existing Phase 1-7 resources have explicit visibility/owner policy") for every table without requiring a bespoke per-domain decision about what the backfilled value should be -- the default matches what every phase's own spec already implies about that domain's collaborative nature.

**Session/login flow.** `sessions.user_id` stays FK'd to `users.(workspace_id, id)` exactly as today -- a session is, and remains, scoped to one workspace at a time; "switching workspaces" creates a *new* session against a different `(workspace_id, users.id)` pair for the same `account_id`, it does not make one session span two workspaces (matching the "actor, workspace and tenant context are server derived" cross-phase invariant -- a single ambient session must never leave which workspace it's scoped to ambiguous). Login: `POST /auth/login` (new) authenticates `accounts.email` + password (Argon2id verify), looks up every `workspace_memberships` row with `status = 'active'` for that account, and either auto-selects the session if there is exactly one or returns the workspace list for the caller to pick from (`POST /auth/select-workspace`) -- the backend half of "workspace switcher." `require_auth_context()` (`backend/ecc/auth.py`) is unchanged in shape (`AuthContext(workspace_id, user_id, timezone)`); it is what it already joins against (`sessions` -> `workspaces`) that is now genuinely multi-account rather than incidentally single-account.

## Decision 2 (approval gate): complete authorization matrix

**A single, closed, centrally-defined authorization function, not a per-endpoint ad hoc check.** `ecc.platform.authz.authorize(auth, resource_type, resource_id, action) -> bool` (new module, `backend/ecc/platform/` per `STD-001`'s repo-layout rule that shared cross-domain mechanism lives under `platform/`, not inside one domain package) is the single decision point every domain's query/mutation boundary calls -- mirroring how `require_csrf`/`require_auth_context` are already the single point every mutating endpoint goes through, not a pattern reinvented per domain.

**Roles are a closed, bounded enum with a fixed permission set each -- not a customizable ACL builder.** `owner|admin|member|viewer`, matching `PHASE-008-multi-user.md`'s own "Roles provide bounded baselines" line and `PERMISSION-CONTRACT.md`'s "Workspace administrators cannot read personal/private vaults merely because they administer membership." Fixed baseline (illustrative, finalized in `PHASE-008-DATA-MODEL.md`'s own addition when Task 3 lands): `owner`/`admin` manage membership/invitations/roles and read/write every `workspace`-visibility resource; `member` reads/writes `workspace`-visibility resources in domains they're not excluded from and reads their own `private`/`shared_explicitly` resources; `viewer` reads only. A closed, enumerable role set is what makes `TEST-PLAN.md`'s own "complete role/resource/action matrix" requirement achievable as a literal finite test matrix rather than an open-ended fuzzing target -- the same reasoning Phase 6 Decision 3 used for closing `INSIGHT-CONTRACT.md`'s `kind` enum instead of leaving it free text.

**`resource_grants` are the explicit, bounded exception mechanism** (`id`, `workspace_id`, `grantee_account_id`, `resource_type`, `resource_id`, `actions` (array), `granted_by`, `expires_at` nullable, `revoked_at` nullable) -- resource/action/time scoped per `PERMISSION-CONTRACT.md`'s own line, the same "narrow, purpose-bound, revocable" shape `cross_domain_grants` already established for Phase 7. A grant can widen access to a specific resource beyond a role's baseline (e.g. a `member` given `read` on one `shared_explicitly` item); it can never widen access to an entire `private`-visibility resource class, and never to any Phase 7 personal-domain table at all (see below).

**The authorization decision, concrete and total (every branch reachable, none implicit):**

1. `auth.user_id`'s current `workspace_memberships.status != 'active'` for `auth.workspace_id` -> deny (a revoked/suspended/removed member has zero authority regardless of any grant or role, checked first, every request).
2. Requester is the resource's own `owner_id` -> allow every action *except where a domain's own contract further restricts it* (Phase 7's own retention/encryption/professional-referral rules keep applying unchanged -- Decision 2 does not loosen anything Phase 7 already decided).
3. Resource `visibility = 'private'` and requester is not the owner -> deny, unconditionally, **with one structural carve-out named explicitly, not left to a future oversight: every Phase 7 personal-domain table (`personal_domains`, `domain_consents`, `domain_sources`, `domain_records`, `goals`, `routines`, `check_ins`, `personal_insights`, `personal_insight_feedback`, `cross_domain_grants`) is hardcoded `private` with no code path that ever sets it to `shared_explicitly` or `workspace`, and `resource_grants` rows targeting these tables are rejected at write time by a `CHECK`-equivalent (`_UNGRANTABLE_RESOURCE_TYPES` allowlist rejection in `authz.py`, enforced before any grant insert), not merely never issued by convention.** This is `PHASE-008-multi-user.md`'s own out-of-scope line ("default sharing of personal domains") made impossible rather than merely undefaulted, extending F-04's "Phase 8 roles do not grant private-vault access" from a stated constraint into an enforced one, the same "structural not conventional" move Decision 2 of the Phase 7 design doc made for cross-domain leakage.
4. Resource `visibility = 'shared_explicitly'` -> allow only if an active (`revoked_at IS NULL`, `expires_at` future-or-null) `resource_grants` row names this requester, this resource, this action.
5. Resource `visibility = 'workspace'` -> allow if the requester's current role's fixed permission set includes `{resource_type}:{action}`.
6. None of the above matched -> deny. No implicit allow path exists anywhere in this function.

**Deny is server-side and pre-query, not a post-hoc filter.** Every domain's list/get/mutate endpoint calls `authorize()` before constructing its SQL (a denied single-resource `GET` returns `404`, never `403`, so an unauthorized caller cannot distinguish "does not exist" from "exists but you can't see it," matching `API-SCHEMAS.md`'s own "Sensitive private content returns 404 to unauthorized callers"); a denied list endpoint filters visibility server-side in the `WHERE` clause (`owner_id = :requester OR visibility = 'workspace' OR id IN (:granted_ids)`), never client-side, matching `PERMISSION-CONTRACT.md`'s "UI hiding is not security."

**Background jobs re-check, never cache authority across a job's own lifetime.** Automation (`ecc.domains.automation`) and connector-sync (`ecc.domains.engineering`) background work already runs under a captured `AuthContext`/actor at job-start; Task 3/4 add an explicit `authorize()` call immediately before each job's own side-effecting step (not once at enqueue time), so a permission or membership change mid-run takes effect on the very next side effect rather than only on the job's next full run -- directly what `PERMISSION-CONTRACT.md`'s "Background jobs snapshot no broader authority... and re-check before side effects" requires and what Decision 4's revocation SLO below depends on.

**Rollout is generic-mechanism-first, one reference domain second, breadth third -- Phase 7's own precedent, not a new pattern.** Task 3 builds `authz.py` plus the schema migration for every table, and wires it end to end into one reference domain (`engineering`, chosen because it is this codebase's largest and most-reused existing domain, the same "prove the framework before spending it everywhere" reasoning Phase 7 Decision 1 used picking `habits`); Task 4 widens the same mechanism to every remaining domain (knowledge, attention, automation, AI runtime, calendar/scheduling) -- mechanical repetition of a proven pattern, not new design.

## Decision 3 (approval gate): invitation verification

**Invitations are recipient-bound by email, single-use, expiring, and re-verified at acceptance time against the accepting account's own email -- every property independently enforced, not merely one check standing in for all four.** `invitations`: `id`, `workspace_id`, `email` (the sole recipient binding), `role` (the role granted on acceptance), `token_hash` (`SHA-256`, the exact `sessions.token_hash` pattern -- the raw token is returned once at creation and never stored, mirroring `backend/ecc/auth.py`'s existing session-token discipline exactly, not a new secret-handling mechanism), `invited_by` (`users.id`), `expires_at` (7 days, matching `sessions`' own existing 7-day session lifetime as this codebase's established default freshness window), `accepted_at`/`rejected_at`/`revoked_at` (mutually exclusive terminal states), `created_at`.

**Verification, concrete, at every stage:**

1. **Creation** (`POST /workspaces/{id}/invitations`, `owner`/`admin` role required via Decision 2's `authorize()`): rejects if `email` already has an `active` `workspace_memberships` row in this workspace (no duplicate-member invitation), and rejects a second concurrently-pending (`accepted_at IS NULL AND rejected_at IS NULL AND revoked_at IS NULL AND expires_at > now()`) invitation for the same `(workspace_id, email)` pair -- re-inviting requires revoking the pending one first, closing the "duplicate/expired tokens" test case `TEST-PLAN.md` names explicitly, at the write path rather than leaving two live tokens for the same recipient to reason about.
2. **Delivery.** No new technology -- this codebase has no approved outbound-email sending capability in `RFC-005.md` today, and adding one is out of this design's scope (a real SMTP/transactional-email provider would itself need its own RFC-005 amendment and ADR, the same gate Phase 6's OAuth providers and Phase 4's Ollama activation each went through, not something a permissions-focused phase design should bundle in as an incidental dependency). The invitation-accept link (containing the raw token, once) is returned directly to the inviter in the `POST /workspaces/{id}/invitations` response for them to deliver out-of-band (copy/paste, matching how `scripts/bootstrap_dev.py`'s own one-time bootstrap code is already handed to an operator directly, not emailed) -- real email delivery is named in the Deferred backlog this document's own "Task N scope" section states below, not silently assumed to already exist.
3. **Acceptance** (`POST /invitations/{id}/accept`, requires an authenticated `accounts` session -- if the caller has no account yet, `POST /accounts` (new, unauthenticated, email+password) must run first, itself requiring the raw token as a query parameter so account creation is never usable to enumerate pending invitations by workspace): the endpoint independently checks (a) `token_hash` matches (constant-time compare, mirroring `require_csrf`'s existing `compare_digest` discipline), (b) `expires_at > now()`, (c) `accepted_at IS NULL AND rejected_at IS NULL AND revoked_at IS NULL`, and (d) **the authenticated caller's own `accounts.email` case-insensitively equals `invitations.email`** -- this fourth check is `API-SCHEMAS.md`'s own "Invitation... payloads cannot assert recipient identity after acceptance" line made concrete: accepting with a different, already-authenticated account than the one the invitation named is rejected even if that account holds a technically-valid, unexpired token for someone else's inbox. All four checks happen inside one transaction with the row locked (`SELECT ... FOR UPDATE`), so two concurrent accept attempts against the same token cannot both succeed -- the exact `lock_idempotency` discipline this codebase's idempotency-key mechanism already uses for double-submit protection, applied here to prevent a token being consumed twice.
4. **Single-use, enforced by the same transaction, not by convention.** A successful accept sets `accepted_at` and, in the same transaction, creates the `users`/`workspace_memberships` rows -- any second use of the same token after that point fails check (c) above deterministically, not merely "shouldn't happen in practice."
5. **Rejection/revocation** are symmetric, equally final: `POST /invitations/{id}/reject` (recipient-initiated, same email-match check as acceptance) and revocation (inviter/admin-initiated, no email-match check needed since the inviter is by definition authorized) both set their own terminal timestamp and are equally checked by (c) above.

## Decision 4 (approval gate): revocation propagation SLO

**Revocation is naturally near-real-time because this codebase has never introduced request-scoped or long-TTL permission caching -- the 60-second target `PHASE-008-multi-user.md`'s own non-functional requirement names is a ceiling this design stays structurally far under, not a target requiring new invalidation infrastructure to hit.** Every `authorize()` call (Decision 2) reads `workspace_memberships.status`, `resource_grants.revoked_at`/`expires_at`, and `sessions.revoked_at` fresh from PostgreSQL on every single request -- there is no in-process or Redis-backed permission cache anywhere in this design to invalidate, the same reasoning `sessions.revoked_at`'s own existing real-time check already relies on for today's single-user session revocation.

**Concrete propagation paths, each measured against the same 60-second ceiling:**

1. **Membership revocation/suspension** (`workspace_memberships.status` set to `suspended`/`removed`): the next request on any existing session for that account against that workspace re-derives `AuthContext` via `require_auth_context()` and then hits Decision 2's step 1 (`status != 'active'` -> deny) -- effectively immediate, bounded only by network round-trip, not a polling interval. Existing `sessions` rows for that `(workspace_id, users.id)` pair are also explicitly revoked (`sessions.revoked_at = now()`) in the same transaction as the membership change, so a request already mid-flight when the change commits still fails the *session* lookup even if it raced past the membership check -- two independent revocation paths converging on the same request, not one relied on alone.
2. **`resource_grants` revocation** (`revoked_at` set): the next `authorize()` call against that resource re-reads the row fresh and Decision 2's step 4 fails -- same immediacy, no separate propagation mechanism needed since grants were never cached.
3. **Background/automation jobs already in flight when a revocation commits**: Decision 2's "re-check before each side effect, not once at job-start" requirement is what bounds this path -- a long-running job's *next* side-effecting step (not its next full run) re-evaluates `authorize()` against current state, so the propagation bound for a background job is one step-interval, not one full job-cycle. `ecc.domains.automation`'s existing step-by-step execution model (already stepwise, per Phase 5's own design) is what makes this bound achievable without restructuring how jobs run.
4. **Account-level disable** (`accounts.disabled_at` set, e.g. an operator response to a compromised account) revokes every `sessions` row across every workspace that account has a `users` row in, in one transaction keyed on `account_id` -- the single kill switch Decision 1 named `accounts.disabled_at` for, covering every workspace at once rather than requiring a separate revocation per membership.

**Measured, not merely argued.** `TEST-PLAN.md`'s own "revocation propagates to sessions/caches/background work within 60 seconds" non-functional requirement becomes a real integration test in Task 3/4 -- revoke a membership/grant, assert the very next request (not a request after a sleep) is denied, and a separate test asserting a background job's in-flight step re-checks and fails after a mid-run revocation, mirroring how Phase 6's own connector-token-rotation tests proved propagation rather than asserting the mechanism "should" work.

## Task 1 scope for this activation

Per the sequence Decision 1/2 above imply, this activation delivers:

- Migration: `accounts` (new); `users` gains `account_id`, loses `email`/`password_hash`; `workspace_memberships` (new); backfill of every existing `users` row into a matching `accounts` row plus an `active`/`owner`-role `workspace_memberships` row (the sole pre-existing user in each workspace becomes that workspace's first `owner`, matching how the dev-bootstrap script already treats the sole user today).
- `ecc.platform.accounts` (or equivalent, finalized against `STD-001`'s layout rule when Task 1 lands): Argon2id password hashing, `POST /accounts` (invitation-token-gated, see Decision 3), `POST /auth/login`, `POST /auth/select-workspace`, session creation reusing `backend/ecc/auth.py`'s existing cookie/CSRF mechanism unchanged in shape.
- `GET /workspaces` (every workspace the authenticated account has an `active` membership in -- the workspace-switcher's own data source), `GET|PATCH /workspaces/{id}` (name/settings, `owner`/`admin` only for `PATCH`).
- Tests: account creation/login/logout, multi-workspace session selection, `users`/`workspace_memberships` backfill migration round-trip (upgrade/downgrade against real Postgres, per this repository's own established migration-verification discipline), cross-account isolation (account A can never select a workspace it has no active membership in, even by guessing a `workspace_id`).

Invitations (Decision 3), the authorization engine and its schema-wide visibility/owner migration (Decision 2), sharing, delegation, notifications, and ownership transfer/removal remain out of this activation's scope, tracked as "Not started" in `docs/phases/phase-008/IMPLEMENTATION-STATUS.md` until their own task lands per the companion implementation plan.
