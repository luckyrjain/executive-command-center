# Phase 6 Engineering Workspace Implementation Plan

Companion to `docs/superpowers/specs/2026-07-27-phase-6-engineering-workspace-design.md` (the decisions) -- this document is the task sequence and per-task scope, mirroring the shape of `docs/superpowers/plans/2026-07-25-phase-5-automation-design.md`'s own task breakdown.

## Task 1 — Connector framework and source projections (this activation)

- Migration: `connector_accounts`, `sync_cursors`, `sync_runs` (`docs/phases/phase-006/DATA-MODEL.md`). The remaining projection tables (`repositories`, `engineering_work_items`, `changes`, `reviews`, `deployments`, `incidents`, `engineering_decisions`, `service_links`, `delivery_metric_snapshots`, `source_tombstones`) are added by Tasks 2-6 below, the task that first populates each one -- matching Phase 5 Task 1's identical precedent (`workflow_runs` wasn't created until Task 2's own migration).
- `ecc.domains.engineering.connectors`: `ConnectorAdapter` Protocol (`authorize`/`backfill`/`incremental_sync`/`handle_webhook`/`refresh_permissions`/`disconnect` -- "validate" is folded into `authorize`'s return value, not a separate method) and `ConnectorRegistry`, mirroring `ecc.domains.automation.adapters.ActionAdapter`'s structural-typing shape.
- `ecc.domains.engineering.crypto`: Fernet-based `encrypt_credential`/`decrypt_credential` over `ECC_CONNECTOR_TOKEN_ENCRYPTION_KEY`.
- `ecc.domains.engineering.sandbox_adapter`: one deliberately-fake `sandbox.github` adapter (no network call) registered into the shared production registry, exercising the full contract shape end to end.
- `ecc.domains.engineering.connector_accounts`: `GET|POST /api/v1/engineering/connectors`, `POST .../{id}/sync`, `POST .../{id}/disable`, `GET /api/v1/engineering/sync-runs`.
- Tests: workspace isolation, credential-never-returned, backfill/incremental/disconnect lifecycle against the sandbox adapter, encrypted-storage round-trip.

## Task 2 — GitHub read sync

**Repositories complete.** Real GitHub REST API backfill/incremental sync through the same `ConnectorAdapter` contract Task 1 defines (`github_adapter.GitHubAdapter`, migration `0045_phase6_repositories.py`). Task 1's disclosed pool-exhaustion risk is resolved (`sync_connector_endpoint`/`create_connector_endpoint` restructured into phases across separate pooled connections, with a partial-unique-index-backed guard (`uq_sync_runs_running_per_account`, migration `0046`) serializing concurrent syncs per account after review found the initial restructuring alone reintroduced idempotency/cursor races -- see `connector_accounts.py`'s own module docstring).

**Deferred to a Task 2 follow-up, not yet done:** work items (issues), changes (commits/PRs), reviews, deployments (`DATA-MODEL.md`'s remaining projection tables); webhook ingestion has no receiving HTTP endpoint or webhook-secret storage yet (`GitHubAdapter.handle_webhook` implements the parsing/upsert logic but is not wired to a public route -- see that module's own docstring for why).

## Task 3 — GitLab read sync

**Complete.** Real GitLab REST API backfill/incremental sync through the same `ConnectorAdapter` contract Task 2 implements for GitHub (`gitlab_adapter.GitLabAdapter`) -- no new migration, since `repositories` (migration `0045_phase6_repositories.py`) already names `gitlab` in its provider CHECK constraint. Applies every lesson Task 2's own review rounds found from the first version: real scope checking (`GET /personal_access_tokens/self` always returns actual granted scopes, no fabricated-fallback risk), a still-rate-limited retry degrading to `partial` rather than raising, the `_MAX_PAGES_PER_CALL` bound reporting `partial` rather than a silent `succeeded`, and `response.links` for `Link`-header pagination. Genuine (not no-op) best-effort `disconnect()` via `DELETE /personal_access_tokens/self`, realistically expected to fail at this connector's own default read-only scopes. Same deferrals as Task 2: work items/changes/reviews/deployments and webhook ingestion's receiving endpoint.

## Task 4 — Jira work-item sync

**Complete.** Real Jira Cloud REST API v3 backfill/incremental sync through the identical `ConnectorAdapter` contract Tasks 2-3 implement (`jira_adapter.JiraAdapter`, migration `0047_phase6_work_items.py` -- work items only, since Jira is not a source-control provider, so there is no repository/change/review/deployment analogue for this adapter at all). Resolves a genuine architectural difference from GitHub/GitLab rather than cutting a corner: Jira Cloud is multi-tenant (a customer-chosen `{site}.atlassian.net` host per connection), so the stored credential is pipe-delimited (`"{site}|{email}|{api_token}"`) and this adapter builds its own request URL per call. HTTP Basic auth (email + API token, Atlassian's documented mechanism for personal API tokens); offset-based pagination (`startAt`/`maxResults`/`total`, no `Link` header); `authorize` always returns an honestly-empty `granted_scopes` since a personal API token has no scope grant to report at all (`required_scopes` is the empty set -- the most degraded case in this codebase's "never fabricate a scope match" lineage, past GitHub's fine-grained-PAT gap and GitLab's always-real scopes); rate-limit handling mirrors `gitlab_adapter.py`'s shape (`429` + `Retry-After`, a still-rate-limited retry degrading to `partial`, the `_MAX_PAGES_PER_CALL` bound reporting `partial`). `disconnect()` is a documented no-op, like GitHub's (not GitLab's) -- Atlassian exposes no public self-revocation API for a personal API token. Same deferrals as Tasks 2-3: webhook ingestion's receiving endpoint, access loss/deletion/rename detection, metric fixtures, ambiguous identities.

## Task 5 — Delivery and reliability metrics

**Complete, partial scope disclosed.** Implements the seven metric definitions and windows from the design doc's Decision 3 table, snapshot computation, and the coverage-threshold policy (95% complete / 50% insufficient) -- against real data. **Only three of the seven metrics are genuinely computable this task: `work_ageing`, `blocked_work`, `review_latency`.** The other four (`delivery_frequency`, `lead_time_for_changes`, `change_failure_rate`, `time_to_restore`) all require `deployments` and/or `incidents` data, and neither table exists yet -- `incidents` is Task 6's own scope; `deployments` was never assigned to any task by name in this plan, a real gap this task's own review found and disclosed rather than silently expanding scope to close by itself. These four always report `insufficient_coverage`/`value=None`.

To make `review_latency`/`work_ageing` real rather than deferred alongside the other four, this task also: extends `github_adapter.GitHubAdapter` with `change` (merged PRs, per-repository fan-out over already-synced `repositories`, chosen over the GitHub Search API's separate stricter rate limit) and `review` (sourced from already-synced `changes`, a second timeline call per change for `review-requested-at`) sync -- GitLab's own equivalent is deferred to a Task 5 follow-up, since its real API shape (a global merge-request endpoint, but a Premium-only approvals endpoint) needs its own design pass, not a copy of GitHub's; and adds `engineering_work_items.provider_created_at`, a Task 4 gap `work_ageing` exposed (that metric needs an item's real creation date, not merely when this system first observed it). `GET /engineering/metrics` computes and persists a fresh snapshot on every call (no periodic scheduler exists yet in this phase) -- a disclosed departure from pure REST `GET` semantics, mirroring `POST /connectors/{id}/sync`'s own identical reality since Task 1.

## Task 6 — Decisions, incidents and knowledge linking

**Complete, partial scope disclosed.** Implements `incidents`/`engineering_decisions` capture, resolve/decide transitions, listing, and correlation to `changes` (via `incident_changes`/`decision_changes` join tables, migration `0049`) -- making `time_to_restore` the fourth genuinely computable metric (Task 5 left it, along with `delivery_frequency`/`lead_time_for_changes`/`change_failure_rate`, always `insufficient_coverage` since no `incidents` table existed yet). `delivery_frequency`/`lead_time_for_changes`/`change_failure_rate` remain blocked -- all three still need `deployments`, which this plan never assigns to any task.

Two real gaps deliberately deferred, not silently absent, matching this phase's own established precedent for splitting a task's real scope across PRs (Task 5's GitLab change/review-sync deferral is the identical pattern): correlation to `deployments`/work items (no concrete caller populates a second pair of join tables yet); and ambiguous-identity resolution raised against Phase 2's existing `resolution_candidates`/`merge_entities` endpoints (design doc's "why this isn't a green field" section) rather than a second resolution mechanism -- `engineering_work_items.reporter_external_id`/`assignee_external_id`, `changes.author_external_id` and `reviews.reviewer_external_id` all remain unresolved raw provider identifiers after this task; wiring them into Phase 2's real scoring/threshold/deterministic-match logic is a substantial integration in its own right, deferred to a documented follow-up.

## Task 7 — Approved write actions

**Complete, partial scope disclosed.** GitHub/GitLab/Jira write actions registered as `ecc.domains.automation.adapters.ActionAdapter`s (`ecc.domains.engineering.write_actions`), dispatched through the existing Phase 5 `worker.py` gate under an `automation_policies` row -- no second authority mechanism, no new migration or HTTP endpoint.

Neither this plan doc nor the design doc names a concrete action taxonomy (only write *scopes* -- `repo`/`api`/`write:jira-work` -- are named in Decision 2). This task ships **one action concept, three provider flavours: add a comment to an existing GitHub issue/PR, GitLab issue, or Jira issue** (`github.add_issue_comment`/`gitlab.add_note`/`jira.add_comment`), chosen deliberately over create-issue/PR/MR, merge, transition, label and close because it is the only write uniformly, cleanly reversible across all three providers (GitHub's REST API has no endpoint to delete an issue at all), creates no new external business identity, and maps onto the closed high-impact taxonomy (`public`) with no judgment call. Every adapter declares `high_impact_categories={"public"}` unconditionally -- not merely the honest taxonomy answer, but the actual, load-bearing access control, since `automation/policy.py`'s own documented gap ("`action_types`/`data_classes`/`value_limit` are stored but never enforced against a dispatching adapter") means this is the one real control guaranteeing a fresh, digest-bound, human approval on every dispatch regardless of the authorizing policy's own `approval_mode`.

Two real gaps deliberately deferred, disclosed rather than silently absent: containment is asymmetric across providers (GitHub/Jira validate the target against this workspace's own already-synced `repositories`/`engineering_work_items`; GitLab has no synced issue/MR projection to validate against yet, since its own change/review sync remains a Task 5 follow-up); and no `compensate()` is implemented, since `ActionAdapter.compensate(action_input)` receives only the original input, never the provider-assigned comment id `execute()` alone learns -- a dedicated `github.delete_issue_comment`-style adapter is the documented follow-up if a real caller needs it.

## Task 8 — Executive UX and browser acceptance

**Complete.** Engineering Overview, Delivery, Reliability, Repository, Incident, Decision, Connector Health and Coverage frontend views per `UX-STATES.md` (`frontend/src/features/engineering/`, a tabbed `EngineeringWorkspace` shell mirroring `AutomationWorkspace.tsx`'s own pattern), plus Playwright acceptance coverage of the required degraded states (first sync, backfill, partial permissions, stale connector, rate limited, disconnected, provider unavailable, conflicting identities) -- all eight states verified end to end with `@axe-core/playwright` accessibility checks.

One real, disclosed scope addition: neither this plan doc nor the design doc named a concrete query surface for `repositories`/`engineering_work_items` (Tasks 2/4's own scope was sync only), and the Repository/Coverage views have nothing to query without one -- `GET /engineering/repositories`/`/work-items` were added as thin, workspace-scoped list endpoints, the identical "add the query endpoint the UX genuinely needs" pattern Tasks 5-7 each already set a precedent for. `GET /engineering/changes`/`/deployments`/`/overview` remain unimplemented: no view in this task's own eight surfaces needs a `changes` list (only opaque `change_ids` references), `deployments` has no data source at all yet (same gap Tasks 5-6 already disclosed), and "overview" is served entirely by composing already-existing endpoint responses client-side.

Conflicting identities is necessarily a disclosure state, not an interactive resolution flow: this phase has no identity-resolution mechanism for engineering data (`engineering_work_items.reporter_external_id`/`assignee_external_id` remain unresolved raw provider identifiers, per Task 6's own disclosed deferral), so the Coverage view surfaces them as a labeled sample list rather than fabricating a merge control with no backend behind it.

A genuine component bug was found and fixed by the Playwright browser-acceptance run itself, before this task's PR was opened: the Connector Health view's "no sync has ever run" state was keyed partly on connector status rather than sync-run history alone, so it stayed shown even once a connector's first backfill was already in progress -- a contradiction a purely-mocked unit test's own fixture happened not to exercise.
