# Phase 7 Personal Intelligence Implementation Plan

Companion to `docs/superpowers/specs/2026-07-31-phase-7-personal-intelligence-design.md` (the decisions) -- this document is the task sequence and per-task scope, mirroring the shape of `docs/superpowers/plans/2026-07-27-phase-6-engineering-workspace.md`'s own task breakdown.

## Task 1 — Domain/consent/vault framework and the `habits` reference domain (this activation)

- Migration: `personal_domains`, `domain_consents`, `domain_records`, `domain_sources`, `goals`, `routines`, `check_ins`, `deletion_jobs` (`docs/phases/phase-007/DATA-MODEL.md`). `cross_domain_grants` and `personal_insights` beyond deterministic kinds are added by Task 5 below, the task that first needs them -- matching Phase 6 Task 1's identical precedent (`sync_runs`-style "not every table upfront").
- `ecc.domains.personal.crypto`: Fernet-based `encrypt_field`/`decrypt_field` over `ECC_PERSONAL_DATA_ENCRYPTION_KEY`, mirroring `ecc.domains.engineering.crypto`'s shape (dedicated key, decrypted value never logged/returned/audited) but field-level (`domain_records.payload`'s individual sensitive/high_stakes keys) rather than whole-column, since `standard`-classified fields on the same record must stay plaintext/queryable.
- `ecc.domains.personal.domains`: domain enable/disable (default `false` per domain per user), consent grant/revoke, generic `domain_records`/`domain_sources` CRUD enforcing per-field encryption by the owning domain's classification tier.
- `ecc.domains.personal.habits`: the one reference domain -- habit definitions, check-ins, deterministic streak/gap insights (no model call).
- `ecc.domains.personal.export_deletion`: export (human- and machine-readable) and deletion-job propagation, proving the mechanism every later domain reuses rather than reimplementing.
- `GET|POST /personal/domains`, `POST .../{id}/enable|disable|export|delete`, `GET|POST /personal/records`, `GET|PATCH /personal/records/{id}`, `GET|POST /personal/goals|routines|check-ins`, `GET|POST /personal/consents`, `POST /personal/consents/{id}/revoke`, `GET /personal/insights`, `POST /personal/insights/{id}/dismiss` (`.../feedback` deferred to Task 5).
- Tests: workspace/user isolation, disabled-domain-blocks-all-access, encrypted-field-never-returned-in-list-view, export completeness, deletion propagation, and the always-in-scope adversarial fixtures (no diagnostic/scoring language leaking even from a `standard` domain).

## Task 2 — `learning` domain (complete)

**Confirmed: no new mechanism needed, as this task's own plan anticipated.** `learning` is `standard`-classified, identical to `habits` -- Task 1's domain enablement and generic `domain_records` CRUD already accept any closed-enum `domain_key`. `tests/test_personal_learning_postgres.py` proves enable/list/disable, `course`/`resource` record CRUD (including a `course`'s `progress_pct` update), and whole-domain export/delete all work unmodified; `docs/phases/phase-007/DATA-MODEL.md`'s "Task 2 status" section documents the `course`/`resource` `record_type` payload conventions. No `goals`/`routines`/`check_ins` convention defined for `learning` -- course progress is better served by `domain_records.payload.progress_pct` than by forcing a recurring-habit shape onto content that isn't one; not attempted without a real usage need driving it.

## Task 3 — `travel` domain (complete)

**No new table or migration -- one small, generic API addition.** `travel` is `standard`-classified, identical to `habits`/`learning`. `GET /personal/records` gains two optional query parameters, `effective_from`/`effective_until` (inclusive on both bounds), filtering on the existing `domain_records.effective_at` column -- generic on the endpoint, not `travel`-specific. `travel`'s own `trip` `record_type` convention (`payload`: `destination`, `start_date`, `end_date` optional, `notes` optional; `effective_at` set to the trip's `start_date`) is the first domain to give this filter a real reason to exist -- structured, meaningfully time-ranged records. `tests/test_personal_travel_postgres.py` proves enable/independent-domain isolation, `trip` record CRUD, the date-range filter (range match, inclusive exact-instant boundary, from-only/until-only bounds, empty-result range), and whole-domain export/delete. `docs/phases/phase-007/DATA-MODEL.md`'s "Task 3 status" section documents the convention and clarifies retention itself is unchanged (`standard` stays retained indefinitely -- "retention-by-date-range" means the record's own date range is queryable, not that records expire on a timer). No `goals`/`routines`/`check_ins` convention defined for `travel`, same reasoning as `learning`'s own Task 2 finding.

## Task 4 — `relationships` domain (complete)

`sensitive` classification -- first domain the F-04 non-scoring invariant binds directly. No relationship-health score, no contact-frequency ranking, anywhere in this task's schema or UI (structurally true by omission: no such field exists in `contact`/`interaction`'s own payload conventions or anywhere else in this task's diff). Also the first domain to populate `ecc.domains.personal.crypto` for real -- `notes` (on both `contact` and `interaction` record types) is Fernet-encrypted individually within `payload`; `contact_name`/`relationship_type`/`interaction_type` stay plaintext/queryable. `ecc.domains.personal.domains._encrypt_payload`/`_decrypt_payload` wrap the crypto module around the existing `_ENCRYPTED_FIELD_NAMES_BY_RECORD_TYPE` mechanism (already structurally present since Task 1, previously exercised against nothing). A real gap found and fixed along the way: `export_domain_endpoint` (`export_deletion.py`) read `domain_records.payload` directly, bypassing decryption entirely -- for `relationships` this would have exported ciphertext instead of the human-readable export `DOMAIN-PRIVACY-CONTRACT.md` requires; fixed by decrypting each record's payload before it enters the export response. A second real gap: the idempotency cache (`idempotency_records.response_body`) would otherwise have persisted a decrypted `notes` value verbatim across a replayed create/update request -- fixed by building the cached response from the still-encrypted row and decrypting only the copy returned to the caller (and any later cache-hit replay, decrypted at read time, never at write time). `tests/test_personal_relationships_postgres.py` proves `notes` is genuinely ciphertext in `domain_records.payload` at rest (not merely absent from the API response), list responses redact it, single-record/export responses decrypt it, and the idempotency-records row itself never holds the decrypted value. `docs/phases/phase-007/DATA-MODEL.md`'s "Task 4 status" section and `DOMAIN-PRIVACY-CONTRACT.md`'s own "Task 4 confirmation" paragraph have the full detail.

## Task 5 — Cross-domain grants and the first AI-generated insights (split into two PRs)

**Repository-owner directed split** -- this task as originally scoped bundles a new database table with a whole new Phase 4 evaluated task type, materially larger and riskier than Tasks 2-4 each were.

**Part 1 (complete).** `cross_domain_grants` schema (migration `0056_phase7_cross_domain_grants.py`) and grant lifecycle (`ecc.domains.personal.grants`: `GET|POST /personal/grants`, `POST .../{id}/revoke`) only -- no consumer reads a grant yet. Schema resolved from `DATA-MODEL.md`'s own "source domain, target purpose, fields/categories and expiry" description: `purpose` (closed enum, `insight_generation` the only value defined) rather than a second domain column; `granted_categories` (JSONB string array); lifecycle mirrors `domain_consents` (grant once, later only ever revoke, no `version`/`updated_at`/`created_by`). `tests/test_personal_grants_postgres.py` (9 tests) covers create/list/revoke, both list filters, idempotent revoke, unknown-grant 404, cross-workspace isolation, and request-schema rejections. `scripts/seed_phase1_acceptance.py` updated proactively for the new workspace-scoped table (verified: exactly 2 rows).

**Part 2 (complete).** `personal.generate_insight`, a new Phase 4 evaluated task type (migration `0057_phase7_insight.py`) -- `trend`/`correlation` insights, gated on Phase 4's own evaluation-floor discipline: a versioned 10-example dataset (migration `0058_phase7_insight_eval.py`, `tests/fixtures/phase7_evaluation_personal_insight.py`) whose five adversarial examples clear `INSIGHT-CONTRACT.md`'s full safety-rubric category set (diagnostic claims, prescriptive treatment, guaranteed-return language, credit/employment/insurance-decision language, sensitive-trait inference) at the same 100%-floor rigor `attention.explain_item`/`meeting.prep_summary` are already held to -- gated into `prompts.py:_GATED_PROMPT_IDS` identically. `personal.get_insight_sources` (`ecc.domains.personal.insight_tools`) is the tool that actually checks a grant (created in part 1) before combining domains -- refuses any requested domain that is not both currently enabled and actively granted. `POST /personal/insights/generate` (`ecc.domains.personal.ai_insights`, gated behind `config.py:personal_ai_insight_generation_enabled`, default `False`) is the production call site, fail-open like `meeting_prep.py`'s own enrichment. `POST /personal/insights/{id}/feedback` ships here (a new, `kind`-less `personal_insight_feedback` table, migration `0059_phase7_insight_feedback.py`), alongside `personal_insights.professional_referral_note` (conditionally required for any `high_stakes`-sourced insight, enforced by `validator.check_personal_insight_grounding`). `tests/test_ai_runtime_personal_insight_evaluation_postgres.py` and `tests/test_personal_ai_insights_postgres.py` cover the harness and the production endpoints respectively.

## Task 6 (complete) — `health` domain

`high_stakes` classification -- the safety rubric from the design doc's Decision 4, already proven structurally on `habits`/`learning`/`travel`/`relationships`, now enforced against real diagnostic-language risk for the first time. No new table or migration; `RecordCreateRequest.retention_acknowledged` enforced generically at `create_record_endpoint` (`422 RETENTION_ACKNOWLEDGEMENT_REQUIRED` when a `high_stakes`-domain record omits it), setting `retention_acknowledged_at` for real for the first time since the column was added unenforced in Task 1's migration `0054`. `vital_reading`/`symptom_log` record types, with `symptom_description`/`notes` Fernet-encrypted (`_ENCRYPTED_FIELD_NAMES_BY_RECORD_TYPE`) -- `symptom_description` matches `DOMAIN-PRIVACY-CONTRACT.md`'s own pre-existing worked example. First genuine end-to-end proof (not just the Task 5 part 2 evaluation harness's synthetic fixtures) that `professional_referral_note` is actually required and enforced for a real `high_stakes`-sourced insight: a mocked model response omitting the note is rejected via `missing_professional_referral` grounding failure, an otherwise-identical response including it persists. `tests/test_personal_health_postgres.py` (8 tests).

## Task 7 (complete) — `finance` domain

`high_stakes` classification, same rubric adapted for regulated-advice/guaranteed-return risk (`must_not_state` fixtures: guaranteed returns, credit/employment/insurance-decision language, already covered generically by Task 5 part 2's adversarial fixture set, anchored in `health`/`finance` sources from the start). No transaction execution or bank-account write access -- `PHASE-007-personal-intelligence.md`'s own out-of-scope line; `transaction` is a manually-entered ledger record the user logs themselves, not a real money movement. No new table, migration, or application-code mechanism -- every enforcement Task 6 built (`retention_acknowledged`, field-level encryption, `professional_referral_note`) is generic on `classification`, so `finance` inherited all three automatically. `account`/`transaction` record types, with `account_notes`/`memo` Fernet-encrypted -- field names matching the design doc's own worked example for this domain. Second real end-to-end proof (after `health`, Task 6) that `professional_referral_note` fires correctly for a `high_stakes` domain, confirming the mechanism generalizes rather than happening to work once. `tests/test_personal_finance_postgres.py` (8 tests).

## Task 8 (complete) — Executive UX and browser acceptance

One domain-generic `PersonalWorkspace` (`frontend/src/features/personal/`: `DomainsPanel`, `RecordsPanel`, `InsightsPanel`, `GrantsPanel`, `ExportDeletePanel`) covering all six domains through a single `domain_key`-parameterized UI, mirroring `EngineeringWorkspace.tsx`'s shell and this backend's own "a caller names a `domain_key`, never a domain-specific code path" convention -- not six bespoke domain surfaces. Every `UX-STATES.md`-required state covered or honestly disclosed as not implemented (`import pending` -- no real import path exists anywhere in this activation, so no UI was built to fake one). Cross-domain grant management (`GrantsPanel`, including the first place in this phase anything computes an `active`/`expired`/`revoked` state from `cross_domain_grants.expires_at`). Playwright acceptance (`personal-domain-lifecycle.mjs`) covering enable -> capture -> grant create/revoke -> inspect/dismiss insight -> export -> delete end to end, with `@axe-core/playwright` accessibility checks after every tab switch. 35 component tests across 5 files. `docs/phases/phase-007/UX-STATES.md`'s own Task 8 section has the full per-state detail.
