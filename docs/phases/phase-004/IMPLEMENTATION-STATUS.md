**A real, second-model-caused correctness gap found and fixed while implementing this.** `evaluation.py`'s `run_evaluation(model_id=...)` was documented as an "assertion, not an override" -- verifying the requested model is registered and eligible, then letting `execute_run` route normally -- but `execute_run` has no way to pin a specific candidate, and nothing checked that the model it actually routed to matched the one requested. ### Task 8 evidence -- Reflection Engine (first slice) on `attention.explain_item`

The repository owner's re-raised deferred-scope item -- "Agent Runtime, multi-agent coordination, Reflection Engine" (design doc's Decision 8 deferred-scope line) -- narrowed to its smallest concrete first piece, per an explicit follow-up decision: one additional, optional, bounded, fail-open model call on `attention.explain_item`, not the design doc Chapter 3's fuller multi-agent Coordinator/Agent-Runtime architecture.

**Backend.** `backend/ecc/domains/ai_runtime/runtime.py`: `_reflect_on_answer` (new), called from `execute_run` after grounding passes and before the run is persisted `completed`. Reuses the existing `call_model` closure verbatim (inherits `RunGuard`'s total-wall-clock budget check with zero new mechanism) and the existing `_render_factors_block`/untrusted-data-delimiter convention (refactored into a shared `_wrap_untrusted_data` helper, reused by a new `_render_prior_answer_block` for the model's own prior answer). Every failure mode (timeout, cancelled, provider error, total-wall-clock budget exceeded, output-token budget exceeded, tool-call-shaped response, schema-invalid reflection response, a proposed revision that itself fails `validate_output`/`check_explain_item_grounding`) is fail-open: the run always completes with the original, already-validated-and-grounded answer. Only a revision that independently passes the exact same validation/grounding checks the original did can replace it. Deliberately does not feed `_breaker_for(...)`'s circuit breaker -- a reflection-layer failure must not degrade the primary task's routing eligibility for that model.

**Review-driven fix.** A 4-dimension parallel review (security, performance, adversarial test-verification, PR hygiene) of this PR found one real, minor defense-in-depth gap: `execute_run`'s primary call re-checks its `eval_count` against `budget.max_output_tokens` via `check_output_token_budget` (a fallback safety net for a model that ignores `num_predict`) but the reflection call's own `eval_count` was never checked the same way. Fixed by threading `budget` into `_reflect_on_answer` and re-running the same check, fail-open (`outcome="output_budget_exceeded"`) on the reflection call specifically, distinct from the pre-existing `outcome="budget_exceeded"` (total wall-clock). Not a vulnerability on its own (`cost` is always `0.0` in this activation), but closes the same gap the primary path already guards against.

`backend/ecc/domains/ai_runtime/validator.py`: `ExplainItemReflection` (new, `{approved, revised_explanation_text, revised_cited_factor_codes}`, `extra="forbid"`) -- deliberately no word-count validator of its own; a proposed revision is re-validated as a fresh `ExplainItemOutput`, so the 60-word rule keeps exactly one owner.

`backend/ecc/domains/ai_runtime/budgets.py`: `reflection_enabled(policy)` -- reads `routing_policies.constraints.reflection_enabled` (default `False`), the same JSONB column `RunBudget.from_policy` already reads its five budget numbers from.

**Migration.** `backend/migrations/versions/0033_phase4_reflection.py`: an in-place `jsonb || jsonb` merge onto the existing active `attention.explain_item` policy row's `constraints` (seeding `reflection_enabled: false`, following `0032_phase4_second_model.py`'s in-place-update precedent), plus a new, separate `prompt_versions` row (`prompt_id='attention.explain_item.reflect.v1'`, following `0029_phase4_prompt_tool_versions.py`'s seeding pattern). A real bug was found and fixed while authoring this migration: `sa.cast(<python str>, JSONB())` double-encodes the string through the JSONB bind processor, turning an intended object merge into a two-element array (`[original_object, "quoted json string"]`) -- confirmed against a real local Postgres instance, not a hypothetical. Fixed by passing a Python **dict** via `sa.literal(..., type_=JSONB())` instead, so the bind processor's single `json.dumps` produces a real object. Migration verified reversible (`upgrade` -> `downgrade -1` -> `upgrade` clean against a local Postgres instance, including re-verifying the merge/removal produces the exact original `constraints` object back).

**Tests.** `tests/test_ai_runtime_runtime_postgres.py`: 7 tests exercising `execute_run` end-to-end against a mocked transport -- disabled-by-default skips the call; approved keeps the original; a valid+grounded revision replaces the output (asserting the full original answer, not just its cited codes, is preserved on discard); a revision that fails grounding is discarded with the original kept; a schema-invalid reflection response is never repair-retried (proven via an actual HTTP call-count assertion, not just the final step-kind list); a tool-call-shaped reflection response is rejected, never dispatched (reusing Step 1/5's allowlist-injection test pattern); a reflection-layer provider error is skipped, run still completes. Plus 7 tests exercising `_reflect_on_answer` directly (timeout, cancelled, total-wall-clock budget exceeded, output-token budget exceeded, an over-60-word revision failing `ExplainItemOutput` re-validation, `revised_cited_factor_codes=None` falling back to the original codes, `approved=False` with no revision text keeping the original) -- covering fail-open branches impractical to force through a real timing/budget race via the full orchestration path. `tests/test_ai_runtime_validation_postgres.py`: 5 tests for `ExplainItemReflection`'s schema shape, including the explicit "an over-60-word revision validates fine as a Reflection object, only rejected at the `ExplainItemOutput` re-validation step" boundary. `tests/test_ai_runtime_budgets_postgres.py`: 4 tests for `reflection_enabled` (seeded-row read, explicit true/false, defaults false when the key is absent). `tests/test_ai_runtime_evaluation_live_ollama.py`: one smoke test proving the reflection call is genuinely invokable end-to-end against a real Ollama server (not run as part of the promotion-floor check -- see `EVALUATION-CONTRACT.md`'s "Reflection Engine (first slice) and this evaluation's floors" section for why).

These test counts and the token-budget fix above reflect a post-open-PR review pass (4 parallel review agents: security, performance, adversarial test-verification, PR hygiene) -- security, performance, and PR-hygiene dimensions found no issues; the adversarial test-verification pass found two weak assertions (now strengthened, above) and six untested fail-open branches (now covered, above).

**Docs.** `DATA-MODEL.md`, `MODEL-ROUTING-CONTRACT.md`, `API-SCHEMAS.md`, `EVALUATION-CONTRACT.md` updated for the new `constraints` key, `prompt_versions` row, `ai_run_steps` step shape, no-new-routing-decision clarification, and the deliberate reflection-disabled-during-floor-check tradeoff. ### Task 11 evidence -- post-launch audit fixes

A repository-owner-requested full audit of Phase 4 (five parallel passes: contract-doc drift, security/isolation, correctness/robustness, test-coverage gaps, known-issues verification) found one real, high-severity correctness bug and confirmed the rest of the system's prior review cycles held up under a fresh adversarial re-check.

**The bug.** `execute_run`'s bounded schema-repair retry (`runtime.py`'s `reattempt()`, called from inside `validate_with_bounded_repair`) calls `call_model` a second time with no exception handling of its own -- unlike the identical primary call a few lines above, which is fully wrapped for `OllamaCallTimeout`/`OllamaCallCancelled`/`OllamaCallFailed`/`RunBudgetExceeded`. `validate_with_bounded_repair` (`validator.py`) does not add any handling either -- by design, it has no opinion on how the second raw response is produced. Not a contrived edge case: `meeting.prep_summary`'s three largest examples already time out on their *first* attempt against the real model (Task 10's live-CI evidence above), making a timeout on a schema-repair *retry* -- whose prompt is strictly larger than the first attempt's -- a realistic sequence.

**Fix 2 -- `_reflect_on_answer`'s "no active reflection prompt" exit skips its trace step.** This function's only call site already gates on `port.reflection_prompt_id is not None and reflection_enabled(policy)` before calling in, so its own `prompt is None` branch (reached when the specific `prompt_versions` row is missing or inactive -- never seeded, or deactivated after the fact) is a distinct, diagnosable condition from every other skip path in the function, all of which record a `steps` entry. Before this fix it silently returned `validated` with no trace step, indistinguishable from an ordinary no-reflection-configured run. Fixed by recording `_model_step(sequence, "skipped", attempt=0, outcome="prompt_unavailable")` before returning.

**Fix 3 -- output schemas cap word count but not raw character length.** `ExplainItemOutput.explanation_text`'s and `MeetingPrepSummary.summary_text`'s word-count field validators split on whitespace, so a single pathological "word" with no whitespace at all (a huge base64 blob, a repeated-character run) satisfies a <=60/<=150-word count while remaining unbounded in raw size. Fixed with `Field(max_length=...)` on both fields (`_MAX_EXPLANATION_CHARS = 2000`, `_MAX_SUMMARY_CHARS = 5000` -- generously above any legitimate word-capped answer, matching the codebase's existing convention for bounding text fields, e.g. `notes.py`'s `body: str = Field(min_length=1, max_length=100000)`), an independent, defense-in-depth ceiling alongside the existing word-count check, not a replacement for it.

### Task 14 evidence -- post-launch audit fixes, phase C (meeting.prep_summary timeout)

Continuing the phased pickup of Task 11's audit findings. Phase C: `meeting.prep_summary`'s last remaining live-model gap named in that audit -- its three heaviest evaluation examples (`rich_all_sections`, `participants_and_commitments_heavy`, `timeline_heavy`) measuring 20.07-20.2s against the 20s per-model-call budget it shared with `attention.explain_item` (`EVALUATION-CONTRACT.md`'s "Sandbox constraint" section). Repository owner's explicit direction (asked before starting, since this is a Decision 5 budget/contract change, not a small robustness fix): raise `meeting.prep_summary`'s own timeout rather than trim the evaluation fixture or leave the gap undocumented.

**A deeper wiring gap found while implementing the requested fix.** Simply raising `router.py:TASK_REQUIREMENTS["meeting.prep_summary"].timeout_seconds` would have changed `budgets.py:RunBudget.per_model_call_seconds`'s *value* but not real enforced behavior: `ollama_client.py:OllamaAdapter.generate()` enforced its per-model-call deadline entirely from `self._timeout_seconds`, set once at construction and never overridable per call. The real production adapter, `runtime.py:get_ollama_adapter`'s single FastAPI-DI instance, is constructed once (`OllamaAdapter()`, no arguments) and shared across every task type, so it always enforced `DEFAULT_PER_MODEL_CALL_TIMEOUT_SECONDS` (20.0s, a fixed module constant) regardless of which task's budget said otherwise -- confirmed by (and previously masked by) an existing test, `test_run_budget_per_model_call_seconds_matches_ollama_adapter_default_timeout`, which only ever checked `attention.explain_item`, whose value happens to equal that constant. `RunBudget.per_model_call_seconds` was real, correctly computed data with no actual consumer.

**The fix, two parts.**
1. `ollama_client.py:OllamaAdapter.generate()` gained an optional `timeout_seconds` parameter overriding the instance's own default for that call only. The underlying `httpx` client's own request timeout (bounding a single hung network read) was decoupled from any one task's budget entirely -- moved to a new fixed `_HTTPX_TRANSPORT_TIMEOUT_SECONDS = 60.0` constant (Decision 5's own total per-run wall-clock ceiling: no single per-model-call timeout should ever legitimately need to exceed a run's entire budget) -- so a per-call deadline override longer than the old 20s default can't be silently cut short by the transport layer's own separate, smaller timeout. `runtime.py:execute_run`'s `call_model` closure now passes `timeout_seconds=budget.per_model_call_seconds`, so the shared adapter instance genuinely enforces each task's own declared value.
2. `router.py:TASK_REQUIREMENTS["meeting.prep_summary"].timeout_seconds` raised from 20.0 to 25.0 -- real margin over the observed ~20.1-20.2s near-miss (not a few-hundred-millisecond clearance), while two calls at 25s (a primary attempt plus one schema-repair retry, this task's own realistic worst case per Task 11's audit) still fit within the 60s total per-run wall-clock budget alongside routing/tool-dispatch/validation overhead. Migration `0036_phase4_meeting_prep_timeout.py` updates the seeded `routing_policies.constraints.per_model_call_timeout_seconds` row to match (an in-place `jsonb || jsonb` merge, `0033_phase4_reflection.py`'s exact precedent), so it does not read as a stale, silently-diverged number -- `TASK_REQUIREMENTS` remains the actual source of truth at runtime (`RunBudget.from_policy` prefers it, same precedent `max_output_tokens` already established), migration verified reversible (`upgrade` -> `downgrade -1` -> `upgrade` clean against a local Postgres instance).

**Tests.** `tests/test_ai_runtime_budgets_postgres.py`: three tests directly against `generate()`'s new override (a fake-clock deadline past the constructor default but not the override does not raise; past the override itself does raise; no override falls back to the constructor default unchanged) plus one confirming `meeting.prep_summary`'s `RunBudget.per_model_call_seconds` (25.0) now genuinely diverges from `attention.explain_item`'s (still 20.0, matching the adapter default). `tests/test_ai_runtime_runtime_postgres.py`: a `_TimeoutSpyAdapter` wrapper recording every `timeout_seconds` `execute_run` actually passes to `generate()`, proving `meeting.prep_summary` gets `25.0` and `attention.explain_item` still gets `20.0` end to end through real `execute_run` calls -- the other half of the fix the isolated `generate()`-level tests alone don't prove (that `execute_run` actually supplies the value, not just that the mechanism works).
