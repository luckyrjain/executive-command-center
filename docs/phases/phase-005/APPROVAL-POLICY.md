# Automation Approval Policy

Authority is least-privilege, explicit, time-bound and revocable. A policy identifies workflow/version, action types, connector targets, data classes, value/count/rate limits, schedule, approval mode and expiry (`DATA-MODEL.md`'s `automation_policies`).

Modes are `preview_only|per_run|bounded_recurring`.

**`preview_only` is mechanically incapable of producing a real side effect (implemented, not aspirational).** A step running under a `preview_only` policy is still gated for approval exactly like `per_run` -- a real, digest-bound `approval_requests` row is created, the run really pauses in `waiting_approval`, and a human can really approve or reject it, which is the point of the mode (an operator rehearses the full authority flow with nothing at stake). But an *approved* `preview_only` step still never reaches its adapter's `execute()`: `ecc.domains.automation.worker._evaluate_dispatch_gate` returns a distinct blocked outcome (`StepBlockedByPreviewOnlyPolicy`) on its single "cleared to dispatch" exit whenever the resolved policy's `approval_mode` is `preview_only`, regardless of approval state, and `process_claimed_run` terminates the run in the `preview_blocked` run status (`DATA-MODEL.md`) instead of dispatching. `preview_blocked` is deliberately **not** `needs_review` and not `failed`: nothing is broken, nothing is ambiguous, and no operator action exists that would let the run proceed -- switching the workflow's policy to `per_run`/`bounded_recurring` and starting a new run is the only way forward. **This was a real docs-vs-code gap, corrected:** this document and `docs/runbooks/PHASE-5-DOGFOOD.md` described the guarantee from the start, but the original implementation treated `preview_only` as identical to `per_run` in every respect, so an approved `preview_only` step really did execute for real. See `approvals.py`'s own module docstring for both readings and why the stricter one is the one the documents promise.

**High-impact action taxonomy** (`docs/superpowers/specs/2026-07-25-phase-5-automation-design.md` Decision 5), a closed enumeration -- always requires per-run approval regardless of policy mode:

| Category | Definition |
|---|---|
| `destructive` | Irreversible mutation (adapter declares `reversible=false`) |
| `financial` | Payment, invoicing or monetary transfer |
| `legal` | Contract, compliance or regulatory-filing action |
| `credential` | Creates, rotates or reveals a credential/secret |
| `person-directed` | Sends a message/notification visible to a human other than the workspace owner |
| `public` | Creates content visible outside the workspace owner's private systems |
| `policy-limit-exceeding` | The specific run's value/count/rate would exceed the authorizing policy's own configured limit, regardless of the action's own category |

Each action adapter statically declares its `high_impact_categories` at registration time, checked before any execution attempt. **A rollback (`step_type='compensation'`) step is the one place this per-run-approval requirement cannot be satisfied at dispatch time**, because compensation runs as an automatic continuation of a failing run and has no approval-inbox surface to wait in; the requirement is upheld there by forbidding the situation entirely -- a compensation step whose `action_ref` names an adapter with any declared `high_impact_categories` is rejected at publish time (`EXECUTION-CONTRACT.md`, `422 COMPENSATION_ACTION_REF_HIGH_IMPACT`), so no high-impact action can ever execute as a rollback. **An adapter that cannot classify itself into any category still defaults to requiring per-run approval** -- `bounded` (eligible for `bounded_recurring` mode, no per-run prompt) is a category an adapter must explicitly and correctly claim; there is no "none of the above, therefore bounded" default (fail closed, matching Phase 4's conservative data-class default precedent).

## Expiry and rate limits (resolved)

| Control | Value | Behavior on limit |
|---|---|---|
| Policy expiry | 90 days from creation/last renewal (default); renewal prompt at 7 days remaining | Expired policy blocks future runs; an already in-flight run continues to its next checkpoint rather than hard-aborting. |
| Per-run approval-request expiry | 24 hours unresponded | Auto-expires to `expired`; never implicitly approved. |
| Runs per workflow per hour | 10 (policy default, overridable per policy) | Next run past the limit rejected at enqueue with `rate_limited`. **Enforced** (`worker.enqueue_run`, the single choke point both `POST /automations/runs` and the schedule-trigger fire path go through): the count is `workflow_runs` rows for this `(workspace_id, workflow_id)` whose `queued_at` falls inside the trailing hour, of any status, and the rejection happens before any row is written. |
| Monetary value / action count per policy per day | No system-wide default -- required, non-nullable per-policy field | No connector in this activation has monetary side effects; the field exists for schema stability and forces an explicit author choice rather than an arbitrary inherited default. `count_limit` is enforced per run (`policy-limit-exceeding`); `value_limit` is **not** enforced -- see the accepted limitation below. |

## Accepted limitation: `action_types`, `data_classes` and `value_limit` are stored but not enforced

Disclosed explicitly, in the same style `docs/phases/phase-005/IMPLEMENTATION-STATUS.md` uses for this phase's other accepted limitations, because earlier revisions of this document read as though all four scope fields were live controls:

- `action_types`, `data_classes` and `value_limit` are persisted (`automation_policies`), validated for shape, and returned by `GET /automations/policies`. **Nothing in the dispatch path compares any of them against a dispatching adapter.** Concretely: a policy scoped to specific `action_types` or `data_classes` currently authorizes **any** registered adapter regardless of that adapter's actual action type or data classification, and a `value_limit` of any size constrains nothing.
- The reason is a missing model, not an oversight. Enforcement requires per-adapter metadata mapping an adapter identity to its action type and the data classes it touches (and, for `value_limit`, a monetary amount per dispatch); `adapters.ActionAdapter` (design doc Decision 8) declares `adapter_id`, `input_schema`/`output_schema`, `reversible` and `high_impact_categories` and nothing else. Adding it means extending the adapter protocol, backfilling every registered adapter, deciding the fail-closed default for an adapter that declines to classify itself, and threading it through both the dispatch gate and `/simulate`. That is its own design change, intentionally not folded into a docs-vs-code reconciliation.
- What holds meanwhile, and does not depend on adapter metadata: `high_impact_categories` (declared by every adapter) always forces per-run approval; `approval_mode` gates every step and, under `preview_only`, blocks dispatch entirely; `expires_at`/`revoked_at` bound authority in time; `count_limit` bounds actions per run; `rate_limit` bounds runs per hour. The gap is "a policy does not narrow *which kinds* of registered adapter it authorizes," not "a policy authorizes unattended execution."
- `schedule` on this table is likewise descriptive: schedule *authority* is evaluated from the `triggers` row's own `schedule_expression`/`timezone` (`DATA-MODEL.md`), never from this column.

Approval displays exact target, payload summary, risk category and expiry. **Reversible status is *not* displayed at the approval surface -- corrected, previously claimed here as though it were.** `ApprovalResponse` (`approvals.py`) carries `run_id`, `step_index`, `action_digest`, `high_impact_categories`, `status`, `requested_at`/`expires_at` and the decision fields, and no field for the step adapter's declared `reversible` flag; neither does `RunStepResponse`. The only endpoint that returns `reversible` at all is `POST /automations/workflows/{id}/simulate`, addressed by a workflow *version* UUID a `workflow_runs` row does not carry. `ApprovalInbox.tsx`'s `ApprovalCard` therefore states the gap to the approver in-component rather than omitting the field silently or guessing a value (`UX-STATES.md`'s own matching disclosure has the full note and names threading `reversible` through to `ApprovalResponse` as the follow-up). Related, and worth stating in the same breath rather than assumed: the `destructive` row above *defines* itself as "adapter declares `reversible=false`," but `AdapterRegistry.register` does not enforce that linkage -- it validates that every declared category is a known one, and never that an adapter with `reversible=False` also declares `destructive`. So an irreversible adapter that omits `destructive` from its own `high_impact_categories` is registered without complaint and, under `bounded_recurring`, dispatches within `count_limit` without a per-run prompt. No adapter registered in this activation is in that position (`local.create_note` and `fake.external_action` are both `reversible=True`; `local.send_test_notification` is `reversible=False` and does declare a category, `person-directed`), but the invariant rests on adapter-author discipline, not on a check. **Material changes invalidate approval**: an approval is bound to the exact `action_digest` (`EXECUTION-CONTRACT.md`) it was granted against -- any change to the step's resolved input, the workflow version, or the policy in force produces a new digest, and the prior approval does not carry forward to it (the mechanical enforcement of "unauthorized, expired, changed or replayed approvals are rejected").

**Revocation** takes effect immediately for any not-yet-started step (matches the phase NFR verbatim); an in-flight step already dispatched completes or reaches its next durability checkpoint before the run halts. This covers **compensation steps too**: a rollback step is not-yet-started until its adapter is actually invoked, so the worker re-reads the authorizing policy immediately before that call and blocks the compensation (`error_class='PolicyUnusableDuringCompensation'`, run ends `compensation_failed`) if the policy has since been revoked or expired -- revocation is never bypassed by a run that happens to be rolling back rather than progressing.
