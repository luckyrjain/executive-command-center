### Task 1 evidence -- workflow schema, policy model and triggers (data layer only, this commit)

**Migration.** `backend/migrations/versions/0038_phase5_workflow_schema.py` -- the true next-in-chain after `0037_phase4_meeting_timeout2.py`, per this codebase's own documented migration-numbering convention (migration `0029`'s own docstring precedent). Creates four tables, all workspace-scoped (a deliberate divergence from Phase 4's global `prompt_versions`/`tool_definitions`, matching every Phase 1-3 domain table's convention instead -- see the migration's own module docstring for the full reasoning):

- `workflow_definitions` -- the workflow-family identity row (`id`, `workspace_id`, `workflow_id`, `created_by`, timestamps), `UNIQUE(workspace_id, workflow_id)`. A second table beyond the single-table shape Phase 4's `prompt_versions` used, added specifically so `automation_policies`/`triggers` have a stable FK target for "which workflow family" independent of any one version row's lifecycle.
- `workflow_versions` -- `workflow_id`, `version`, `graph` (JSONB), `trigger_refs` (JSONB), `policy_ref` (nullable UUID, no FK -- see migration docstring), `definition_hash` (`sha256` over `{graph, trigger_refs, policy_ref}`), `status` (`draft|active|retired`). `trg_workflow_versions_immutability` (`BEFORE UPDATE`) rejects any change to `graph`/`trigger_refs`/`policy_ref`/`definition_hash` once `status <> 'draft'`, mirroring migration `0029`'s `trg_prompt_versions_immutability` exactly in style. `uq_workflow_versions_active_per_workflow` (partial unique index, `WHERE status = 'active'`) enforces exactly one active version per `(workspace_id, workflow_id)`.
- `automation_policies` -- `workflow_id`, `action_types`/`data_classes` (`ARRAY(TEXT)`), `value_limit`/`count_limit` (both `NOT NULL`, no `server_default` -- `APPROVAL-POLICY.md`'s resolved decision that a policy author must set both explicitly), `rate_limit` (JSONB, defaults to `{"runs_per_workflow_per_hour": 10}` -- the one limit this doc *does* give a system-wide default), `schedule`, `approval_mode` (`preview_only|per_run|bounded_recurring`), `expires_at` (computed in application code as `created_at + 90 days`, never a DB default), `revoked_at`, `version` (optimistic-concurrency column, Phase 3's established idiom).
- `triggers` -- `workflow_id`, `trigger_type` (`manual|event|schedule`), `event_type_filter`, `schedule_expression`, `timezone`, `skip_missed`. Two `CHECK` constraints enforce design doc Decision 7's "a schedule trigger always names its own timezone explicitly" and "an event trigger always names its filter" at the database layer, not only in application code.

Verified against a live PostgreSQL 16 instance: `alembic upgrade head` applies cleanly, `alembic downgrade -1` then `alembic upgrade head` again reproduces an identical schema (migration is cleanly reversible).

**Application code.** `backend/ecc/domains/automation/` (new package): `workflows.py` (`compute_definition_hash`, `validate_graph_shape`, `create_workflow_draft`, `activate_workflow_version`, `disable_workflow_version`, read helpers, and the HTTP router), `policy.py` (`create_policy`, `revoke_policy`, `policy_status`/`is_policy_usable` -- the expiry-check helper -- and the HTTP router), `triggers.py` (`create_trigger`/`get_trigger`/`list_triggers`, no `APIRouter` of its own -- `API-SCHEMAS.md` names no trigger endpoint in this task's scope, mirroring `ai_runtime.tools`'s router-less shape exactly). `activate_workflow_version`/`disable_workflow_version` only ever write `status`/`updated_at`, so neither function can structurally collide with the immutability trigger; `publish`'s endpoint additionally catches `IntegrityError` around the activation call and converts it to a clean `WORKFLOW_VERSION_ACTIVE_CONFLICT` 409 rather than propagating a raw Postgres exception, per this task's own instruction. Wired into `backend/ecc/main.py` alongside the existing Phase 1-4 routers.

**API surface (Task 1 scope only).** `GET|POST /api/v1/automations/workflows`, `GET /api/v1/automations/workflows/{id}`, `POST /api/v1/automations/workflows/{id}/publish|disable`, `GET|POST /api/v1/automations/policies`, `POST /api/v1/automations/policies/{id}/revoke`. No `/simulate`, `/runs` or `/approvals` endpoint -- those need the durable worker/action-adapter machinery a later task builds; none was stubbed (no dead code). Every mutating endpoint requires `AuthDep`/`CsrfDep` plus an `Idempotency-Key`; every endpoint resolves `workspace_id` server-side from the caller's session, never from a request body or path parameter (confused-deputy protection, matching Phase 4's own precedent the design doc's Threat model section cites). Required error codes from `API-SCHEMAS.md` all exercised within this task's real endpoints: `SCHEMA_INVALID` (`POST /workflows`, a structurally invalid graph -- duplicate `step_id`s, an edge referencing an unknown or non-forward step, a missing `action_ref` on an `action`/`compensation` step), `WORKFLOW_NOT_ACTIVE` (`POST /workflows/{id}/disable` against a non-active version), `POLICY_EXPIRED`/`POLICY_REVOKED` (`POST /policies/{id}/revoke` against an already-expired or already-revoked policy).

**Tests.** `tests/test_automation_workflows_postgres.py` (37 tests), `tests/test_automation_policy_postgres.py` (21 tests), `tests/test_automation_triggers_postgres.py` (8 tests) -- 66 tests in total (`test_retired_row_every_hashed_column_rejected` is parametrized x3, `trigger_refs`/`policy_ref`/`definition_hash`). Covers, per this task's own required minimum: the DB-level immutability trigger rejecting a post-activation content edit via **direct SQL**, bypassing `workflows.py` entirely (mirroring `test_ai_runtime_versioning_postgres.py`'s identical structure for Phase 4's analogous property); the partial unique index rejecting a second `active` row via direct `INSERT`; draft creation and version increment (`create_workflow_draft`); activation both via the application path (`activate_workflow_version`, exactly-one-active enforced by locking) and the endpoint (`publish`); cross-workspace isolation for workflows, policies and triggers (a resource from workspace A is a 404, never a 403 or a visible-but-empty row, from workspace B -- `GET`, `list`, `publish`, `revoke` all independently verified); policy expiry/revocation state transitions (`policy_status`, `revoke_policy`'s four possible outcomes); the DB-level `NOT NULL` backstop on `value_limit`/`count_limit` (direct `INSERT` omitting either fails with `IntegrityError`) and the HTTP-layer equivalent (`POST /policies` omitting either is `422`); the `triggers` table's two `CHECK` constraints (a `schedule` trigger without `schedule_expression`/`timezone`, or an `event` trigger without `event_type_filter`, both rejected with `IntegrityError`).

**Judgment calls a reviewer should double-check.** (1) `workflow_definitions` as a second table, diverging from Phase 4's single-table `prompt_versions` shape -- justified in the migration's own docstring by `automation_policies`/`triggers` needing a stable FK target `workflow_versions` alone cannot provide. (2) `workflow_versions.policy_ref` carries no FK constraint (an opaque UUID, validated at the application layer against the caller's own workspace) -- avoids an artificial table-creation-order constraint; a workflow can be drafted before or after its intended policy. (3) `POST /automations/workflows` serves both "create a new workflow" and "add a new version to an existing one" through one endpoint, since `API-SCHEMAS.md`'s Task-1-scoped surface names no separate "add version" route. (4) `publish`/`disable` address a specific `workflow_versions` row by its own UUID (not by `(workflow_id, version)`), matching how Phase 4's `GET /ai/runs/{id}` addresses a single run. (5) `POST /policies/{id}/revoke` rejects (rather than silently no-ops) revoking an already-revoked or already-expired policy, on the reasoning that both are terminal states a second `revoke` call cannot meaningfully act on further, and the required `POLICY_REVOKED`/`POLICY_EXPIRED` error codes need a real call site to be exercised within this task's scope.

RETURNING *`, preceded only by a plain unlocked candidate `SELECT` -- no `FOR UPDATE`, per this task's own instruction -- generalized to reclaim `status IN ('leased', 'running')` with an expired lease, not `'leased'` alone; see the "Correction from the design-time draft" section this commit adds to `docs/runbooks/PHASE-5-RECOVERY.md` for why); `renew_lease` (the heartbeat, an independently callable/testable function, called once per step by `process_claimed_run` -- "called between steps at minimum," the documented minimum shape this task's own instructions allow); `run_step` (idempotency-gated dispatch: `action_digest` computed and durably **committed** -- not merely `flush()`-ed -- to the database before `execute()` is ever called; a `succeeded` digest is never re-dispatched; a `dispatched`-with-no-outcome digest -- the crash-in-the-gap case -- is marked `unknown` without calling `execute()`; only `step_type == "action"` is dispatched, `UnsupportedStepType` otherwise, since approval-gate/condition dispatch is out of this task's scope); `process_claimed_run` (the sequential per-run driving loop, heartbeats before each step, checks `cancel_requested_at` before each not-yet-dispatched step); `cancel_run` (immediate for a `queued` run, a flag a claimed run's own loop observes before its next step otherwise); `_redact_payload` (a real transform, not a comment -- strips any `secret`/`password`/`token`/`credential`/`api_key`/`authorization`-shaped key's value before either `input` or `output` is ever written, recursively over nested dicts/lists).

**No HTTP surface** -- matches `triggers.py`'s own router-less precedent exactly and this task's own explicit scope boundary (`/runs`/`/approvals` need Task 3's approval-gate logic and a later task's real adapters to be meaningful, not merely this task's worker). No internal-only trigger endpoint was added either; this task's own tests call `enqueue_run`/`claim_next_run`/`process_claimed_run`/`cancel_run` directly, which was sufficient to exercise every required property without a new router.

**Tests.** `tests/test_automation_worker_postgres.py` -- 25 tests. Covers, per this task's own required minimum: two workers racing the same `workflow_runs` row under real concurrent database connections (`ThreadPoolExecutor`, two independent `SessionFactory` sessions, not mocked) -- exactly one claims it; crash recovery for a run stuck in `leased` with an expired lease, and separately (the stronger case) a run stuck in `running` mid-graph with one step already `succeeded`, reclaimed and resumed from `current_step_index`, never re-dispatching the already-succeeded step; at-most-one-effect (`run_step` called twice for the same step index, the fake adapter's `execute_calls` stays at 1); the unknown-outcome case (a `dispatched` row with a real persisted digest and no recorded outcome, inserted directly to simulate the exact crash timing) surfaces as `unknown`/`needs_review` without ever calling `execute()`; cancellation blocking a not-yet-dispatched step while leaving an already-succeeded one alone; the full enqueue-claim-run-every-step-succeeded path across a 3-step graph; an adapter's `RuntimeError` marking the step `failed` and the run `failed` (`error_class` recorded); workspace isolation (`get_run`/`list_run_steps`/`cancel_run` from workspace B against workspace A's run all fail closed, `cancel_run` returning `WorkflowRunNotFound`); redaction of secret-shaped keys in both stored `input` and `output` (including a unit test of `_redact_payload` over nested structures); `renew_lease` as an independently callable function (updates `leased_until`/`lease_heartbeat_at`, returns `None` for the wrong `worker_id`); `compute_action_digest`'s payload-substitution property (changing `resolved_input` or `workflow_version` changes the digest, same inputs reproduce the same digest); `AdapterRegistry`'s own registration-time validation; `DigestVisibilityProbeAdapter` (a real crash-durability proof, not an absence-of-exception check -- see the "Real bug found and fixed during review" note below).

**Real bug found and fixed during review: `run_step`'s digest write was `flush()`-ed, not committed.** `run_step` originally called `session.flush()` (not `session.commit()`) after inserting the `'dispatched'`+`action_digest` row, and every other write in this module (`claim_next_run`'s lease claim, `_mark_running`/`_finish_run`'s state transitions, every outcome `UPDATE` in `run_step`) was left to whatever transaction the caller's own `with session.begin():` block happened to commit. Since `process_claimed_run` runs an entire multi-step graph inside one such caller-managed transaction, `flush()` alone meant none of it was actually durable until the *whole run* finished and the outer transaction committed -- a real process crash at any point mid-run (including, worst case, right after a real adapter's `execute()` call had a genuine external side effect) would roll back everything, including the claim itself, leaving the run looking exactly like it was never touched. A subsequent worker would then legitimately re-claim and re-execute it from scratch: a real duplicate side effect, the exact failure Decision 3's digest-before-execute guarantee and `EXECUTION-CONTRACT.md`'s "at most one effect under crash/retry" exist to prevent. Confirmed by direct experiment: reverting the fix's one `commit()` back to `flush()` makes `test_dispatched_digest_is_durably_committed_before_execute_is_called` fail (its `DigestVisibilityProbeAdapter` opens an independent connection inside `execute()` and finds the 'dispatched' row genuinely invisible, since an uncommitted write in one transaction is not visible to another under this database's default READ COMMITTED isolation); restoring the fix makes it pass again. **Fix:** every durability-critical write in `worker.py` (`claim_next_run`, `renew_lease`, `_mark_running`, `_finish_run`, and all five outcome-writing branches inside `run_step`) now calls `session.commit()` directly on a bare session, matching `ecc.domains.ai_runtime.runtime._persist_terminal`'s own established precedent for the identical problem (a long-running operation that must durably checkpoint before a risky external call, called from both fresh and already-open sessions). This required updating every test call site that invoked one of these functions from inside a `with session.begin():` block to a bare `with SessionFactory() as session:` instead (`session.commit()` called from inside a caller-held `.begin()` context raises `InvalidRequestError` -- confirmed directly), and adding `test_dispatched_digest_is_durably_committed_before_execute_is_called` (`DigestVisibilityProbeAdapter`) as the one test that proves the property directly rather than merely by absence of an exception, since none of Task 2's original tests would have caught this: they only ever exercised the "already dispatched" recovery path via a hand-constructed row inserted through a separate, genuinely-committed connection, never by observing `run_step`'s own internal write actually become durable.

**Cross-check against `docs/runbooks/PHASE-5-RECOVERY.md`'s specific claims.** 30s lease + 2s poll interval + heartbeat every step (at least every 10s) matches the runbook's numbers exactly (`worker.py`'s `LEASE_DURATION_SECONDS`/`POLL_INTERVAL_SECONDS`/`HEARTBEAT_INTERVAL_SECONDS` = `30`/`2`/`10`, unchanged from Decision 3). The one real divergence -- the reclaim predicate needing to cover `running`, not `leased` alone, for the recovery guarantee to hold for a crash mid-run rather than only a crash immediately post-claim -- is corrected in the runbook itself (this commit), not silently papered over; the 90-second manual-confirmation diagnostic query in that runbook is updated to match (`status IN ('leased', 'running')`). No other number or mechanic diverged between the design-time document and this implementation.

**Judgment calls a reviewer should double-check.** (1) **The claim predicate's `leased`-vs-`running` generalization** (above) -- the single most load-bearing deviation from Decision 3's literal SQL text in this task; flagged in three places (`worker.py`'s own docstring, this evidence section, `PHASE-5-RECOVERY.md`'s new correction section) rather than left implicit. (2) **Heartbeat shape** -- `renew_lease` is called once per step by `process_claimed_run` (the "called between steps at minimum" option this task's own instructions explicitly allowed), not a background thread; sufficient for this task's fast in-process fake adapters, and reusable as-is by a later task's slow real adapters wrapping one `execute()` call in a timer that calls this same function every 10s while that call is in flight. (3) **Adapter failure produces `failed`, not `needs_review`** -- an adapter's own raised exception is a definitively-classified failure (the process is still alive to observe and record it), distinct from the crash-interrupted case (`unknown`/`needs_review`), where the process died before any outcome could be recorded at all; this task treats only the latter as ambiguous. (4) **No internal-only HTTP endpoint was added** -- this task's own tests call the worker's functions directly, which proved sufficient; a reviewer who wants a browser-observable proof of this task's behavior before Task 3/5 land would need to add one, deliberately not done here per this task's own default. (5) **`resolved_input` is the step's static `input_mapping` dict as-is** -- this task does not implement `input_mapping`'s `$trigger.*`/prior-step-output templating (that materialization is `runtime.py`'s concern, the design doc's Architecture impact section lists it as a separate module from `worker.py`); sufficient to prove the digest/idempotency/lease mechanics this task must prove, but a later task's real orchestration loop will need to resolve `input_mapping` before calling `run_step`, not after.
