### Task 1 evidence -- workflow schema, policy model and triggers (data layer only, this commit)

**Migration.** `backend/migrations/versions/0038_phase5_workflow_schema.py` -- the true next-in-chain after `0037_phase4_meeting_timeout2.py`, per this codebase's own documented migration-numbering convention (migration `0029`'s own docstring precedent). Creates four tables, all workspace-scoped (a deliberate divergence from Phase 4's global `prompt_versions`/`tool_definitions`, matching every Phase 1-3 domain table's convention instead -- see the migration's own module docstring for the full reasoning):

- `workflow_definitions` -- the workflow-family identity row (`id`, `workspace_id`, `workflow_id`, `created_by`, timestamps), `UNIQUE(workspace_id, workflow_id)`. A second table beyond the single-table shape Phase 4's `prompt_versions` used, added specifically so `automation_policies`/`triggers` have a stable FK target for "which workflow family" independent of any one version row's lifecycle.
- `workflow_versions` -- `workflow_id`, `version`, `graph` (JSONB), `trigger_refs` (JSONB), `policy_ref` (nullable UUID, no FK -- see migration docstring), `definition_hash` (`sha256` over `{graph, trigger_refs, policy_ref}`), `status` (`draft|active|retired`). `trg_workflow_versions_immutability` (`BEFORE UPDATE`) rejects any change to `graph`/`trigger_refs`/`policy_ref`/`definition_hash` once `status <> 'draft'`, mirroring migration `0029`'s `trg_prompt_versions_immutability` exactly in style. `uq_workflow_versions_active_per_workflow` (partial unique index, `WHERE status = 'active'`) enforces exactly one active version per `(workspace_id, workflow_id)`.

Two `CHECK` constraints enforce design doc Decision 7's "a schedule trigger always names its own timezone explicitly" and "an event trigger always names its filter" at the database layer, not only in application code.

Verified against a live PostgreSQL 16 instance: `alembic upgrade head` applies cleanly, `alembic downgrade -1` then `alembic upgrade head` again reproduces an identical schema (migration is cleanly reversible).

**Real bug found and fixed during review: `run_step`'s digest write was `flush()`-ed, not committed.** `run_step` originally called `session.flush()` (not `session.commit()`) after inserting the `'dispatched'`+`action_digest` row, and every other write in this module (`claim_next_run`'s lease claim, `_mark_running`/`_finish_run`'s state transitions, every outcome `UPDATE` in `run_step`) was left to whatever transaction the caller's own `with session.begin():` block happened to commit. Since `process_claimed_run` runs an entire multi-step graph inside one such caller-managed transaction, `flush()` alone meant none of it was actually durable until the *whole run* finished and the outer transaction committed -- a real process crash at any point mid-run (including, worst case, right after a real adapter's `execute()` call had a genuine external side effect) would roll back everything, including the claim itself, leaving the run looking exactly like it was never touched. A subsequent worker would then legitimately re-claim and re-execute it from scratch: a real duplicate side effect, the exact failure Decision 3's digest-before-execute guarantee and `EXECUTION-CONTRACT.md`'s "at most one effect under crash/retry" exist to prevent. Confirmed by direct experiment: reverting the fix's one `commit()` back to `flush()` makes `test_dispatched_digest_is_durably_committed_before_execute_is_called` fail (its `DigestVisibilityProbeAdapter` opens an independent connection inside `execute()` and finds the 'dispatched' row genuinely invisible, since an uncommitted write in one transaction is not visible to another under this database's default READ COMMITTED isolation); restoring the fix makes it pass again. **Fix:** every durability-critical write in `worker.py` (`claim_next_run`, `renew_lease`, `_mark_running`, `_finish_run`, and all five outcome-writing branches inside `run_step`) now calls `session.commit()` directly on a bare session, matching `ecc.domains.ai_runtime.runtime._persist_terminal`'s own established precedent for the identical problem (a long-running operation that must durably checkpoint before a risky external call, called from both fresh and already-open sessions). This required updating every test call site that invoked one of these functions from inside a `with session.begin():` block to a bare `with SessionFactory() as session:` instead (`session.commit()` called from inside a caller-held `.begin()` context raises `InvalidRequestError` -- confirmed directly), and adding `test_dispatched_digest_is_durably_committed_before_execute_is_called` (`DigestVisibilityProbeAdapter`) as the one test that proves the property directly rather than merely by absence of an exception, since none of Task 2's original tests would have caught this: they only ever exercised the "already dispatched" recovery path via a hand-constructed row inserted through a separate, genuinely-committed connection, never by observing `run_step`'s own internal write actually become durable.

**Cross-check against `docs/runbooks/PHASE-5-RECOVERY.md`'s specific claims.** 30s lease + 2s poll interval + heartbeat every step (at least every 10s) matches the runbook's numbers exactly (`worker.py`'s `LEASE_DURATION_SECONDS`/`POLL_INTERVAL_SECONDS`/`HEARTBEAT_INTERVAL_SECONDS` = `30`/`2`/`10`, unchanged from Decision 3). The one real divergence -- the reclaim predicate needing to cover `running`, not `leased` alone, for the recovery guarantee to hold for a crash mid-run rather than only a crash immediately post-claim -- is corrected in the runbook itself (this commit), not silently papered over; the 90-second manual-confirmation diagnostic query in that runbook is updated to match (`status IN ('leased', 'running')`). No other number or mechanic diverged between the design-time document and this implementation.

**Judgment calls a reviewer should double-check.** (1) **The claim predicate's `leased`-vs-`running` generalization** (above) -- the single most load-bearing deviation from Decision 3's literal SQL text in this task; flagged in three places (`worker.py`'s own docstring, this evidence section, `PHASE-5-RECOVERY.md`'s new correction section) rather than left implicit. (2) **Heartbeat shape** -- `renew_lease` is called once per step by `process_claimed_run` (the "called between steps at minimum" option this task's own instructions explicitly allowed), not a background thread; sufficient for this task's fast in-process fake adapters, and reusable as-is by a later task's slow real adapters wrapping one `execute()` call in a timer that calls this same function every 10s while that call is in flight. (3) **Adapter failure produces `failed`, not `needs_review`** -- an adapter's own raised exception is a definitively-classified failure (the process is still alive to observe and record it), distinct from the crash-interrupted case (`unknown`/`needs_review`), where the process died before any outcome could be recorded at all; this task treats only the latter as ambiguous. (4) **No internal-only HTTP endpoint was added** -- this task's own tests call the worker's functions directly, which proved sufficient; a reviewer who wants a browser-observable proof of this task's behavior before Task 3/5 land would need to add one, deliberately not done here per this task's own default. (5) **`resolved_input` is the step's static `input_mapping` dict as-is** -- this task does not implement `input_mapping`'s `$trigger.*`/prior-step-output templating (that materialization is `runtime.py`'s concern, the design doc's Architecture impact section lists it as a separate module from `worker.py`); sufficient to prove the digest/idempotency/lease mechanics this task must prove, but a later task's real orchestration loop will need to resolve `input_mapping` before calling `run_step`, not after.

### Task 3 evidence -- approval inbox and policy-driven revocation enforcement

**Migration.** `backend/migrations/versions/0040_phase5_approval_requests.py` -- the true next-in-chain after `0039_phase5_workflow_runs.py`. Creates `approval_requests`: `(workspace_id, run_id)` composite-FK'd to `workflow_runs(workspace_id, id)` with `ondelete="CASCADE"` (identical shape to `workflow_run_steps`'s own FK); `step_index`; `action_digest` (`String(64)`, the exact digest this request authorizes); `high_impact_categories` (`ARRAY(TEXT)`, matching `automation_policies.action_types`'s own array convention); `status` restricted to three values (`pending|approved|rejected`), **not** four -- `expires_at`-driven expiry is computed live (`approvals.approval_lifecycle_status`), never written back to the row, mirroring `automation_policies`' own "no stored lifecycle column, a pure function derives the label" convention exactly (the migration's own docstring spells out the transactional problem this sidesteps: a lazy `expired` write from inside a router's `with session.begin():` block would be rolled back by the very `HTTPException` an expired decision raises). Two `CHECK` constraints enforce `status`/`decision`/`decided_at`/`decided_by` consistency at the database layer (a `pending` row has all three `NULL`; a decided row has all three set, `decision` matching `status`). `(workspace_id, decided_by)` composite-FK's to `users`, nullable -- Postgres's `MATCH SIMPLE` semantics skip enforcement entirely while `decided_by IS NULL` (a `pending` row), matching every other actor-reference FK in this codebase for every row that has actually been decided. A partial unique index (`uq_approval_requests_pending_per_run_step`, `WHERE status = 'pending'`) enforces at most one open request per `(run_id, step_index)` at the database layer, not only by `create_approval_request`'s own check-then-insert discipline. **Application code -- `backend/ecc/domains/automation/approvals.py`** (new module). `evaluate_approval_requirement(adapter, policy, *, action_step_count_so_far)` -- pure, no session: any non-empty `high_impact_categories` always requires approval regardless of `approval_mode` (Decision 5 verbatim); `preview_only`/`per_run` require approval for every step, including `bounded` ones; `bounded_recurring` requires approval only once `action_step_count_so_far >= policy.count_limit` (`policy-limit-exceeding`, evaluated using `count_limit` only -- `value_limit` has no adapter-declared monetary field in this activation and `rate_limit` is an enqueue-time concern per `APPROVAL-POLICY.md`'s own table, out of this task's explicit scope; see the module's own docstring for the full reasoning). `create_approval_request` (caller-committed, `expires_at = requested_at + 24h` computed in application code, matching `policy.create_policy`'s identical precedent). `decide_approval` -- the five-outcome function (`ApprovalRequest | ApprovalNotFound | ApprovalDigestMismatch | ApprovalAlreadyDecided | ApprovalExpired`): requires `current_action_digest` to match the stored `action_digest` exactly for an `"approved"` decision (omitted or mismatched is `ApprovalDigestMismatch`, never silently accepted -- not required for `"rejected"`, matching `API-SCHEMAS.md`'s echo requirement naming only `/approve`); folds `_advance_run_after_decision` (a raw-SQL helper, not a call into `worker.py` -- see below) into every decision so every caller, HTTP or direct, gets correct run-advancement without having to remember a second call. `get_pending_approval`/`get_approved_request`/`get_approval`/`list_approvals` -- workspace-scoped reads. HTTP router: `GET /api/v1/automations/approvals` (optional `status` filter), `POST .../{id}/approve` (`action_digest` required in the body), `POST .../{id}/reject` -- `AuthDep`/`CsrfDep`/`Idempotency-Key` on the mutating endpoints, workspace-scoped, following `workflows.py`/`policy.py`'s exact idempotency-lock/audit/outbox pattern (`_lock_idempotency`, `_load_cached`, `_store_idempotency`, `_write_side_effects`), now used identically by four modules in this package.

**Wired into `backend/ecc/domains/automation/worker.py`'s `run_step`.** The gate (`_evaluate_dispatch_gate`, plus the `_count_dispatched_action_steps` helper it uses for `policy-limit-exceeding`) runs in the `else:` branch -- i.e. only when the `SELECT ... FOR UPDATE` existing-row check has confirmed **no** `workflow_run_steps` row exists yet for this step -- and, critically, **before** that branch's `INSERT` of the `'dispatched'` row, not after. This ordering is the single most load-bearing design decision in this task's own wiring (documented at length in `worker.py`'s own module docstring, restated in `run_step`'s docstring, and in `_evaluate_dispatch_gate`'s own): writing `'dispatched'` first, then evaluating the gate, would leave a step paused for approval looking identical -- to any later `run_step` call examining `workflow_run_steps` -- to Task 2's own crash-in-the-gap case (`'dispatched'`, a real digest, no recorded outcome), which Task 2's own existing branch unconditionally marks `unknown`/`needs_review` on sight with no way to distinguish "still legitimately waiting for a human" from "the process that wrote this row is dead." Evaluating the gate before that row exists at all means a paused step leaves **no** `workflow_run_steps` row, so a resumed `run_step` call simply re-evaluates the gate from scratch -- both the crash-recovery-ambiguity risk and the "how does a paused step resume" question are solved by the same one design choice. Two new dispatch outcomes, neither ever written to `workflow_run_steps`: `StepBlockedByPolicy` (`run.policy_id is None`, or `policy.get_policy` finds nothing, or `policy.is_policy_usable` is `False` -- fail-closed, "no policy means no authority," this task's own instruction; `process_claimed_run` maps this to `run.status = 'needs_review'`, reusing Task 2's existing terminal-until-human-action state rather than inventing a fifth run status) and `StepAwaitingApproval` (`evaluate_approval_requirement` said yes and no `approved` row matches the live, freshly-computed digest via `get_approved_request` -- an existing `pending` request is reused, or a fresh one created and durably committed immediately; `process_claimed_run` maps this to `run.status = 'waiting_approval'`).

**Resuming a `waiting_approval` run reuses the existing claim/poll machinery verbatim -- no new reclaim predicate.** `approvals._advance_run_after_decision` (called from inside `decide_approval`, for every caller) flips an approved run's status straight back to `'queued'` (only if the run is still exactly `waiting_approval` at the exact `step_index` the decision applies to -- a decision for a step the run has already moved past for any other reason is a no-op); `claim_next_run`'s ordinary `_CLAIMABLE_PREDICATE` already matches `'queued'`, so the very next poll cycle (any worker's) claims it and `process_claimed_run` resumes at the unchanged `current_step_index`, exactly as any other queued run. A `rejected` decision instead flips the run straight to `'failed'` (a human declined -- nothing left to resume, matching how an adapter's own raised exception also produces `failed`, not `needs_review`). `_advance_run_after_decision` lives in `approvals.py`, not `worker.py`, as a small independent raw-SQL helper -- `worker.py` already imports `approvals.py` (its dispatch gate calls `evaluate_approval_requirement`/`create_approval_request`/`get_pending_approval`/`get_approved_request`), so `approvals.py` cannot import `worker.py` back without a circular import; the SQL needed to flip one `workflow_runs` row's status is small enough not to be worth threading a dependency through in the other direction.

**`preview_only` mode -- a genuine judgment call, resolved and documented, not left ambiguous.** `APPROVAL-POLICY.md` names the mode but does not itself state whether a `bounded` step still dispatches unattended under it. This task implements `preview_only` identically to `per_run`: every action step requires approval, not merely high-impact ones -- the safer, more literal reading of "nothing executes unattended" this task's own instructions named as the baseline to justify departing from. The alternative reading (`preview_only` additionally blocks even an *approved* step from ever reaching `execute()`, permanently confining a policy in this mode to `/simulate`) was not implemented because `/simulate` already guarantees "never reaches `execute()`" structurally by construction (Decision 4, `adapters.py`'s own module docstring) for *any* simulation request regardless of policy mode -- implementing the second reading would mean this module re-deriving "was this run started via `/simulate` or `POST /runs`" and blocking dispatch a second way for one specific mode, a second enforcement mechanism for a property `/simulate` already has, and squarely a `/simulate`-endpoint concern this task does not touch. Full reasoning in `approvals.py`'s own module docstring.

**Real bug found and fixed during review: `_finish_run` was reused for the non-terminal `waiting_approval`/`needs_review` states, leaving a stale `finished_at` on a run that later resumed.** `process_claimed_run`'s dispatch loop originally called the same `_finish_run` helper Task 2 wrote for genuinely terminal outcomes (`succeeded`/`failed`/`cancelled`) for `waiting_approval` and `needs_review` too. Both are deliberately excluded from `_TERMINAL_RUN_STATUSES` precisely because they are resumable -- and `waiting_approval` has a real, reachable resume path: `approvals._advance_run_after_decision` flips an approved run's status straight back to `'queued'` without ever clearing `finished_at`. The result was a genuinely inconsistent row: `status = 'queued'` (i.e. still actively in flight) with a non-null `finished_at` (implying the run was already done) from the moment it first paused until it next reached a real terminal state. Confirmed by direct experiment against a live PostgreSQL database (a standalone script driving the exact pause -> approve -> resume sequence through the real `worker`/`approvals` modules, not mocked): before the fix, the resumed row showed `status='queued'` with `finished_at` set; reverting the fix later and re-running the affected tests reproduced the same failure (`AssertionError: assert datetime(...) is None`) in `test_high_impact_step_pauses_run_without_ever_calling_execute`, `test_approving_correct_digest_resumes_run_and_dispatches_exactly_once`, `test_no_policy_blocks_dispatch_as_needs_review` and `test_unknown_outcome_surfaces_without_retry`. None of Task 3's original tests asserted on `finished_at` in the pause/resume path, so this was completely uncaught. **Fix:** a new `_pause_run` helper (`worker.py`) performs the identical lease-releasing `UPDATE` as `_finish_run` but deliberately never touches `finished_at`; all three call sites that transition a run to `waiting_approval` or `needs_review` (`StepAwaitingApproval`, `StepBlockedByPolicy`, and Task 2's own `unknown`-outcome branch) now call `_pause_run` instead of `_finish_run`, which keeps the genuinely-terminal `cancelled`/`failed`/`succeeded` transitions on `_finish_run` unchanged. `_finish_run`'s own docstring now states the terminal-only contract explicitly so a future outcome branch cannot make the same mistake silently. Regression assertions (`finished_at is None` through the pause, and again immediately after the approval-triggered resume back to `'queued'`; `finished_at is not None` once the run actually reaches `succeeded`) were added to the four tests named above.

**Judgment calls a reviewer should double-check.** (1) **`preview_only` treated identically to `per_run`** (above) -- the one judgment call this task's own instructions explicitly flagged as needing a documented decision; the alternative reading (permanently confining `preview_only` to `/simulate`, never real dispatch even once approved) was not implemented. (2) **How a `waiting_approval` run resumes** -- reusing the existing `queued`-state claim/poll path via a direct status flip on approval decision, rather than a new `claim_next_run`-adjacent reclaim predicate; chosen because `waiting_approval` carries no `leased_until` a poll cycle could compare against `now()`, and a human's approval decision is already a natural, synchronous, already-transactional trigger to requeue. (3) **How an unusable policy's block is surfaced** -- reusing `needs_review` (Task 2's existing terminal-until-human-action state) rather than a new run status; no new `workflow_runs` column records *which* of "no policy" / "revoked" / "expired" applied -- `run.policy_id` plus the named policy's own `revoked_at`/`expires_at` fields are already sufficient for an operator to determine why. (4) **`policy-limit-exceeding` evaluated using `count_limit` only**, not `value_limit` (no adapter in this activation declares a monetary field) or `rate_limit` (an enqueue-time concern, out of this task's explicit dispatch-time scope). (5) **The gate runs before, not after, the `'dispatched'` row is written** -- a deliberate, disclosed departure from the most literal reading of this task's own instruction text ("after computing digest ... before calling `execute()`"), justified at length in `worker.py`'s own module docstring: writing `'dispatched'` first would make a paused step indistinguishable from Task 2's own crash-ambiguous `unknown` case.
