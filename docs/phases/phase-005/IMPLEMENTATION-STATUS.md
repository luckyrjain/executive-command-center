### Task 1 evidence -- workflow schema, policy model and triggers (data layer only, this commit)

**Migration.** `backend/migrations/versions/0038_phase5_workflow_schema.py` -- the true next-in-chain after `0037_phase4_meeting_timeout2.py`, per this codebase's own documented migration-numbering convention (migration `0029`'s own docstring precedent). Creates four tables, all workspace-scoped (a deliberate divergence from Phase 4's global `prompt_versions`/`tool_definitions`, matching every Phase 1-3 domain table's convention instead -- see the migration's own module docstring for the full reasoning):

- `workflow_definitions` -- the workflow-family identity row (`id`, `workspace_id`, `workflow_id`, `created_by`, timestamps), `UNIQUE(workspace_id, workflow_id)`. A second table beyond the single-table shape Phase 4's `prompt_versions` used, added specifically so `automation_policies`/`triggers` have a stable FK target for "which workflow family" independent of any one version row's lifecycle.
- `workflow_versions` -- `workflow_id`, `version`, `graph` (JSONB), `trigger_refs` (JSONB), `policy_ref` (nullable UUID, no FK -- see migration docstring), `definition_hash` (`sha256` over `{graph, trigger_refs, policy_ref}`), `status` (`draft|active|retired`). `trg_workflow_versions_immutability` (`BEFORE UPDATE`) rejects any change to `graph`/`trigger_refs`/`policy_ref`/`definition_hash` once `status <> 'draft'`, mirroring migration `0029`'s `trg_prompt_versions_immutability` exactly in style. `uq_workflow_versions_active_per_workflow` (partial unique index, `WHERE status = 'active'`) enforces exactly one active version per `(workspace_id, workflow_id)`.
- `automation_policies` -- `workflow_id`, `action_types`/`data_classes` (`ARRAY(TEXT)`), `value_limit`/`count_limit` (both `NOT NULL`, no `server_default` -- `APPROVAL-POLICY.md`'s resolved decision that a policy author must set both explicitly), `rate_limit` (JSONB, defaults to `{"runs_per_workflow_per_hour": 10}` -- the one limit this doc *does* give a system-wide default), `schedule`, `approval_mode` (`preview_only|per_run|bounded_recurring`), `expires_at` (computed in application code as `created_at + 90 days`, never a DB default), `revoked_at`, `version` (optimistic-concurrency column, Phase 3's established idiom).
- `triggers` -- `workflow_id`, `trigger_type` (`manual|event|schedule`), `event_type_filter`, `schedule_expression`, `timezone`, `skip_missed`. Two `CHECK` constraints enforce design doc Decision 7's "a schedule trigger always names its own timezone explicitly" and "an event trigger always names its filter" at the database layer, not only in application code.

Verified against a live PostgreSQL 16 instance: `alembic upgrade head` applies cleanly, `alembic downgrade -1` then `alembic upgrade head` again reproduces an identical schema (migration is cleanly reversible).

**Application code.** `backend/ecc/domains/automation/` (new package): `workflows.py` (`compute_definition_hash`, `validate_graph_shape`, `create_workflow_draft`, `activate_workflow_version`, `disable_workflow_version`, read helpers, and the HTTP router), `policy.py` (`create_policy`, `revoke_policy`, `policy_status`/`is_policy_usable` -- the expiry-check helper -- and the HTTP router), `triggers.py` (`create_trigger`/`get_trigger`/`list_triggers`, no `APIRouter` of its own -- `API-SCHEMAS.md` names no trigger endpoint in this task's scope, mirroring `ai_runtime.tools`'s router-less shape exactly). `activate_workflow_version`/`disable_workflow_version` only ever write `status`/`updated_at`, so neither function can structurally collide with the immutability trigger; `publish`'s endpoint additionally catches `IntegrityError` around the activation call and converts it to a clean `WORKFLOW_VERSION_ACTIVE_CONFLICT` 409 rather than propagating a raw Postgres exception, per this task's own instruction. Wired into `backend/ecc/main.py` alongside the existing Phase 1-4 routers.

**API surface (Task 1 scope only).** `GET|POST /api/v1/automations/workflows`, `GET /api/v1/automations/workflows/{id}`, `POST /api/v1/automations/workflows/{id}/publish|disable`, `GET|POST /api/v1/automations/policies`, `POST /api/v1/automations/policies/{id}/revoke`. **Tests.** `tests/test_automation_worker_postgres.py` -- 25 tests. Covers, per this task's own required minimum: two workers racing the same `workflow_runs` row under real concurrent database connections (`ThreadPoolExecutor`, two independent `SessionFactory` sessions, not mocked) -- exactly one claims it; crash recovery for a run stuck in `leased` with an expired lease, and separately (the stronger case) a run stuck in `running` mid-graph with one step already `succeeded`, reclaimed and resumed from `current_step_index`, never re-dispatching the already-succeeded step; at-most-one-effect (`run_step` called twice for the same step index, the fake adapter's `execute_calls` stays at 1); the unknown-outcome case (a `dispatched` row with a real persisted digest and no recorded outcome, inserted directly to simulate the exact crash timing) surfaces as `unknown`/`needs_review` without ever calling `execute()`; cancellation blocking a not-yet-dispatched step while leaving an already-succeeded one alone; the full enqueue-claim-run-every-step-succeeded path across a 3-step graph; an adapter's `RuntimeError` marking the step `failed` and the run `failed` (`error_class` recorded); workspace isolation (`get_run`/`list_run_steps`/`cancel_run` from workspace B against workspace A's run all fail closed, `cancel_run` returning `WorkflowRunNotFound`); redaction of secret-shaped keys in both stored `input` and `output` (including a unit test of `_redact_payload` over nested structures); `renew_lease` as an independently callable function (updates `leased_until`/`lease_heartbeat_at`, returns `None` for the wrong `worker_id`); `compute_action_digest`'s payload-substitution property (changing `resolved_input` or `workflow_version` changes the digest, same inputs reproduce the same digest); `AdapterRegistry`'s own registration-time validation; `DigestVisibilityProbeAdapter` (a real crash-durability proof, not an absence-of-exception check -- see the "Real bug found and fixed during review" note below).

**Real bug found and fixed during review: `run_step`'s digest write was `flush()`-ed, not committed.** `run_step` originally called `session.flush()` (not `session.commit()`) after inserting the `'dispatched'`+`action_digest` row, and every other write in this module (`claim_next_run`'s lease claim, `_mark_running`/`_finish_run`'s state transitions, every outcome `UPDATE` in `run_step`) was left to whatever transaction the caller's own `with session.begin():` block happened to commit. Since `process_claimed_run` runs an entire multi-step graph inside one such caller-managed transaction, `flush()` alone meant none of it was actually durable until the *whole run* finished and the outer transaction committed -- a real process crash at any point mid-run (including, worst case, right after a real adapter's `execute()` call had a genuine external side effect) would roll back everything, including the claim itself, leaving the run looking exactly like it was never touched. A subsequent worker would then legitimately re-claim and re-execute it from scratch: a real duplicate side effect, the exact failure Decision 3's digest-before-execute guarantee and `EXECUTION-CONTRACT.md`'s "at most one effect under crash/retry" exist to prevent. Confirmed by direct experiment: reverting the fix's one `commit()` back to `flush()` makes `test_dispatched_digest_is_durably_committed_before_execute_is_called` fail (its `DigestVisibilityProbeAdapter` opens an independent connection inside `execute()` and finds the 'dispatched' row genuinely invisible, since an uncommitted write in one transaction is not visible to another under this database's default READ COMMITTED isolation); restoring the fix makes it pass again. **Fix:** every durability-critical write in `worker.py` (`claim_next_run`, `renew_lease`, `_mark_running`, `_finish_run`, and all five outcome-writing branches inside `run_step`) now calls `session.commit()` directly on a bare session, matching `ecc.domains.ai_runtime.runtime._persist_terminal`'s own established precedent for the identical problem (a long-running operation that must durably checkpoint before a risky external call, called from both fresh and already-open sessions). This required updating every test call site that invoked one of these functions from inside a `with session.begin():` block to a bare `with SessionFactory() as session:` instead (`session.commit()` called from inside a caller-held `.begin()` context raises `InvalidRequestError` -- confirmed directly), and adding `test_dispatched_digest_is_durably_committed_before_execute_is_called` (`DigestVisibilityProbeAdapter`) as the one test that proves the property directly rather than merely by absence of an exception, since none of Task 2's original tests would have caught this: they only ever exercised the "already dispatched" recovery path via a hand-constructed row inserted through a separate, genuinely-committed connection, never by observing `run_step`'s own internal write actually become durable.

**Cross-check against `docs/runbooks/PHASE-5-RECOVERY.md`'s specific claims.** 30s lease + 2s poll interval + heartbeat every step (at least every 10s) matches the runbook's numbers exactly (`worker.py`'s `LEASE_DURATION_SECONDS`/`POLL_INTERVAL_SECONDS`/`HEARTBEAT_INTERVAL_SECONDS` = `30`/`2`/`10`, unchanged from Decision 3). The one real divergence -- the reclaim predicate needing to cover `running`, not `leased` alone, for the recovery guarantee to hold for a crash mid-run rather than only a crash immediately post-claim -- is corrected in the runbook itself (this commit), not silently papered over; the 90-second manual-confirmation diagnostic query in that runbook is updated to match (`status IN ('leased', 'running')`). No other number or mechanic diverged between the design-time document and this implementation.

**Judgment calls a reviewer should double-check.** (1) **The claim predicate's `leased`-vs-`running` generalization** (above) -- the single most load-bearing deviation from Decision 3's literal SQL text in this task; flagged in three places (`worker.py`'s own docstring, this evidence section, `PHASE-5-RECOVERY.md`'s new correction section) rather than left implicit. (2) **Heartbeat shape** -- `renew_lease` is called once per step by `process_claimed_run` (the "called between steps at minimum" option this task's own instructions explicitly allowed), not a background thread; sufficient for this task's fast in-process fake adapters, and reusable as-is by a later task's slow real adapters wrapping one `execute()` call in a timer that calls this same function every 10s while that call is in flight. (3) **Adapter failure produces `failed`, not `needs_review`** -- an adapter's own raised exception is a definitively-classified failure (the process is still alive to observe and record it), distinct from the crash-interrupted case (`unknown`/`needs_review`), where the process died before any outcome could be recorded at all; this task treats only the latter as ambiguous. (4) **No internal-only HTTP endpoint was added** -- this task's own tests call the worker's functions directly, which proved sufficient; a reviewer who wants a browser-observable proof of this task's behavior before Task 3/5 land would need to add one, deliberately not done here per this task's own default. (5) **`resolved_input` is the step's static `input_mapping` dict as-is** -- this task does not implement `input_mapping`'s `$trigger.*`/prior-step-output templating (that materialization is `runtime.py`'s concern, the design doc's Architecture impact section lists it as a separate module from `worker.py`); sufficient to prove the digest/idempotency/lease mechanics this task must prove, but a later task's real orchestration loop will need to resolve `input_mapping` before calling `run_step`, not after.

### Task 3 evidence -- approval inbox and policy-driven revocation enforcement

**Migration.** `backend/migrations/versions/0040_phase5_approval_requests.py` -- the true next-in-chain after `0039_phase5_workflow_runs.py`. Creates `approval_requests`: `(workspace_id, run_id)` composite-FK'd to `workflow_runs(workspace_id, id)` with `ondelete="CASCADE"` (identical shape to `workflow_run_steps`'s own FK); `step_index`; `action_digest` (`String(64)`, the exact digest this request authorizes); `high_impact_categories` (`ARRAY(TEXT)`, matching `automation_policies.action_types`'s own array convention); `status` restricted to three values (`pending|approved|rejected`), **not** four -- `expires_at`-driven expiry is computed live (`approvals.approval_lifecycle_status`), never written back to the row, mirroring `automation_policies`' own "no stored lifecycle column, a pure function derives the label" convention exactly (the migration's own docstring spells out the transactional problem this sidesteps: a lazy `expired` write from inside a router's `with session.begin():` block would be rolled back by the very `HTTPException` an expired decision raises). Two `CHECK` constraints enforce `status`/`decision`/`decided_at`/`decided_by` consistency at the database layer (a `pending` row has all three `NULL`; a decided row has all three set, `decision` matching `status`). `(workspace_id, decided_by)` composite-FK's to `users`, nullable -- Postgres's `MATCH SIMPLE` semantics skip enforcement entirely while `decided_by IS NULL` (a `pending` row), matching every other actor-reference FK in this codebase for every row that has actually been decided. ### Task 4 evidence -- schedule triggers, pause/resume and the run-management HTTP surface

**Scope, precisely stated (the roadmap label says "notifications"; the actual contract text overrides it).** This task ships: (1) `ecc.domains.automation.scheduler` -- the 60-second schedule-trigger evaluation tick (Decision 7), timezone-aware via `zoneinfo` + a newly-added `croniter` dependency, with catch-up-once misfire semantics; (2) `worker.pause_run`/`worker.resume_run` -- the user-initiated pause/resume named in `API-SCHEMAS.md`; (3) `ecc.domains.automation.runs` -- the `/api/v1/automations/runs` HTTP surface (`GET|POST /runs`, `GET /runs/{id}`, `POST /runs/{id}/pause|resume|cancel`). It does **not** ship event-trigger firing or a notifications delivery system -- both explicitly out of scope, reasoning below.

**Flagged discrepancy: no pre-existing cron-parsing dependency.** The design doc's own text (Decision 7) reads "an existing cron-parsing dependency already available to the backend" -- checked directly against `pyproject.toml`/`uv.lock` before writing `scheduler.py`: no such dependency existed. Resolved by adding `croniter==6.2.4` (small, pure-Python, MIT-licensed, composes directly with `zoneinfo`) as a new pinned dependency -- a mechanical library addition, not a new RFC-005-gated technology activation (it is a library choice inside an already-approved activation, distinct from Decision 1's Temporal-vs-Postgres question). `scheduler.py`'s own module docstring restates this in full.

**Migration.** `backend/migrations/versions/0041_phase5_scheduler_and_pause.py` -- the true next-in-chain after `0040_phase5_approval_requests.py`. Adds two nullable columns to existing tables, no new table: `triggers.last_fired_at` (the scheduler's own catch-up-once anchor) and `workflow_runs.pause_requested_at` (the user-initiated-pause analogue of `cancel_requested_at`, migration 0039). Verified against a live PostgreSQL 16 instance: `alembic upgrade head` applies cleanly, `downgrade -1` then `upgrade head` again reproduces an identical schema.

**Last-fired-tracking design choice: a dedicated `triggers.last_fired_at` column, not a `MAX(queued_at)` derivation from `workflow_runs`.** Two options were on the table (this task's own instructions named both): (a) a new column, updated transactionally alongside the fired run; (b) query the most recent `workflow_runs` row with `trigger_ref = 'schedule:<id>'`. This task picks (a): a dedicated column makes "did this trigger already fire for this window" a single indexed point lookup rather than a string-prefix-filtered scan with no supporting index, and keeps the trigger's own fire-bookkeeping colocated with the trigger row itself. `scheduler.run_scheduler_once` writes both the fired `workflow_runs` row (`worker.enqueue_run`) and the anchor update (`triggers.mark_trigger_fired`) inside **one atomic transaction, one commit** -- not `run_step`'s two-commit before/after-`execute()` discipline, because there is no risky external call between the two writes to bracket (`enqueue_run` only ever inserts a `queued` row). This is the more conservative choice than either single-write-first-then-second-write-separately ordering: committing the run before the anchor risks a crash-induced duplicate fire; committing the anchor before the run risks a crash-induced silently-lost fire; one atomic transaction has neither failure mode. `scheduler.py`'s own module docstring has the full reasoning, including why this is a *simpler* discipline than `worker.py`'s, not a departure from its "durability-critical writes commit immediately on a bare session" rule.

**Misfire policy, made mechanically concrete.** Per trigger, per tick: compute `first_due` (earliest occurrence after the anchor); if in the future, not due. Otherwise compute `second_due` (the occurrence after that); if `second_due` has also already elapsed, more than one window was missed -- a genuine backlog, not merely "on time within one tick." A backlog fires **once** (`skip_missed=False`, the default) or **zero times** (`skip_missed=True`); either way the anchor advances straight to the tick's own `now`, never to `first_due` or any earlier instant, so no trigger can ever be re-evaluated as "still owing" a fire this tick already resolved. A single elapsed occurrence (the ordinary steady state) always fires regardless of `skip_missed` -- this is what lets a `skip_missed=True` trigger still fire at all once it catches up to the present, rather than suppressing every fire unconditionally.

**Real bug found and fixed during review: two concurrent scheduler ticks could both fire the same due trigger.** `triggers.mark_trigger_fired` originally performed an unconditional `UPDATE`, not a compare-and-swap -- unlike `worker.claim_next_run`'s already-established `UPDATE ... WHERE <the state just read> RETURNING ...` idiom for the structurally identical "two independent processes acting on the same row with no `SELECT ... FOR UPDATE` lock" shape. Two scheduler instances (e.g. two `scripts/run_automation_worker.py` replicas, a very ordinary horizontal-scaling move for the "the worker runs as a service" deployment `docs/runbooks/PHASE-5-RECOVERY.md` already anticipates) evaluating the same due trigger at effectively the same instant would both read the same stale `last_fired_at`, both compute `_Due`, and both call `worker.enqueue_run` -- two `workflow_runs` rows for one scheduled occurrence, exactly the kind of duplicate side effect Decision 7's entire misfire-policy section exists to prevent, just caused by concurrency rather than a crash. Undisclosed and untested by this task's own original test suite (no test exercised two concurrent `run_scheduler_once` calls at all). **Fix:** `mark_trigger_fired` now takes `expected_last_fired_at` and performs `UPDATE ... WHERE ... AND last_fired_at IS NOT DISTINCT FROM :expected_last_fired_at`, returning whether it won; `run_scheduler_once` calls it *before* `enqueue_run` (still inside the same one-commit transaction, preserving the original durability property unchanged) and only proceeds to enqueue if it won -- a lost race returns the new `TriggerRaceLost` outcome and enqueues nothing. Proven two ways: a deterministic, non-threaded test calling `mark_trigger_fired` twice with the same stale expectation (the second call reliably returns `False`, no dependence on real thread timing), and a real-concurrency `ThreadPoolExecutor` test asserting at most one `TriggerFired`/one `workflow_runs` row ever results from two simultaneous ticks -- mirroring `worker.py`'s own `test_two_workers_racing_the_same_run_exactly_one_claims_it` precedent for the identical class of property. `scheduler.py`'s own module docstring gained a "Concurrency safety" section explaining the mechanism (Postgres's default READ COMMITTED semantics: the losing transaction's `UPDATE` blocks on the winner's row lock, then re-evaluates its `WHERE` clause against the now-committed data and naturally affects zero rows -- no explicit lock needed).

**Also found and fixed during the same review pass:** a `mypy` error (`triggers.mark_trigger_fired`'s `session.execute(...).rowcount` -- `Session.execute`'s stub return type does not statically expose `rowcount` even though the runtime object always has one for a `text()` `UPDATE`), fixed with an explicit `cast` and a comment explaining why, not a blanket `# type: ignore`. And one idempotency-key literal in `tests/test_automation_runs_postgres.py`'s no-CSRF test tripped `gitleaks`' entropy-based `generic-api-key` rule as a false positive on this PR's first CI run (a coincidental character-entropy match on an ordinary test string, not a real secret -- confirmed by inspecting the flagged line directly and computing its Shannon entropy against several lower-entropy alternatives); renamed to a lower-entropy literal rather than adding permanent gitleaks allowlist configuration for one test string.

**Real bug found and fixed during this task's own self-review: `cancel_run` left an already-`'paused'` run permanently stuck.** `'paused'` is deliberately excluded from `_CLAIMABLE_PREDICATE` (a paused run must never be silently reclaimed and resumed by a poll cycle -- only an explicit `resume_run` call may do that), which means `process_claimed_run` never revisits a `'paused'` run on its own. `cancel_run`'s original logic (mirrored unchanged from Task 2) only flipped `status` to `'cancelled'` immediately for a `'queued'` run; every other non-terminal status, including the newly-reachable `'paused'`, only got `cancel_requested_at` set with `status` left unchanged. For `'paused'` specifically this is a real, permanent bug: no code path ever consults that flag again without an intervening `resume_run` call the operator may never make (they asked to *cancel*, not resume-then-cancel) -- the run would sit forever in `'paused'`, looking cancellable but never actually becoming `'cancelled'`. Confirmed by direct experiment: temporarily disabling the fix (`test_cancel_an_already_paused_run_becomes_cancelled_not_stuck`, reverted and re-applied) reproduces `AssertionError: assert 'paused' == 'cancelled'`; with the fix, the same test passes and a follow-up `resume_run` attempt on the now-`'cancelled'` run correctly reports `WorkflowRunNotPaused(status='cancelled')`, confirming the run is genuinely terminal, not merely relabeled. **Fix:** `cancel_run`'s immediate-terminal branch now reads `row["status"] in ("queued", "paused")` -- safe because a `'paused'` run, by construction, has already had its lease released by `_pause_run` (`leased_by`/`leased_until` both `NULL`), so there is no in-flight step to protect, exactly like a never-claimed `'queued'` run. `worker.py`'s own module docstring and `cancel_run`'s docstring both restate this.
