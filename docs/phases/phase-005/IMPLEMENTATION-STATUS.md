**Real bug found and fixed during review: `run_step`'s digest write was `flush()`-ed, not committed.** `run_step` originally called `session.flush()` (not `session.commit()`) after inserting the `'dispatched'`+`action_digest` row, and every other write in this module (`claim_next_run`'s lease claim, `_mark_running`/`_finish_run`'s state transitions, every outcome `UPDATE` in `run_step`) was left to whatever transaction the caller's own `with session.begin():` block happened to commit. Since `process_claimed_run` runs an entire multi-step graph inside one such caller-managed transaction, `flush()` alone meant none of it was actually durable until the *whole run* finished and the outer transaction committed -- a real process crash at any point mid-run (including, worst case, right after a real adapter's `execute()` call had a genuine external side effect) would roll back everything, including the claim itself, leaving the run looking exactly like it was never touched. A subsequent worker would then legitimately re-claim and re-execute it from scratch: a real duplicate side effect, the exact failure Decision 3's digest-before-execute guarantee and `EXECUTION-CONTRACT.md`'s "at most one effect under crash/retry" exist to prevent. Confirmed by direct experiment: reverting the fix's one `commit()` back to `flush()` makes `test_dispatched_digest_is_durably_committed_before_execute_is_called` fail (its `DigestVisibilityProbeAdapter` opens an independent connection inside `execute()` and finds the 'dispatched' row genuinely invisible, since an uncommitted write in one transaction is not visible to another under this database's default READ COMMITTED isolation); restoring the fix makes it pass again. **Fix:** every durability-critical write in `worker.py` (`claim_next_run`, `renew_lease`, `_mark_running`, `_finish_run`, and all five outcome-writing branches inside `run_step`) now calls `session.commit()` directly on a bare session, matching `ecc.domains.ai_runtime.runtime._persist_terminal`'s own established precedent for the identical problem (a long-running operation that must durably checkpoint before a risky external call, called from both fresh and already-open sessions). This required updating every test call site that invoked one of these functions from inside a `with session.begin():` block to a bare `with SessionFactory() as session:` instead (`session.commit()` called from inside a caller-held `.begin()` context raises `InvalidRequestError` -- confirmed directly), and adding `test_dispatched_digest_is_durably_committed_before_execute_is_called` (`DigestVisibilityProbeAdapter`) as the one test that proves the property directly rather than merely by absence of an exception, since none of Task 2's original tests would have caught this: they only ever exercised the "already dispatched" recovery path via a hand-constructed row inserted through a separate, genuinely-committed connection, never by observing `run_step`'s own internal write actually become durable.

**Cross-check against `docs/runbooks/PHASE-5-RECOVERY.md`'s specific claims.** 30s lease + 2s poll interval + heartbeat every step (at least every 10s) matches the runbook's numbers exactly (`worker.py`'s `LEASE_DURATION_SECONDS`/`POLL_INTERVAL_SECONDS`/`HEARTBEAT_INTERVAL_SECONDS` = `30`/`2`/`10`, unchanged from Decision 3). The one real divergence -- the reclaim predicate needing to cover `running`, not `leased` alone, for the recovery guarantee to hold for a crash mid-run rather than only a crash immediately post-claim -- is corrected in the runbook itself (this commit), not silently papered over; the 90-second manual-confirmation diagnostic query in that runbook is updated to match (`status IN ('leased', 'running')`). No other number or mechanic diverged between the design-time document and this implementation.

**Judgment calls a reviewer should double-check.** (1) **The claim predicate's `leased`-vs-`running` generalization** (above) -- the single most load-bearing deviation from Decision 3's literal SQL text in this task; flagged in three places (`worker.py`'s own docstring, this evidence section, `PHASE-5-RECOVERY.md`'s new correction section) rather than left implicit. (2) **Heartbeat shape** -- `renew_lease` is called once per step by `process_claimed_run` (the "called between steps at minimum" option this task's own instructions explicitly allowed), not a background thread; sufficient for this task's fast in-process fake adapters, and reusable as-is by a later task's slow real adapters wrapping one `execute()` call in a timer that calls this same function every 10s while that call is in flight. (3) **Adapter failure produces `failed`, not `needs_review`** -- an adapter's own raised exception is a definitively-classified failure (the process is still alive to observe and record it), distinct from the crash-interrupted case (`unknown`/`needs_review`), where the process died before any outcome could be recorded at all; this task treats only the latter as ambiguous. (4) **No internal-only HTTP endpoint was added** -- this task's own tests call the worker's functions directly, which proved sufficient; a reviewer who wants a browser-observable proof of this task's behavior before Task 3/5 land would need to add one, deliberately not done here per this task's own default. (5) **`resolved_input` is the step's static `input_mapping` dict as-is** -- this task does not implement `input_mapping`'s `$trigger.*`/prior-step-output templating (that materialization is `runtime.py`'s concern, the design doc's Architecture impact section lists it as a separate module from `worker.py`); sufficient to prove the digest/idempotency/lease mechanics this task must prove, but a later task's real orchestration loop will need to resolve `input_mapping` before calling `run_step`, not after.

### Task 4 evidence -- schedule triggers, pause/resume and the run-management HTTP surface

**Scope, precisely stated (the roadmap label says "notifications"; the actual contract text overrides it).** This task ships: (1) `ecc.domains.automation.scheduler` -- the 60-second schedule-trigger evaluation tick (Decision 7), timezone-aware via `zoneinfo` + a newly-added `croniter` dependency, with catch-up-once misfire semantics; (2) `worker.pause_run`/`worker.resume_run` -- the user-initiated pause/resume named in `API-SCHEMAS.md`; (3) `ecc.domains.automation.runs` -- the `/api/v1/automations/runs` HTTP surface (`GET|POST /runs`, `GET /runs/{id}`, `POST /runs/{id}/pause|resume|cancel`). It does **not** ship event-trigger firing or a notifications delivery system -- both explicitly out of scope, reasoning below.

**Flagged discrepancy: no pre-existing cron-parsing dependency.** The design doc's own text (Decision 7) reads "an existing cron-parsing dependency already available to the backend" -- checked directly against `pyproject.toml`/`uv.lock` before writing `scheduler.py`: no such dependency existed. Resolved by adding `croniter==6.2.4` (small, pure-Python, MIT-licensed, composes directly with `zoneinfo`) as a new pinned dependency -- a mechanical library addition, not a new RFC-005-gated technology activation (it is a library choice inside an already-approved activation, distinct from Decision 1's Temporal-vs-Postgres question). `scheduler.py`'s own module docstring restates this in full.

**Migration.** `backend/migrations/versions/0041_phase5_scheduler_and_pause.py` -- the true next-in-chain after `0040_phase5_approval_requests.py`. Adds two nullable columns to existing tables, no new table: `triggers.last_fired_at` (the scheduler's own catch-up-once anchor) and `workflow_runs.pause_requested_at` (the user-initiated-pause analogue of `cancel_requested_at`, migration 0039). Verified against a live PostgreSQL 16 instance: `alembic upgrade head` applies cleanly, `downgrade -1` then `upgrade head` again reproduces an identical schema.

**Last-fired-tracking design choice: a dedicated `triggers.last_fired_at` column, not a `MAX(queued_at)` derivation from `workflow_runs`.** Two options were on the table (this task's own instructions named both): (a) a new column, updated transactionally alongside the fired run; (b) query the most recent `workflow_runs` row with `trigger_ref = 'schedule:<id>'`. This task picks (a): a dedicated column makes "did this trigger already fire for this window" a single indexed point lookup rather than a string-prefix-filtered scan with no supporting index, and keeps the trigger's own fire-bookkeeping colocated with the trigger row itself. `scheduler.run_scheduler_once` writes both the fired `workflow_runs` row (`worker.enqueue_run`) and the anchor update (`triggers.mark_trigger_fired`) inside **one atomic transaction, one commit** -- not `run_step`'s two-commit before/after-`execute()` discipline, because there is no risky external call between the two writes to bracket (`enqueue_run` only ever inserts a `queued` row). This is the more conservative choice than either single-write-first-then-second-write-separately ordering: committing the run before the anchor risks a crash-induced duplicate fire; committing the anchor before the run risks a crash-induced silently-lost fire; one atomic transaction has neither failure mode. `scheduler.py`'s own module docstring has the full reasoning, including why this is a *simpler* discipline than `worker.py`'s, not a departure from its "durability-critical writes commit immediately on a bare session" rule.

**Misfire policy, made mechanically concrete.** Per trigger, per tick: compute `first_due` (earliest occurrence after the anchor); if in the future, not due. Otherwise compute `second_due` (the occurrence after that); if `second_due` has also already elapsed, more than one window was missed -- a genuine backlog, not merely "on time within one tick." A backlog fires **once** (`skip_missed=False`, the default) or **zero times** (`skip_missed=True`); either way the anchor advances straight to the tick's own `now`, never to `first_due` or any earlier instant, so no trigger can ever be re-evaluated as "still owing" a fire this tick already resolved. A single elapsed occurrence (the ordinary steady state) always fires regardless of `skip_missed` -- this is what lets a `skip_missed=True` trigger still fire at all once it catches up to the present, rather than suppressing every fire unconditionally.

**Real bug found and fixed during review: two concurrent scheduler ticks could both fire the same due trigger.** `triggers.mark_trigger_fired` originally performed an unconditional `UPDATE`, not a compare-and-swap -- unlike `worker.claim_next_run`'s already-established `UPDATE ... WHERE <the state just read> RETURNING ...` idiom for the structurally identical "two independent processes acting on the same row with no `SELECT ... FOR UPDATE` lock" shape. Two scheduler instances (e.g. two `scripts/run_automation_worker.py` replicas, a very ordinary horizontal-scaling move for the "the worker runs as a service" deployment `docs/runbooks/PHASE-5-RECOVERY.md` already anticipates) evaluating the same due trigger at effectively the same instant would both read the same stale `last_fired_at`, both compute `_Due`, and both call `worker.enqueue_run` -- two `workflow_runs` rows for one scheduled occurrence, exactly the kind of duplicate side effect Decision 7's entire misfire-policy section exists to prevent, just caused by concurrency rather than a crash. Undisclosed and untested by this task's own original test suite (no test exercised two concurrent `run_scheduler_once` calls at all). **Fix:** `mark_trigger_fired` now takes `expected_last_fired_at` and performs `UPDATE ... WHERE ... AND last_fired_at IS NOT DISTINCT FROM :expected_last_fired_at`, returning whether it won; `run_scheduler_once` calls it *before* `enqueue_run` (still inside the same one-commit transaction, preserving the original durability property unchanged) and only proceeds to enqueue if it won -- a lost race returns the new `TriggerRaceLost` outcome and enqueues nothing. Proven two ways: a deterministic, non-threaded test calling `mark_trigger_fired` twice with the same stale expectation (the second call reliably returns `False`, no dependence on real thread timing), and a real-concurrency `ThreadPoolExecutor` test asserting at most one `TriggerFired`/one `workflow_runs` row ever results from two simultaneous ticks -- mirroring `worker.py`'s own `test_two_workers_racing_the_same_run_exactly_one_claims_it` precedent for the identical class of property. `scheduler.py`'s own module docstring gained a "Concurrency safety" section explaining the mechanism (Postgres's default READ COMMITTED semantics: the losing transaction's `UPDATE` blocks on the winner's row lock, then re-evaluates its `WHERE` clause against the now-committed data and naturally affects zero rows -- no explicit lock needed).

This task adds `compensate_ref: str | None` to `GraphStepModel` and four new structural rules to `validate_graph_shape` (`workflows.py`): valid only on a `step_type='action'` step; must resolve to an existing `step_id` in the same graph; that target step's own `step_type` must be `'compensation'`; a `step_type='compensation'` step may never be the target of any `on_success`/`on_failure` edge, and may never itself declare a `compensate_ref` (no nested compensation). `tests/test_automation_workflows_postgres.py` gained 7 new tests (44 total, up from 37) covering every one of these rules directly, plus the well-formed-graph acceptance case.

**A second real gap, in `worker.process_claimed_run`'s own main loop, fixed before compensation dispatch could be wired in at all.** Confirmed directly by reading `run_step` (as this task's own instructions required): it raises `UnsupportedStepType` for any `step_type != "action"` -- unhandled by `process_claimed_run`'s dispatch loop, which previously called `run_step` unconditionally for every `step_index` it walked. A `step_type='compensation'` step sitting inline in the flat `steps` list (or, by the identical latent gap, an `'approval_gate'`/`'condition'` step -- neither of those two ever gets exercised by any of this activation's own graphs, but the mechanism was equally unsafe for them) would, if the main walk ever linearly reached it, crash the entire claimed-run dispatch. **Fix:** the main loop now checks `step.get("step_type") != "action"` *before* renewing the lease or dispatching, and skips forward (`step_index += 1; continue`) without ever calling `run_step` and without writing any `workflow_run_steps` row for the skipped step -- deliberately generalized to any non-`'action'` step type, not narrowly patched for `'compensation'` alone, since the underlying crash risk was identical for all three. `tests/test_automation_compensation_postgres.py::test_inline_compensation_step_never_crashes_the_main_walk` proves this directly: a three-step graph with a `compensation` step physically at index 1 (never targeted by any edge) completes normally, with `workflow_run_steps` rows written for indices 0 and 2 only -- reverting the fix reproduces the original `UnsupportedStepType` crash immediately.

**Bounded retry (`EXECUTION-CONTRACT.md`: "bounded exponential backoff only for classified transient failures ... never for a step whose side effect may have already partially occurred").** No such mechanism existed before this task -- `run_step`'s `except Exception` block caught literally anything and immediately, unconditionally marked the step `'failed'`. `adapters.TransientAdapterError` (new, declared alongside `ActionAdapter` since it is part of the adapter-contract surface an adapter author needs to know about) is the one exception class an adapter may raise to assert "this specific failure definitely occurred before any side effect, safe to auto-retry" -- every other exception keeps today's exact unconditional-`'failed'` behavior; `run_step` never guesses retry-safety for an unclassified error. `MAX_RETRY_ATTEMPTS = 3`, backoff `RETRY_BACKOFF_BASE_SECONDS ** attempt_count` seconds (`_retry_backoff_seconds`: 2s/4s/8s for attempts 1/2/3), both new module-level constants in `worker.py` alongside `POLL_INTERVAL_SECONDS`/`LEASE_DURATION_SECONDS`. On a `TransientAdapterError` with `attempt_count < MAX_RETRY_ATTEMPTS`, `run_step` itself (not `process_claimed_run`) durably commits `workflow_run_steps.status = 'retrying'`/`attempt_count += 1` and releases the run's own lease back to `'queued'` with `next_attempt_at = now() + backoff` -- the identical lease-release shape `_pause_run` uses, via a direct `UPDATE` rather than a call to `_pause_run` itself (which has no `next_attempt_at` parameter and is reserved for `waiting_approval`/`needs_review`). `_CLAIMABLE_PREDICATE` gained `AND (next_attempt_at IS NULL OR next_attempt_at <= now())` so a retry-pending run is never reclaimed before its backoff elapses. Once exhausted, `run_step` falls through to the ordinary, unconditional `'failed'` path unchanged. A `'retrying'`-status existing row (a reclaimed, now-due run resuming the exact step it paused on) is handled by `run_step`'s existing-row branch falling through to a fresh dispatch attempt that `UPDATE`s the same row (never a second `INSERT`), reusing its carried-forward `attempt_count` -- exactly the same "fall through to a fresh dispatch below" shape Task 2's own `'pending'`/`'skipped'` branch already had.

**Compensation dispatch (Decision 9).** When a step's outcome is `'failed'`, `process_claimed_run` no longer unconditionally calls `_finish_run(..., "failed")` -- it first calls `_qualifying_compensations` (new), which looks at the graph's own already-`succeeded` `action` steps with index `< step_index` (the step that just failed is never itself compensated) and collects any with a `compensate_ref` set, in **descending** original-step-index order (standard saga rollback order: undo the most recently completed effect first -- proven directly by `test_two_qualifying_compensations_dispatch_in_descending_order`, two compensatable steps, asserting the exact dispatch order via a shared log list). No qualifying step: unchanged behavior, `_finish_run(..., "failed")`. One or more: `_mark_compensating` (new) flips `run.status` to `'compensating'` via a direct `UPDATE` that deliberately does **not** release the lease (an automatic continuation of the same claimed dispatch, not a human-wait state), then `_run_compensation_sequence` (new) dispatches each qualifying compensation in turn via `_dispatch_compensation_step` (new), renewing the lease before each -- continuing to attempt every qualifying compensation even after one fails, so partial compensation stays visible (this phase's own acceptance criterion), never stopping early. `_dispatch_compensation_step` computes its own `action_digest` from the *compensation* step's own `step_id`/`input_mapping` (never the original step's -- this identifies *this compensation dispatch attempt*), writes its own `workflow_run_steps` row (`step_type='compensation'`, at the compensation step's own `step_index` -- a row distinct from the step it compensates, per `DATA-MODEL.md`) plus its own `compensation_steps` ledger row (`compensates_step_index` = the *original* step's index), with identical commit-before-execute durability discipline to `run_step` itself. Once every qualifying compensation has been attempted: all succeeded -> `_finish_run(..., "compensated")`; any failed/unknown -> `_finish_run(..., "compensation_failed")`. `process_claimed_run`'s own cancel/pause/kill-switch checks are deliberately never re-consulted inside this sequence -- once compensation starts, it runs to its own completion, generalizing this module's existing "an already-dispatched step is never force-interrupted" philosophy to a whole compensation sequence.

**The two-shapes adapter-resolution judgment call (resolved and documented, not left ambiguous).** Decision 9 and `local_adapters.py`'s `FakeExternalActionAdapter.compensate()` were read carefully before deciding: `compensate(action_input)` is documented to take "the same `action_input` `execute()` was originally called with, not the prior `execute()` call's output." This task's own reading: `_dispatch_compensation_step` prefers the *original* step's own registered adapter's `compensate()` (`adapters.compensable`) when declared, calling it with the *original* step's own resolved input (`test_step_1_succeeds_step_2_fails_compensates_step_1_ends_compensated` asserts this directly -- the compensation step's own, deliberately-different `input_mapping` is never what reaches `compensate()`); when the original adapter declares no `compensate()`, the *compensation* step's own `action_ref` is expected to name a distinct, dedicated "undo" adapter registration, dispatched via that adapter's ordinary `execute()` with the compensation step's own resolved input instead (`test_original_adapter_without_compensate_falls_back_to_dedicated_undo_adapter`). A reviewer who prefers the opposite precedence (compensation-step-adapter-first, original-adapter-compensate-as-fallback) should treat this as the one judgment call most worth double-checking -- both shapes are real and tested, only their priority order was a genuine choice this task made.

**Kill switches (`docs/runbooks/PHASE-5-RECOVERY.md`'s "Kill switches and their recovery interaction" section, written at design time with no table behind it before this task).** New module `backend/ecc/domains/automation/kill_switches.py` -- `activate_kill_switch`/`deactivate_kill_switch`/`is_workflow_killed`/`get_active_kill_switch`/`get_latest_kill_switch`/`list_kill_switches`, plus `POST /automations/workflows/{workflow_id}/kill_switch` and `POST /automations/kill_switch`, both actor-authenticated, CSRF- and idempotency-key-protected, following `workflows.py`/`policy.py`'s exact idempotency-lock/audit/outbox pattern. **Real bug found and fixed during this task's own self-review: `renew_lease` did not recognize `'compensating'` as a lease-bearing state.** `_mark_compensating` deliberately keeps the run's existing lease (module docstring: "an automatic continuation of the same claimed dispatch, not a human-wait state"), and `_run_compensation_sequence` renews that lease before each compensation it dispatches, calling the same `renew_lease` function every ordinary step dispatch already uses. `renew_lease`'s own `WHERE` clause, however, still read `status IN ('leased', 'running')` -- unchanged since Task 2, and never widened when `'compensating'` was introduced this same task. The result: every compensation-dispatch test failed immediately, not on some edge case -- `renew_lease` returned `None` on the very first compensation attempt (the run's status is `'compensating'`, matching neither of the two states the `WHERE` clause checked), `_run_compensation_sequence` interpreted this as "lease lost" and returned immediately without dispatching anything, leaving the run stuck in `'compensating'` forever. Confirmed by direct experiment: `test_step_1_succeeds_step_2_fails_compensates_step_1_ends_compensated` (and three of this task's other five new compensation tests) failed with `AssertionError: assert 'compensating' == 'compensated'` before the fix; all pass after it. **Fix:** `renew_lease`'s `WHERE` clause now reads `status IN ('leased', 'running', 'compensating')` -- a one-word-wider generalization, mirroring `claim_next_run`'s own identical `'leased'`-to-`'leased', 'running'` generalization from Task 2's own review, both docstrings cross-referencing each other's reasoning explicitly rather than restating it.

**Real bug found and fixed during my own independent review pass (after this task's implementing agent's own self-review, before merge): two action steps sharing one `compensate_ref` target silently dropped the second step's compensation while the run still reported full success.** `_dispatch_compensation_step`'s idempotency short-circuit is keyed on `workflow_run_steps`' own `(run_id, step_index)` -- the compensation step's *graph position* -- exactly like every other step in this table, deliberately reusing that established idempotency shape rather than inventing a new one (this task's own design choice, correct on its own terms). But `validate_graph_shape`'s original four `compensate_ref` rules never checked that the mapping from a `compensate_ref` target back to the action step(s) declaring it is one-to-one -- nothing stopped two different action steps from pointing `compensate_ref` at the *same* `step_type='compensation'` step_id. Reproduced directly against a live PostgreSQL instance: a graph with `s1`/`s2` both succeeding and both declaring `compensate_ref="c1"`, then `s3` failing -- `_qualifying_compensations` correctly produces two tuples in descending order, but `_run_compensation_sequence` dispatching the first (`s2`'s) compensation INSERTs a `workflow_run_steps` row at `c1`'s `step_index` and marks it `succeeded`; dispatching the second (`s1`'s) then finds that row *already* `succeeded` at the same `step_index` and returns immediately -- `compensate()` is never called for `s1`, no `compensation_steps` ledger row is ever written for `compensates_step_index=0`, and the run still ends `status='compensated'`, reporting complete success while one step's real side effect was never undone and there is no ledger trace that it was ever supposed to be. **Fix:** rather than loosening the dispatch idempotency key (a far larger, riskier change than this activation's simple graph model needs, and the wrong fix regardless -- `(run_id, step_index)` is the same invariant every other step in this table depends on), `validate_graph_shape` gained a fifth `compensate_ref` rule: a given compensation step may be the `compensate_ref` target of at most one action step, tracked via a `compensation_target_claimed_by` map built during the same single pass the existing four rules already walk. An author who genuinely needs to undo two steps' effects the same way now authors two separate `step_type='compensation'` steps (even if both name the same `action_ref`) -- rejected at publish time, not discovered as a silent runtime skip. `tests/test_automation_workflows_postgres.py` gained `test_validate_graph_shape_rejects_two_action_steps_sharing_one_compensate_ref` proving the rejection directly.

**A disclosed, real scope boundary this task did not attempt to close: compensation dispatch is not crash-resumable.** `_CLAIMABLE_PREDICATE` was deliberately *not* widened to reclaim `status = 'compensating'` rows the way it already is for `'leased'`/`'running'` -- doing so correctly would need the same crash-safety rigor `run_step` itself received in Task 2's own review (a `DigestVisibilityProbeAdapter`-shaped direct proof, not merely absence-of-exception), and this task's own required test list did not name a crash-mid-compensation case. **Concrete consequence:** a worker crash while a run is `status = 'compensating'` leaves it permanently stuck -- its lease eventually expires, but no reclaim predicate ever picks it up again, requiring manual operator intervention (`docs/runbooks/PHASE-5-RECOVERY.md`'s own updated text has the full diagnostic-query guidance this task added). `activate_workflow_version` published such a graph without complaint. `API-SCHEMAS.md` already states, as an already-decided guarantee, "a workflow with an adapter that cannot be simulated (no `simulate()` implementation) is rejected at `publish` time" -- but this activation's `ActionAdapter` Protocol requires *both* `simulate()` and `execute()` on every object `AdapterRegistry.register` accepts, so there is no registered-but-`simulate()`-less adapter this activation's own contract can produce; the actual, narrower gap is an unregistered `action_ref` entirely. **Fix:** `workflows.unregistered_action_refs` (new, plain function, mirroring `validate_graph_shape`'s own "kept as a plain function" precedent) checks every `action`/`compensation` step's `action_ref` against a given `AdapterRegistry`; `activate_workflow_version` gained an **optional**, keyword-only `adapter_registry` parameter (default `None`, meaning "no check") specifically so this task's own new check does not retroactively break every pre-existing Phase 5 test module that calls `activate_workflow_version` directly with a private, test-only `AdapterRegistry()` naming test-only `action_ref`s never meant to be dispatched through the shared production registry (confirmed directly: every one of the ~13 existing call sites across `tests/test_automation_*_postgres.py` passes exactly three positional arguments, unaffected by an additional keyword-only parameter with a backward-compatible default). `publish_workflow_endpoint` -- the one real HTTP call site this task's own guarantee needs to hold for -- always passes the shared production `adapters.registry`. New error code `ACTION_REF_NOT_REGISTERED`, `422` (not `409`): a graph-content validation failure, the same status code class as `SCHEMA_INVALID`, not a lifecycle-state conflict the way `WORKFLOW_VERSION_NOT_DRAFT`/`WORKFLOW_VERSION_ACTIVE_CONFLICT` are. `simulation_only` (`API-SCHEMAS.md`'s originally-named code) is left unimplemented as its own distinct code -- this activation's Protocol makes the condition it names unreachable, so a second code for it would be redundant with `ACTION_REF_NOT_REGISTERED`, not complementary.

**`POST /automations/workflows/{id}/simulate` (`workflows.py`, new).** Walks `version.graph["steps"]` in order (`_simulate_steps`, new): `action` steps resolve the adapter via the shared production registry, resolve `input_mapping` the same verbatim-dict shape `worker._resolve_step` uses, call `adapter.simulate(action_input)` only (never `execute()`/`compensate()` -- no code path in this function can reach either), and collect `preview` (the `simulate()` output, redacted the same way a persisted step's `output` already is), `reversible`/`high_impact_categories` (the adapter's own static declarations -- API-SCHEMAS.md's own concrete realization of "declared side effects" and "requested permissions/scopes"), and `compensate_ref` (shown on the *declaring* action step's own entry, never as a separate preview -- Decision 9's compensation model, surfaced per this task's own instruction). `approval_gate`/`condition` steps are represented structurally only (`dispatch_gate = "not_applicable"`), matching `process_claimed_run`'s own main-loop skip logic for these two types. `compensation` steps are never part of the main walk at all, matching Task 6's own "reachable only through `compensate_ref`" rule. Every action step's `dispatch_gate` (`clear | requires_approval | policy_blocked | adapter_not_registered`) is computed by resolving the version's own pinned `policy_ref` and calling `approvals.evaluate_approval_requirement` -- the exact same function `worker._evaluate_dispatch_gate` calls for real dispatch -- so "every approval point the run would hit" (`API-SCHEMAS.md`, verbatim) is a genuine re-evaluation, never a separate, potentially-drifting guess. A version whose `action_ref` does not resolve (a version drafted, or hand-constructed, before this task's own publish-time check existed) degrades to `dispatch_gate = "adapter_not_registered"`/`error = "AdapterNotRegistered"` rather than a `500`.

**A deliberate, disclosed circular-import avoidance, not an oversight.** `worker.py` already imports `workflows.get_active_workflow_version`/`get_workflow_version` -- importing anything back from `worker.py` into `workflows.py` (specifically `_redact_payload`, needed to redact a `simulate()` preview the same way a persisted step's `output` is redacted, and the `WorkspaceScopeMismatch` confused-deputy check `run_step` already applies) would be a real circular import, not a hypothetical one. `workflows.py` instead carries its own small, disclosed duplicates (`_simulate_redact_payload`, `SimulateWorkspaceScopeMismatch`) -- the identical "a helper duplicated per-module to avoid an architectural problem" precedent this file's own `_request_hash`/`_lock_idempotency`/`_load_cached`/`_store_idempotency` already set relative to `runs.py`/`policy.py`/`kill_switches.py`'s independently-defined equivalents. Confirmed safe to import `.adapters`/`.policy`/`.approvals` directly into `workflows.py` (none of those three modules imports `workflows.py` or `worker.py` back) before writing any of this, not assumed.

**A deliberate, documented judgment call: `/simulate` has no `CsrfDep`/`Idempotency-Key`, even though `API-SCHEMAS.md` lists the route as a `POST`.** Every other mutating endpoint in `workflows.py` requires both because it writes a row; `/simulate` writes none, under any outcome -- proven directly by `test_simulate_never_writes_any_row` (below), not merely asserted. Kept as `POST`, not `GET`, only because the already-approved contract names a `POST`; this activation's `input_mapping` has no live templating today (`worker._resolve_step`'s own long-standing disclosure, equally true here), so the simulation is fully determined by the version's own already-pinned graph and needs no request body -- a later task adding real per-call input overrides to `/simulate` would be the natural point to reconsider this call, and add a body.

**`GET /automations/workflows/{workflow_id}/kill_switch` (`kill_switches.py`, new).** A pure read, no `CsrfDep`/`Idempotency-Key`, matching every other `GET` in this package. Response is a new `KillSwitchStatusResponse` (documented choice over reusing `KillSwitchResponse` bare, since a global and a per-workflow switch can each be independently active and `KillSwitchResponse` alone cannot express "killed by which scope"): `killed` (`True` if either scope has an active row, mirroring `is_workflow_killed`'s own OR), `active_global`/`active_workflow` (each `null` or a `KillSwitchResponse`), `history` (this workflow's own per-workflow-scope rows only, `workflow_id = workflow_id` -- deliberately never the global scope's own separate, workflow-independent history, which would be a confusing, unbounded list to embed here; the global scope's *current* state is still fully visible via `active_global`). Does not itself validate that `workflow_id` names a real `workflow_definitions` row, matching the two existing `POST` kill-switch endpoints' own identical looseness (an opaque-string scope, no FK, same precedent as `workflow_runs.workflow_id`/`automation_policies.workflow_id` elsewhere in this package).

**`compensation_steps` in `GET /automations/runs/{id}`.** `runs.py` gained `CompensationStepResponse` (mirrors `RunStepResponse`'s own shape for the sibling table exactly -- the same fields `worker.CompensationStep` carries, minus `id`/`workspace_id`/`run_id`, matching `RunStepResponse`'s own identical omissions) and `RunDetailResponse.compensation_steps: list[CompensationStepResponse]`, populated via `worker.list_compensation_steps` (existing since Task 6, never wired into this router before now -- confirmed directly, not assumed). **Judgment calls a reviewer should double-check.** (1) **`activate_workflow_version`'s new `adapter_registry` parameter defaults to `None` (no check), rather than defaulting to the shared production registry.** The safer-sounding default (always check) would have broken all ~13 pre-existing direct call sites across other tasks' own test modules, which intentionally publish workflows naming private, test-only `action_ref`s to test lifecycle behavior (locking, immutability, idempotency) unrelated to adapter registration. The real guarantee this task needs only has to hold at the one real HTTP call site (`publish_workflow_endpoint`), which always passes the registry explicitly -- a reviewer who considers "opt-in, off by default" too permissive for a plain function other future callers might invoke without realizing the check is skippable should treat tightening this as a candidate follow-up, weighed against the real cost of rewriting ~13 existing tests' own call sites. (2) **`/simulate`'s own dedicated graph-walk (`workflows._simulate_steps`), not a `dry_run=true` flag threaded through `worker.py`'s real orchestration loop**, is a disclosed divergence from the design doc's own literal Decision 4 sketch -- forced by a genuine circular-import constraint (`worker.py` already imports `workflows.py`), not a stylistic preference; functionally equivalent (no code path to `execute()`/`compensate()` either way, the identical `approvals.evaluate_approval_requirement` call either way) but a different module boundary. A reviewer who expects `/simulate` and `POST /runs` to share one literal orchestration function should note this as the concrete next step, not assume it already happened. (3) **No CSRF/idempotency-key on `/simulate`**, despite being a `POST` -- justified above; the concrete cost is that a CSRF attack could still trigger a simulation from an authenticated browser session (no state-changing consequence, but the workflow's own graph/policy structure would be visible in the response) -- a reviewer who weighs even a read-only information-disclosure surface as CSRF-relevant should treat adding `CsrfDep` back as a small, low-cost hardening step. (4) **`KillSwitchStatusResponse`'s `history` field is per-workflow-scope only, never including the global scope's own history** -- a deliberate choice (global history is not specific to any one workflow and would be unbounded/confusing embedded per-workflow); a reviewer who wants a single "everything that ever affected this workflow" view (including every global activation/deactivation, not just the currently-active one) should treat a combined or separately-`GET`-able global-history endpoint as a natural follow-up, not something this task silently decided against forever. (5) **`ACTION_REF_NOT_REGISTERED` is `422`, `simulation_only` is left unimplemented as its own code** -- both a status-code choice and an error-taxonomy choice a reviewer should confirm against `API-SCHEMAS.md`'s updated text rather than assume matches the original document's literal wording.
