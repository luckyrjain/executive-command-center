# Phase 5 API Schemas

Resolved administrative/runtime surface for this first activation (`docs/superpowers/specs/2026-07-25-phase-5-automation-design.md`):

```text
GET|POST /automations/workflows
GET /automations/workflows/{id}
POST /automations/workflows/{id}/publish|disable|simulate
GET /automations/workflows/{id}/kill_switch
GET|POST /automations/policies
POST /automations/policies/{id}/revoke
GET|POST /automations/runs
GET /automations/runs/{id}
POST /automations/runs/{id}/pause|resume|cancel
GET /automations/approvals
POST /automations/approvals/{id}/approve|reject
POST /automations/workflows/{id}/kill_switch
POST /automations/kill_switch
GET /automations/triggers
```

**`GET /automations/triggers` is a Task 7 addition**, closing a real gap found while building the frontend workflow-list/detail and "schedule controls" views against this contract: a workflow's `GET .../workflows/{id}` response exposes only `trigger_refs: list[str]` (bare reference strings, e.g. `"manual"`), never a trigger's own `schedule_expression`/`timezone`/`skip_missed`/`last_fired_at` -- there was no HTTP path at all to a trigger's own configured schedule before this task, only `triggers.list_triggers`/`get_trigger` callable from non-HTTP code (Task 1's own deliberate, disclosed scope decision). A pure read (no `CsrfDep`/`Idempotency-Key`), workspace-scoped via the caller's own `AuthContext`, optionally filtered by `workflow_id` (`?workflow_id=...`) -- mirrors `kill_switches.py`'s `GET .../kill_switch` (Task 7a) precedent exactly for router/auth/response-model conventions. Returns `{triggers: [...]}`, each entry `{id, workflow_id, trigger_type, event_type_filter, schedule_expression, timezone, skip_missed, last_fired_at, created_at, updated_at}` -- `Trigger`'s own full shape (`DATA-MODEL.md`), not a subset. Deliberately **read-only, no CRUD**: this activation's "schedule controls" need only display a workflow's own already-configured trigger(s), never author new ones from the browser -- workflow/trigger authoring remains `POST /automations/workflows`'s own `trigger_refs` field, unchanged by this task. **Workflow visibility carries over to triggers.** Trigger rows are stored `visibility = 'workspace'`, so the list filters on both the trigger row and its workflow's governing version (the active version, else the latest), the same version policy create authorizes against: a trigger of a workflow the caller cannot read is omitted, with or without `?workflow_id=`, and a family with no version hides its triggers. The check is live, so making a workflow private, transferring it or revoking a grant hides its existing triggers too. There is no single-trigger HTTP read.

**Two small, disclosed, additive response-shape gaps found and closed the same way, while building the frontend against this contract (Task 7):**

- `WorkflowSummaryResponse` (`GET /automations/workflows`) gained `latest_version_id`/`active_version_id` (each a version row's own UUID, `null` for `active_version_id` when no version is active). Before this task, the list endpoint exposed only bare version *numbers* (`latest_version`/`active_version`), giving a caller no way to link from this list into `GET /automations/workflows/{version_id}` at all -- that endpoint is addressed by a version row's own UUID, never by `(workflow_id, version)`. A pure additive field on an existing response, not a new query (the list query already loads every version row to compute `latest`/`active`).
- `RunStepResponse` (`GET /automations/runs/{id}`) gained `attempt_count` (`workflow_run_steps.attempt_count`, Task 6 -- never wired into this response before now). Needed to make the `retrying` step status legible in a UI ("attempt 2 of 3", not merely "retrying"): `worker.WorkflowRunStep` already carried this field; this is a pure response-shape addition, no new query.

**`POST /automations/workflows/{id}/kill_switch` (per-workflow) and `POST /automations/kill_switch` (global) are a Task 6 addition** to this originally-approved endpoint list -- neither existed when this document was first moved to "Approved for Implementation" (Task 0); only the `kill_switch_active` error code was named. Disclosed here explicitly, matching how prior tasks disclosed generalizations rather than silently changing an "Approved for Implementation" doc. Both are actor-authenticated, workspace-scoped, CSRF- and idempotency-key-protected, matching every other mutating Phase 5 endpoint's convention exactly. Body: `{active: bool, reason: string | null}`. `active=true` activates a switch for the named scope (idempotent -- an already-active exact scope is a no-op, no duplicate row); `active=false` deactivates it (idempotent -- no active row for that scope is also a no-op). `automation_kill_switches` (`docs/phases/phase-005/DATA-MODEL.md`) is an append-only-ish audit trail, not just current state: deactivating marks the existing active row rather than deleting it; reactivating inserts a fresh row. `ecc.domains.automation.worker.enqueue_run` (the single choke point both `POST /automations/runs` and the schedule-trigger fire path go through) rejects a killed workflow with `kill_switch_active` (`409`) before creating any `workflow_runs` row at all -- "Global/workflow kill switches stop new runs" (`PHASE-005-automation.md`'s Rollback plan, verbatim). `claim_next_run`'s own predicate additionally ensures a killed workflow's already-`queued`/lease-expired rows are never claimed or reclaimed either, matching `docs/runbooks/PHASE-5-RECOVERY.md`'s "never claimed, reclaimed, or resumed regardless of lease state."

**`GET /automations/workflows/{id}/kill_switch` is a Task 7a addition**, closing `UX-STATES.md`'s own named gap ("a future UI surfaces the workflow's own current kill-switch state ... so an operator sees *why* new runs are rejected before attempting one"). A pure read (no CSRF/idempotency-key), workspace-scoped, addressed by `workflow_id` (a string, like the two `POST` endpoints above -- not a version UUID). Returns `{workflow_id, killed, active_global, active_workflow, history}`: `killed` is `true` if *either* a global or this-exact-workflow switch is currently active (`kill_switches.is_workflow_killed`'s own "either scope" semantics); `active_global`/`active_workflow` are each either `null` or a `KillSwitchResponse`-shaped object (the same shape the two `POST` endpoints already return); `history` is this workflow's own per-workflow-scope activation/deactivation history only (never the global scope's own separate history, which is not specific to any one workflow).

`POST /automations/workflows/{id}/simulate` runs a graph-walk over `version.graph["steps"]` calling only each resolved adapter's `simulate()` -- the orchestration loop reachable from this endpoint has no code path that can call an adapter's `execute()` or `compensate()` at all. **Implemented Task 7a** (a documented divergence from the design doc's own literal sketch -- see below). The response returns, per step: the resolved adapter's own declared `preview` (its `simulate()` output, redacted the same way a persisted step's `output` is), `reversible` and `high_impact_categories` (Decision 8's static per-adapter declarations -- the concrete realization of both "declared side effects" and "requested permissions/scopes," this activation having no separate scope concept beyond the seven-category taxonomy), the step's own `compensate_ref` target if declared, the adapter's `action_type`/`data_class` and the `dispatch_value` the step's validated static input would move (what real dispatch records as `workflow_run_steps.dispatch_value`), and a `dispatch_gate` (`clear | requires_approval | policy_blocked | adapter_not_registered | input_invalid | not_applicable`) computed by re-evaluating `approvals.evaluate_policy_scope` and `approvals.evaluate_approval_requirement` against the version's own pinned policy, in the dispatch gate's own order -- the exact same policy-checking logic real dispatch uses, not a separate guess, so "every approval point the run would hit" is genuinely accurate. A `policy_blocked` step carries `policy_block_reason` (`no_policy | policy_revoked | policy_expired | action_type_not_authorized | data_class_not_authorized`; the last two from the policy-scope enforcement, `docs/superpowers/specs/2026-10-01-automation-policy-scope-enforcement-design.md`); `input_invalid` means the step's static input fails the adapter's `input_schema` (or its `dispatch_value`), with `error` naming the exception class (e.g. `ValidationError`) -- an out-of-scope step reports `policy_blocked` even when its input is also invalid, matching dispatch. `approval_gate`/`condition` steps are represented structurally (`dispatch_gate = "not_applicable"`, no adapter call); `compensation` steps are never part of the main walk (reachable only via another step's own `compensate_ref`, shown as that step's own field). A step whose `action_ref` does not resolve in the registry degrades to `dispatch_gate = "adapter_not_registered"` rather than a `500` -- defensive against a version drafted before Task 7a's own publish-time check (below) existed. Addressed by `version_id`, exactly like `publish`/`disable`; workspace-scoped and 404-isolated identically. **Divergence from the design doc's own Decision 4 sketch, disclosed:** Decision 4 describes threading a `dry_run=true` flag through the *same* orchestration loop `POST /automations/runs` uses; Task 7a instead implements simulation as its own dedicated graph-walk (`workflows._simulate_steps`), reusing `worker._resolve_step`'s exact per-step resolution *shape* (`step.get("input_mapping", {})`, verbatim) without importing `worker.py` itself, since `worker.py` already imports `workflows.py` (a real circular-import constraint, not a stylistic preference) -- functionally equivalent (no code path to `execute()`/`compensate()` either way, the same policy-evaluation function reused either way), but a different module boundary than the design doc's own text implies. A **narrower version of the publish-time guarantee than the design doc's own wording states** is what Task 7a actually enforces: "a workflow with an adapter that cannot be simulated (no `simulate()` implementation) is rejected at `publish` time" is, mechanically, "a workflow whose `action_ref` does not resolve in the adapter registry at all is rejected at `publish` time" -- every adapter the registry accepts already implements both `simulate()` and `execute()` (the `ActionAdapter` Protocol requires both), so there is no registered-but-`simulate()`-less adapter this activation's own contract can produce; the only way a step's adapter "cannot be simulated" is if it does not resolve in the registry at all. See the new `ACTION_REF_NOT_REGISTERED` error code below.

`POST /automations/approvals/{id}/approve` requires the caller to echo the exact `action_digest` the approval request names (design doc Decision 3/Threat model) -- an approval whose digest does not match the step's current resolved input is rejected as `digest_mismatch`, never silently accepted against a since-changed step. This is the mechanical enforcement of the acceptance criterion "unauthorized, expired, changed or replayed approvals are rejected."

`POST /automations/runs/{id}/cancel` blocks the run's next not-yet-started step from being dispatched (matching the phase NFR verbatim: "Revocation blocks the next not-yet-started side effect") -- it does not attempt to interrupt a step already dispatched to its adapter's `execute()` mid-flight, since that guarantee cannot be made for an arbitrary adapter (design doc Decision 6). `pause`/`resume` behave identically for suspension/continuation without terminating the run.

**`GET|POST /automations/policies` scope fields are enforced** (`docs/superpowers/specs/2026-10-01-automation-policy-scope-enforcement-design.md`). `POST` refuses an empty or unknown scope with `422`: `POLICY_SCOPE_EMPTY` (no action type or no data class -- an empty scope would authorize nothing) or `POLICY_SCOPE_UNKNOWN_VALUE` (a value outside `adapter_contract.ACTION_TYPES` -- `note.create | notification.send | comment.create | fake.external` -- or `DATA_CLASSES` -- `public | internal | sensitive | restricted`), each with detail `{code, field, values, allowed}` (`field` is `action_types` or `data_classes`). `PolicyResponse` gained `scope_enforced`: `true` for every policy created now, `false` for a legacy row created before migration `0086`, whose `action_types`/`data_classes` are not checked until it expires (at most 90 days). For an enforced policy an adapter is in scope when its `action_type` is listed and its `data_class` ranks at or below the highest listed class; `value_limit` is compared per run against the summed `dispatch_value` (an approval requirement, `policy-limit-exceeding`, never an HTTP rejection). Full rules: `APPROVAL-POLICY.md`'s "Scope enforcement" section and `policy.py`'s module docstring.

**`GET /automations/adapters`** (scope-enforcement design, Decision 5) returns every registered action adapter's static declarations plus the scope vocabularies, so the policy UI offers closed choices instead of free text: `{adapters: [{adapter_id, action_type, data_class, reversible, high_impact_categories, has_dispatch_value}], action_types, data_classes}`, `data_classes` ordered by ascending sensitivity (a policy names a ceiling). A pure read requiring an active membership; the registry is process-global, so it returns no workspace data.

**`GET /automations/runs` and `GET /automations/runs/{id}` can return `status = "preview_blocked"`** (`DATA-MODEL.md`'s run-state vocabulary, added with the `preview_only` dispatch-block fix). A terminal, non-error status: the run's policy is in `preview_only` mode, so every step was gated, any approval was recorded for real, and no adapter was ever executed. Clients must not present it as a failure or as an operator-actionable review state; `?status=preview_blocked` filters for it like any other value.

`GET /automations/runs/{id}` exposes step state and redacted evidence (`workflow_run_steps.input`/`output`, redacted per `DATA-MODEL.md`) -- raw adapter payloads containing resolved secret values are never returned by any endpoint, matching `secret_references`' opaque-handle design.

Every endpoint that creates or mutates a `workflow_runs`/`approval_requests`/`automation_policies` row is resolved server-side against the actor's own workspace and the policy already bound to the target workflow -- no endpoint accepts a caller-supplied `policy_id` override for an existing workflow, closing the confused-deputy path the design doc's Threat model section names (a request can ask "run workflow X," never "run workflow X under policy Y").

**`POST /automations/workflows` against an existing `workflow_id` is an edit of that workflow, and is authorized as one.** The caller must be able to read the family's latest version and its active version (if any), else `404 WORKFLOW_NOT_FOUND`, and to write both, else `403 INSUFFICIENT_ROLE`. All read checks run before any write check, so a family with any version the caller cannot see answers the same `404` an unknown version id does, and the response never carries the next version number. Only the fact that the slug is taken leaks; `workflow_id` is unique per workspace, so that bit is inherent. A `policy_ref` the caller cannot see (the policy and its workflow's governing version must both be readable, as for `GET /automations/policies` below) answers `404 POLICY_NOT_FOUND`, the same as one that does not exist. `POST /automations/workflows/{id}/publish` additionally requires read and write on the active version it would retire, else `403 INSUFFICIENT_ROLE` (not `404`: the caller can see the draft, so the family's existence is already known). All of these run under the row locks and before the idempotency cache, so a same-key replay is re-authorized (ADR-0014).

Idempotency, session-derived identity, audit redaction and 404 isolation apply, matching every existing Phase 1-4 endpoint convention.

**Workflow visibility carries over to policies and runs.** `POST /automations/policies` needs `read` then `write` on the workflow's active version, or its latest version when none is active: a workflow the caller cannot read answers `404 WORKFLOW_NOT_FOUND`, exactly as for an id that never existed, and one they can read but not write answers `403 INSUFFICIENT_ROLE`. A run is visible only while both the run and the `workflow_versions` row it is pinned to (`workflow_id` + `workflow_version`) are readable: `GET /automations/runs` filters on both, and `GET /automations/runs/{id}`, `cancel`, `pause` and `resume` answer `404 RUN_NOT_FOUND` otherwise. Changing a run (`cancel`, `pause`, `resume`) also needs `write` on the pinned version, and so does deciding one of its approvals (`approve`/`reject`), so a read-only grantee on a workflow sees its runs and approvals but gets `403 INSUFFICIENT_ROLE` changing them. This applies to the run's own starter too: a starter whose access to the workflow drops to read can no longer cancel their run. With `require_distinct_approver` on, an approver on a `shared_explicitly` workflow therefore needs a write grant on it; a read-only reviewer grant is not enough. The check is live, so making a workflow private, transferring it or revoking a grant hides its existing runs too, including scheduled runs and runs the caller started. An approval request is visible only while its run is: `GET /automations/approvals` filters on the request, its run and the run's pinned version, and `approve`/`reject` answer `404 APPROVAL_NOT_FOUND` otherwise, checked before a same-key replay is served from the idempotency cache. Policies follow the same version policy create authorizes against: a policy is visible only while both the policy row and its workflow's active version (else latest version) are readable. `GET /automations/policies` filters on both (a family with no version hides its policies), and `POST /automations/policies/{id}/revoke` answers `404 POLICY_NOT_FOUND` otherwise, exactly as for an id that never existed, then needs `write` on both (`403 INSUFFICIENT_ROLE`), since unbinding a policy is authority over the workflow just as binding one is. This check is live too.

## Errors

Required codes: `schema_invalid` (a run/policy/trigger payload failing its Pydantic contract), `workflow_not_active` (target workflow has no `active` version; `POST /automations/runs` returns it only when the caller can read some version of the workflow -- an id the caller cannot see, or that never existed, is `404 WORKFLOW_NOT_FOUND`, and running one needs `read` then `write` on the active version, `404`/`403`), `policy_expired`, `policy_revoked`, `rate_limited` (design doc Decision 6's per-policy runs/hour ceiling -- **now real**: `POST /automations/runs` returns `409 RATE_LIMITED` with `{workflow_id, limit, runs_in_window}` when `worker.enqueue_run` rejects a run that would exceed the authorizing policy's own `rate_limit.runs_per_workflow_per_hour`, before creating any `workflow_runs` row, exactly like `workflow_not_active`/`kill_switch_active`. The *value/count* half of Decision 6's wording is not part of this code: `count_limit` surfaces as a per-run approval requirement (`policy-limit-exceeding`), never as an HTTP rejection, and so does `value_limit` (per run, against the summed `dispatch_value`) -- see `APPROVAL-POLICY.md`'s "Scope enforcement" section), `digest_mismatch` (an approval's digest does not match the step's current resolved input), `approval_expired` (24-hour unresponded window elapsed), `simulation_only` (an adapter without a `simulate()` implementation attempted at `publish`), `kill_switch_active` (a global or per-workflow kill switch blocks dispatch, `docs/runbooks/PHASE-5-RECOVERY.md` -- implemented Task 6: `POST /automations/runs` returns this `409` when `enqueue_run` rejects a killed workflow).

**`ACTION_REF_NOT_REGISTERED` (`422`) is a Task 7a addition**, resolving `simulation_only`'s own guarantee for the case that actually exists in this activation (see the `/simulate` paragraph above for the full "narrower than the doc's literal wording" reasoning). `POST /automations/workflows/{id}/publish` returns it when any `action`/`compensation` step's `action_ref` does not resolve in the shared production adapter registry -- `422`, not `409`, matching `SCHEMA_INVALID`'s own status code: this is a graph-content validation failure (the payload itself is unpublishable), not a conflict about the target row's own lifecycle state the way `WORKFLOW_VERSION_NOT_DRAFT`/`WORKFLOW_VERSION_ACTIVE_CONFLICT` are. `simulation_only` itself remains unimplemented as its own distinct code -- this activation's `ActionAdapter` Protocol makes it unreachable (every registered adapter has both `simulate()` and `execute()`), so `ACTION_REF_NOT_REGISTERED` is the one real check this activation needs, not a second, additional code for a condition the Protocol already forecloses.

**`COMPENSATION_ACTION_REF_HIGH_IMPACT` (`422`) is the publish-time half of the compensation-authorization fix** (`EXECUTION-CONTRACT.md`'s "Authorized, for a compensation step specifically" note; `APPROVAL-POLICY.md`'s high-impact taxonomy). `POST /automations/workflows/{id}/publish` returns it when a `step_type='compensation'` step's own `action_ref` resolves, in the shared production adapter registry, to an adapter declaring any non-empty `high_impact_categories` -- such an adapter "always requires per-run approval regardless of policy mode," and the worker's compensation-dispatch path structurally cannot create an approval request (a rollback has no approval-inbox surface to wait in), so the graph is refused rather than the invariant being silently dropped at rollback time. Same `422` and same `{workflow_id, version, violations}` detail shape as `ACTION_REF_NOT_REGISTERED` above, for the same "the submitted graph itself is unpublishable" reason, but a deliberately distinct code: the remedy differs (register the adapter / fix the typo, versus this action may not be used as a rollback at all), and it additionally carries an explicit `message` so a client with no branch for this code still renders a readable sentence. Checked strictly after `ACTION_REF_NOT_REGISTERED`, so an `action_ref` that resolves to nothing at all is always reported under that code rather than depending on check ordering.

**`ACTION_REF_OUTSIDE_POLICY_SCOPE` (`422`)** (scope-enforcement design, Decision 5): `POST /automations/workflows/{id}/publish` returns it when any `action`/`compensation` step's registered adapter is outside the version's own `policy_ref` scope (`approvals.evaluate_policy_scope`). Detail `{code, message, workflow_id, version, violations}`, each violation `{step_id, action_ref, reason}` with `reason` `action_type_not_authorized | data_class_not_authorized`. Checked after `COMPENSATION_ACTION_REF_HIGH_IMPACT`, and skipped when there is no `policy_ref` or the policy is legacy (`scope_enforced = false`), revoked or expired -- those block at dispatch with their own reasons. A compensation step is checked unconditionally, stricter than dispatch. Publish catches authoring errors early; the dispatch gate stays authoritative, blocking an out-of-scope step to `needs_review` with an `automation.step_blocked` audit event. `GET /automations/runs/{id}` then returns `scope_block: {step_index, reason}` (null otherwise) while the run is `needs_review`, read from that audit row, since a scope block writes no step row.

`POLICY_SCOPE_EMPTY` / `POLICY_SCOPE_UNKNOWN_VALUE` (`422`, `POST /automations/policies`): see the policies paragraph above.
