# Phase 5 UX States

Primary surfaces: workflow builder, simulation, policy review, approval inbox and run history. Clearly distinguish proposed, approved, active, paused and revoked. Show next scheduled run, authority scope and side effects.

Required states include waiting approval, expired approval, policy revoked, paused, retrying, unknown external outcome, partially compensated and kill switch active -- mapped directly to `DATA-MODEL.md`'s resolved run/step states (`waiting_approval`, `expired`, `needs_review`/`unknown`, `compensation_failed`, `rate_limited`). A run in `needs_review` (an `unknown` step outcome, `EXECUTION-CONTRACT.md`) surfaces as a distinct, non-dismissible state requiring the operator to inspect the target system and explicitly resolve it (`docs/runbooks/PHASE-5-RECOVERY.md`'s "What an operator does" section) -- it is never presented as a transient/retrying state, since automatic resolution is exactly what this state exists to prevent.

**Wiring notes, Task 6 (backend now real; this remains a backend-only task -- no frontend surface ships here, per its own scope boundary).** "Retrying" is realized as a `queued` run whose *current step's own row* shows `workflow_run_steps.status = 'retrying'` (`attempt_count`/`error_class` visible via `GET /automations/runs/{id}`'s step detail) -- there is no run-level `'retrying'` status (`DATA-MODEL.md`). "Partially compensated" is realized as a run in `compensation_failed` whose `compensation_steps` ledger shows a mix of `succeeded`/`failed` rows -- exactly the acceptance criterion "partial compensation is visible and recoverable." "Kill switch active" is realized as: a `needs_review` run (a kill switch discovered mid-dispatch, `process_claimed_run`'s per-step check) plus, separately, a `409 kill_switch_active` response from `POST /automations/runs` for any *new* run attempt against a killed workflow.

**Wiring notes, Task 7a (backend now real; still backend-only -- no frontend surface ships here, a later task builds against these three endpoints).** Both gaps Task 6 left named above are now closed by real endpoints, not only a direct DB read: "partially compensated" is `GET`-able via `RunDetailResponse.compensation_steps` (`GET /automations/runs/{id}`, `worker.list_compensation_steps` wired into `runs.py`) rather than `list_compensation_steps` called from non-HTTP code only; "kill switch active" is `GET`-able via `GET /automations/workflows/{id}/kill_switch` (current effective state -- global/per-workflow -- plus this workflow's own history) rather than `kill_switches.list_kill_switches` called from non-HTTP code only, so a future UI can genuinely show an operator *why* new runs are rejected before attempting one, not only after. **Simulation** (`API-SCHEMAS.md`'s `/simulate`, this section's own next paragraph) is also now real: `POST /automations/workflows/{id}/simulate` returns, per step, the adapter's declared preview/`reversible`/`high_impact_categories`, the step's own `compensate_ref` target if any, and a `dispatch_gate` genuinely re-evaluated against the version's own pinned policy -- the data a "simulation results are visually distinct from real run history" UI (this section's next paragraph) would render against.

Destructive/high-impact approvals (`APPROVAL-POLICY.md`'s taxonomy) require deliberate confirmation: the exact target, payload summary, high-impact category, reversible status and expiry are shown before the approve action is reachable, and the approval UI never pre-fills or auto-submits a decision. Simulation results (`API-SCHEMAS.md`'s `/simulate`) are visually distinct from real run history at every surface -- a simulated run can never be mistaken for one that produced real side effects, matching the acceptance criterion "simulation never causes side effects" being visible, not just true.

All flows are keyboard accessible and meet WCAG 2.2 AA.

**Wiring notes, Task 7 (the frontend surface itself, `frontend/src/features/automation/`, now real -- this is the task the "no frontend surface ships here" notes above were deferring to).** Every state this document names maps to a real, rendered UI state, not a placeholder:

- **Waiting approval / expired approval**: `RunWorkspace.tsx`'s `RunDetailView` renders `waiting_approval` with its own plain-language description; `ApprovalInbox.tsx` computes expiry client-side the same way `approvals.approval_lifecycle_status` does server-side and disables both Approve/Reject once expired, additionally handling the server's own `APPROVAL_EXPIRED`/`APPROVAL_ALREADY_DECIDED`/`DIGEST_MISMATCH` responses as distinct, specific messages -- never a generic error string.
- **Policy revoked**: `PolicyPanel.tsx` shows `status`/`revoked_at` directly; `RunDetailView`'s own `needs_review` handling cross-references the run's own `policy_id` against the policy list and names "this run's own policy is currently revoked" as the strongest available, directly attributable cause when true.
- **Paused**: `RunDetailView` offers Pause/Resume per `RUN_NOT_PAUSED`'s own error surface, mapped to a readable message.
- **Retrying**: realized exactly as this document's own "Wiring notes, Task 6" paragraph specifies -- a step-level `RunStepResponse.status === 'retrying'` badge (`RunDetailView`'s per-step list), now additionally showing `attempt_count` (a Task 7 response-shape addition, `API-SCHEMAS.md`) as "attempt N of 3" -- the run's own status line is never shown as "retrying" (there is no such run-level status; `RunDetailView`'s own status line always reads the run's real status, e.g. `queued`, alongside the step-level retrying badge).
- **Unknown external outcome / needs_review**: rendered as a distinct, non-dismissible `role="alert"` block (`RunDetailView`) that inspects every corroborating signal actually available -- the run's own policy status, current kill-switch state for the workflow, and the last dispatched step's own `unknown` status -- surfacing whichever is directly attributable, or an honest "no further cause is determinable from data available to this view" when none is. This activation's data model does not record *which* of these caused a given `needs_review` transition (no dedicated reason column, `worker.py`'s own design) -- Task 7 does not fabricate a distinction the data can't support; the UI shows what is knowable and states plainly when the cause is not determinable.
- **Partially compensated**: `RunDetailView` renders `compensation_steps` as an explicit ledger; a `compensation_failed` run whose ledger mixes `succeeded`/`failed` rows is labeled "Partially compensated" specifically (distinct from a `compensation_failed` run whose ledger is uniformly failed).
- **Kill switch active**: `WorkflowDetail.tsx` shows a workflow's own current kill-switch state (via Task 7a's `GET .../kill_switch`, now wired into the frontend for the first time) *before* a user would attempt a new run against it -- not only discovered via a `409 KILL_SWITCH_ACTIVE` after trying, though that response is also handled with a specific, readable message (`RunWorkspace.tsx`). `KillSwitchPanel.tsx` is the administrative surface for global control and for checking/toggling any workflow_id without first navigating to its own detail view.

**A UX-STATES.md requirement the backend cannot fully support, disclosed rather than fabricated (Task 7):** "reversible status ... shown before the approve action is reachable." No run/approval endpoint in this activation exposes a step's adapter-declared `reversible` flag -- only `POST /workflows/{id}/simulate` does, and only for a workflow *version* addressable by its own UUID, which a `workflow_runs` row does not itself carry (only `workflow_id` plus a bare `workflow_version` integer). `ApprovalInbox.tsx`'s `ApprovalCard` states this limitation directly to the approver ("Reversibility is not exposed at this decision surface by this activation's data model -- check the workflow's Simulate view...") rather than omitting the requirement silently or guessing a value. A reviewer who considers this gap worth closing should treat threading a step's own `reversible` declaration through to `RunStepResponse`/`ApprovalResponse` (mirroring this same task's `attempt_count` addition) as the natural, small follow-up.
