# Phase 5 Data Model

Concrete shape for this first activation, resolved by `docs/superpowers/specs/2026-07-25-phase-5-automation-design.md` (Decisions 1-10) and `docs/adr/ADR-0013-durable-workflow-execution.md`. Every table is workspace scoped, matching every existing Phase 1-4 migration.

| Record | Purpose | Key fields | Resolved for this activation |
|---|---|---|---|
| `workflow_definitions` / `workflow_versions` | Immutable typed workflow graph | `workflow_id`, `version`, `graph`, `definition_hash`, `status` | `definition_hash` is `sha256` over `{graph, trigger_refs, policy_ref}`, reusing Phase 4's `prompt_versions` immutability mechanism exactly: a PostgreSQL trigger rejects `UPDATE` of `graph`/`definition_hash` once `status <> 'draft'`; exactly one `active` version per `workflow_id` via a partial unique index (design doc Decision 2). `graph` is a finite, acyclic, strictly sequential ordered list of steps (`step_id`, `step_type` in `action\|approval_gate\|condition\|compensation`, `action_ref`, `input_mapping`, `on_success`, `on_failure`, `compensate_ref`) -- no loops, no parallel fan-out in this activation (Decision 10). **`compensate_ref` (Task 6):** added to the step schema this same task -- a real, disclosed gap between migration `0039`'s own docstring (which already referred to `compensate_ref` as an existing precedent) and Decision 9 (which requires it) on one hand, and `workflows.py`'s actual `WorkflowStepModel`, which lacked the field entirely, on the other. Valid only on a `step_type='action'` step, must resolve to a `step_type='compensation'` step in the same graph; a `compensation` step may never be an `on_success`/`on_failure` target and may never itself declare a `compensate_ref` (`workflows.validate_graph_shape`, Task 6). |
| `automation_policies` | Approved scope, limits, expiry and revocation | `workflow_id`, `action_types`, `data_classes`, `value_limit`, `count_limit`, `rate_limit`, `schedule`, `approval_mode`, `expires_at`, `revoked_at` | `approval_mode` in `preview_only\|per_run\|bounded_recurring` (existing skeleton, retained). `value_limit`/`count_limit` are required, non-nullable -- no system-wide default (design doc Decision 6); a policy author must set both explicitly. `expires_at` defaults to 90 days from creation/last renewal; `revoked_at` set immediately on revocation and checked before every not-yet-started step's dispatch (Decision 6). **Which of these columns are live controls:** `approval_mode` (per-step approval requirement, plus `preview_only`'s own dispatch block), `expires_at`/`revoked_at` (usability, before every step), `count_limit` (`policy-limit-exceeding`, per run) and `rate_limit` (`runs_per_workflow_per_hour`, enforced at enqueue -- `worker.enqueue_run`) are enforced; `action_types`, `data_classes` and `value_limit` are **stored and returned only, never compared against a dispatching adapter** (accepted limitation, full reasoning in `APPROVAL-POLICY.md`), and `schedule` is descriptive -- schedule authority is evaluated from the `triggers` row, not this column. |
| `triggers` | Event, manual or schedule configuration | `workflow_id`, `trigger_type`, `event_type_filter`, `schedule_expression`, `timezone`, `skip_missed` | `trigger_type` in `manual\|event\|schedule` (Decision 7). `timezone` is a required IANA zone name for `schedule` triggers -- never inferred from server-local time. `skip_missed` (bool, default `false`) governs misfire behavior: `false` fires at most once on recovery after a missed window (catch-up-once), `true` skips entirely. `event_type_filter` matches against the existing durable event-bus contract (`ADR-0005`) -- Phase 5 subscribes as a consumer, no new pub/sub mechanism. |
| `workflow_runs` | Durable run state, lease and correlation | `id`, `workflow_id`, `workflow_version`, `policy_id`, `trigger_ref`, `status`, `current_step_index`, `leased_by`, `leased_until`, `lease_heartbeat_at`, `next_attempt_at`, `queued_at`, `started_at`, `finished_at` | Lease/claim mechanism per design doc Decision 3: single-statement compare-and-swap `UPDATE ... WHERE status='queued' OR (status='leased' AND leased_until < now()) RETURNING *`. 2s poll interval, 30s lease duration, 10s heartbeat while a step actively executes. `status` values below. **`next_attempt_at` (Task 6):** the bounded-retry gate -- `NULL` unless a step most recently raised a classified-transient error, in which case it holds the timestamp before which `claim_next_run` must not reclaim this run (released back to `'queued'` in the meantime, exactly like `waiting_approval`/`needs_review`). There is no new `'retrying'` run-status value -- a retry-pending run is an ordinary `'queued'` row; see `workflow_run_steps.status` below for where "retrying" is actually recorded. |
| `workflow_run_steps` | Attempt, idempotency key, status and redacted result | `run_id`, `step_index`, `step_type`, `status`, `action_digest`, `attempt_count`, `input` (redacted), `output` (redacted), `started_at`, `finished_at`, `error_class` | `action_digest` is `sha256` over `{workflow_id, workflow_version, step_id, resolved_input}`, persisted **before** the adapter's `execute()` is called (Decision 3) -- the mechanical enforcement of `EXECUTION-CONTRACT.md`'s "the worker persists state before and after each side effect." A step recorded `succeeded`/`in_progress` with a given digest is never re-dispatched under that same digest. `step_type='compensation'` rows are distinct rows from the step they compensate (Decision 9), never folded into the original step's record. **`attempt_count` (Task 6):** `0` unless this step has ever raised a classified `TransientAdapterError`; incremented each time it transitions to `status='retrying'` (bounded by `MAX_RETRY_ATTEMPTS = 3`, exponential backoff `2 ** attempt_count` seconds -- 2s/4s/8s). |
| `approval_requests` | Requested action, impact, expiry and decision | `run_id`, `step_index`, `action_digest`, `high_impact_categories`, `requested_at`, `expires_at`, `decided_at`, `decision`, `decided_by` | Bound to the exact `action_digest` it approves (Decision 3/Threat model) -- a changed digest invalidates any prior approval for that step. `expires_at` defaults to 24 hours from `requested_at`; unresponded requests auto-expire to `expired`, never implicitly approved. |
| `compensation_steps` | Explicit recovery action/state | `run_id`, `compensates_step_index`, `action_digest`, `status` | Only created when a workflow's own `graph` explicitly declares a `compensate_ref` for a step on the failing path (Decision 9) -- never automatic. Dispatched through the identical lease/claim/idempotency mechanics as any other step; a compensation that itself fails surfaces the run as `compensation_failed`, not an indefinite auto-retry. **Implemented Task 6** (reserved, unpopulated by every prior task): dispatched in descending original-step-index order (most-recently-succeeded first, standard saga rollback order) by `ecc.domains.automation.worker._run_compensation_sequence`; a distinct row from the compensation step's own `workflow_run_steps` row (that row records the step's own dispatch; this row records the *relationship* -- which earlier step, by index, it undoes). **Exposed via `GET /automations/runs/{id}` since Task 7a** (`RunDetailResponse.compensation_steps`, `worker.list_compensation_steps` wired into `runs.py` for the first time) -- previously readable only via a direct DB read or a call to `list_compensation_steps` from non-HTTP code, matching `UX-STATES.md`'s own now-closed "partially compensated" gap. |
| `automation_kill_switches` | Global/per-workflow kill switch, audit trail | `id`, `workspace_id`, `workflow_id` (nullable -- `NULL` = global), `active`, `reason`, `activated_by`, `activated_at`, `deactivated_by`, `deactivated_at` | **Implemented Task 6** -- named by `PHASE-005-automation.md`'s Rollback plan and `docs/runbooks/PHASE-5-RECOVERY.md`'s "Kill switches" section since Task 0, but no table existed before this task. Append-only-ish: deactivating sets `active=false`/`deactivated_at`/`deactivated_by` on the existing active row rather than deleting it; reactivating inserts a fresh row, so the table is a real history, not only current state. Two partial unique indexes (mirroring `workflow_versions`' own "exactly one active version" mechanism) enforce at most one active row per scope: `(workspace_id) WHERE workflow_id IS NULL AND active` (global) and `(workspace_id, workflow_id) WHERE active` (per-workflow). `worker._CLAIMABLE_PREDICATE` checks both scopes via correlated `NOT EXISTS` subqueries; `worker.enqueue_run` checks before creating any row at all. **Readable via `GET /automations/workflows/{id}/kill_switch` since Task 7a** -- current effective state (global/per-workflow) plus this workflow's own per-workflow-scope history, closing `UX-STATES.md`'s own "not yet its own endpoint" gap. |
| `secret_references` | Opaque reference; never secret value | `reference_id`, `provider`, `scope` | Resolved only at the moment of adapter `execute()`; never rendered into `workflow_run_steps.input`/`output` (Threat model: secret leakage). |
| `notifications` | Delivery state for run events | `run_id`, `event_type`, `delivered_at`, `channel` | Existing skeleton, retained unchanged -- notification delivery itself is not a Phase 5 approval-gate item. |

## Run and step states (resolved)

`workflow_runs.status`: `queued \| leased \| running \| waiting_approval \| paused \| needs_review \| succeeded \| failed \| cancelled \| compensating \| compensated \| compensation_failed \| expired \| rate_limited \| preview_blocked`. `needs_review` holds a run when an external outcome cannot be classified as success or transient failure (an `unknown` step outcome, design doc Decision 3) and blocks automatic progression until a human resolves it -- the same terminal-until-human-action state a recovered-but-ambiguous step produces (`docs/runbooks/PHASE-5-RECOVERY.md`).

**`preview_blocked` (migration `0043`)** is the terminal state of a run whose policy is in `preview_only` mode: every action step was gated, any approval was created and decided for real, and no step ever dispatched -- `preview_only` never authorizes a real side effect (`APPROVAL-POLICY.md`). It is deliberately distinct from `needs_review` (nothing is broken or ambiguous, and no operator action could let this run proceed -- an operator sent to investigate it would find nothing to fix) and from `failed`/`cancelled` (nothing failed; nobody cancelled). Terminal in the strict sense the other terminal statuses are: `finished_at` is stamped, the lease is released, and `worker._CLAIMABLE_PREDICATE` never picks the row up again -- correct here because a run pins its `policy_id` at enqueue time and `automation_policies` has no update path (create and revoke only), so no reachable state change could ever make this run dispatchable. **No new `workflow_run_steps.status` value accompanies it:** a preview-blocked step writes no step row at all, the same discipline every other blocked dispatch outcome follows (`StepBlockedByPolicy`/`StepAwaitingApproval`), which is what lets a later re-evaluation of the same step re-run the gate from scratch. `rate_limited`, by contrast, remains a *reserved* run-status value that no code path writes: enqueue-time rate limiting rejects before any `workflow_runs` row exists (surfacing as the `rate_limited` **error code**, `API-SCHEMAS.md`), matching how `workflow_not_active`/`kill_switch_active` also reject without creating a row.

`workflow_run_steps.status`: `pending \| dispatched \| succeeded \| failed \| unknown \| skipped \| retrying`. `unknown` is the recovery-ambiguity outcome above, distinct from `failed` -- a `failed` step's side effect definitely did not (fully) happen; an `unknown` step's side effect may or may not have happened and requires human confirmation before the run can proceed. `retrying` (Task 6) is a step whose adapter raised a classified-transient error (`TransientAdapterError`) and has not yet exhausted `MAX_RETRY_ATTEMPTS` -- distinct from both `failed` (this step's side effect definitely did not occur *and* no further automatic attempt will be made) and `unknown` (ambiguous, requires a human): `retrying` is unambiguous and automatic, bounded by a fixed attempt count and exponential backoff, never indefinite.

## Immutability, idempotency and versioning (resolved)

Workflow definitions are immutable after activation, enforced by a database trigger (not only application code), identical in mechanism to Phase 4's `prompt_versions`/`tool_definitions` trigger. Every `action_digest` is computed and persisted before the corresponding side effect executes, never after (design doc Decision 3) -- the mechanism that makes "at most one effect under crash/retry" (the phase's own non-functional requirement) a property of the schema, not merely of careful application code. Secrets are never stored as values anywhere in this data model, only as opaque `secret_references` rows resolved at the point of use.
