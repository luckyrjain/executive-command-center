# Durable Execution Contract

Workflow graphs are finite, acyclic and versioned (`docs/superpowers/specs/2026-07-25-phase-5-automation-design.md` Decision 2) -- no loops, no parallel fan-out in this first activation (Decision 10). The worker persists state before and after each side effect: a step's `action_digest` (`sha256` over `{workflow_id, workflow_version, step_id, resolved_input}`) is written before the corresponding action adapter's `execute()` is invoked, and the step's terminal outcome is written immediately after (Decision 3). A stable action digest and idempotency key prevent duplicate execution -- a step already recorded `succeeded` or `in_progress` under a given digest is never re-dispatched by any worker that subsequently claims the run.

## Lease and recovery

Durable execution is implemented as a PostgreSQL-backed lease/claim worker (`docs/adr/ADR-0013-durable-workflow-execution.md`), not a distributed workflow engine, for this first activation. A `workflow_runs` row is claimed via a single-statement compare-and-swap `UPDATE ... WHERE status='queued' OR (status='leased' AND leased_until < now()) RETURNING *`. Lease duration is 30 seconds, renewed by a heartbeat (`renew_lease`) as each step is dispatched; a lease that goes 30 seconds without a heartbeat is presumed abandoned (worker crash) and is reclaimable by any live worker's next poll (2-second interval). **Stated precisely, because the difference is observable:** `HEARTBEAT_INTERVAL_SECONDS = 10` is a declared constant that drives no timer, so a single adapter `execute()` call lasting longer than the lease is not heartbeated while in flight and its run does become reclaimable mid-step. That is bounded, not unsafe -- the reclaiming worker never re-dispatches a step already recorded under its `action_digest`, and every run-state write carries a `leased_by` ownership predicate (`worker._write_owned_run_state`) so the displaced worker cannot write to a run it no longer owns. Wrapping a slow `execute()` in a timer that calls `renew_lease` every 10 seconds is the disclosed follow-up (`IMPLEMENTATION-STATUS.md`'s Task 2 judgment call 2, `ADR-0013`). **Restart resumes from the last durable checkpoint** -- this is the same lease-expiry reclaim path that handles a single worker crashing mid-step, not a separate recovery code path (`docs/runbooks/PHASE-5-RECOVERY.md`).

## Retries, unknown outcomes, cancellation, compensation

Retries use bounded exponential backoff only for classified transient failures (connection error, timeout) -- never for a step whose side effect may have already partially occurred. **Unknown external outcomes move to `needs_review` (run) / `unknown` (step); they are not blindly retried.** A crash between digest-persisted and adapter-confirmed-complete is exactly this case: ambiguous, surfaced for human resolution, never guessed at automatically (`docs/runbooks/PHASE-5-RECOVERY.md`'s "What an operator does" section).

Parallel branches and their join semantics are explicitly out of scope for this activation (design doc Decision 10) -- every workflow graph is strictly sequential, so there is no join to specify.

Cancellation stops before the next side effect: a not-yet-dispatched step is guaranteed never to dispatch once cancellation is recorded; a step already dispatched to its adapter completes (or reaches `unknown`) rather than being force-interrupted, since interrupt-mid-`execute()` cannot be guaranteed for an arbitrary adapter.

Compensation executes only declared, authorized steps and records partial recovery: a `compensate_ref` runs only when the workflow's own graph marks a step as requiring compensation on a specific failure path (never automatic or inferred), dispatches through the identical lease/claim/idempotency mechanics as any other step, and is recorded as its own `step_type='compensation'` row distinct from the step it compensates. A compensation that itself fails surfaces the run as `compensation_failed` for human review rather than retrying indefinitely.

**"Authorized," for a compensation step specifically, means two things -- and neither was mechanically enforced before this activation's compensation-authorization fix.** A compensation step is dispatched by the worker's own rollback path, which deliberately does *not* create a per-run approval request (there is no approval-inbox surface for a compensation step to wait in, and parking a rollback in `waiting_approval` would leave the run's effects half-undone indefinitely). Both halves of "authorized" are therefore enforced elsewhere:

1. **A `step_type='compensation'` step may never name an adapter that declares any `high_impact_categories`** (`APPROVAL-POLICY.md`'s taxonomy -- those "always require per-run approval regardless of policy mode," which compensation dispatch cannot provide). This is rejected at **publish** time, not at dispatch time: a graph whose compensation step names such an adapter is refused with `422 COMPENSATION_ACTION_REF_HIGH_IMPACT` and never activates, so no run can reach that dispatch at all. Fail-closed by construction, for every adapter that will ever be registered.
2. **The authorizing policy is re-checked immediately before each compensation step's adapter is invoked.** A compensation step is a not-yet-started step until that moment, so `APPROVAL-POLICY.md`'s "revocation takes effect immediately for any not-yet-started step" applies to it in full: a policy revoked, expired or missing at that instant blocks the compensation, which is recorded `failed` with `error_class='PolicyUnusableDuringCompensation'` in both `workflow_run_steps` and the `compensation_steps` ledger, without the adapter being called. Every remaining qualifying compensation is still attempted and recorded (compensation never stops early), and the run ends `compensation_failed` -- so an operator sees, per step, that the rollback did not happen and why.
