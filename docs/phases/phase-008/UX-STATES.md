# Phase 8 UX States

Surfaces: workspace switcher, members/invitations, sharing review, delegation inbox, shared activity and removal/transfer. Always show current workspace, visibility and accountable owner.

Required states: invitation expired, membership pending/suspended, permission changed, access revoked, delegation awaiting acceptance, ownership conflict and member removal blocked. Sharing previews exactly what becomes visible. Destructive removal and broad grants require deliberate confirmation. WCAG 2.2 AA applies.

## Task 9 status: complete

**No actual frontend code existed for any of Phase 8's surfaces before this task** -- Tasks 1-8 were backend-only (`SharingReview.tsx`, Task 5's own component, existed but was never wired into an app shell; `IMPLEMENTATION-STATUS.md`'s own line: "not yet wired into an app shell -- that's Task 9"). `frontend/src/features/collaboration/` implements one tabbed `CollaborationWorkspace` (mirrors `PersonalWorkspace.tsx`'s identical roving-tabindex shell): `MembersPanel`, `SharingReview` (unchanged, now mounted), `DelegationsPanel`, `ActivityPanel`, plus a globally-mounted `WorkspaceSwitcher` (see `App.tsx`'s own comment for why it sits above every tab rather than inside this one).

Two small, disclosed backend additions were required to serve the frontend, neither in the plan's own text: `WorkspaceResponse.current` (a workspace-list response has no other way to say "this is the one your session is in") and `GET /api/v1/identity/me` (no endpoint anywhere previously told a session its own `account_id`/`users_id`, needed to tell "am I the delegator or the recipient" and "is this member row me" apart from the two parties a `Delegation`/`Member` response otherwise names symmetrically).

Every required state is covered, or its absence is disclosed:

- **Invitation expired**: `MembersPanel`'s `invitationStatus()` computes `Expired` client-side from `expires_at` the moment `now() > expires_at` and no terminal timestamp is set yet -- the backend has no separate `expired` column, matching how `DELEGATION-CONTRACT.md`'s own lazy-expiry convention already works elsewhere in this phase.
- **Membership pending**: realized as **invitation pending**, not a distinct membership row -- `workspace_memberships` has no `pending` status value in its own schema (`ck_workspace_memberships_status`: `active`/`suspended`/`removed` only); a membership row is created already `active`, atomically with acceptance. The pre-acceptance waiting period is entirely represented by the invitation itself (`Pending` status, shown in `MembersPanel`'s Invitations list), which is the real state a workspace's members can actually observe.
- **Membership suspended**: **not implemented, deliberately.** `suspended` is a real value the schema accepts, but no endpoint anywhere in Tasks 1-9 ever writes it, and `list_members_endpoint`'s own query (`WHERE wm.status = 'active'`) would filter a suspended row out of the members list identically to a removed one even if it existed. Building a UI affordance to display or set a status this backend never produces would misrepresent a capability that does not exist -- the identical judgment `personal-domain-lifecycle.mjs`'s own docstring already applies to "Import pending."
- **Permission changed**: `MemberRow`'s role `<select>` (immediate `PATCH`, reflected in the same row) covers workspace-role changes; `SharingReview`'s existing grant list (Task 5, now reachable) is the equivalent for resource-level grants -- a grant has no separate "edit" operation, matching Task 5's own create/revoke-only design.
- **Access revoked**: `SharingReview`'s `Revoke` button (Task 5, unchanged) is now reachable through this task's own navigation; `MembersPanel`'s member removal is the workspace-membership-level equivalent, both requiring the confirmation pattern below.
- **Delegation awaiting acceptance**: `DelegationsPanel`'s `proposed` status shows Accept/Reject to the recipient and an explicit disclosure to the delegator ("There is no way to withdraw a still-pending delegation..."), naming the same `DELEGATION-CONTRACT.md`-driven backend gap Task 6 already disclosed (`revoke` is reachable only from `accepted`) rather than inventing a `proposed -> revoked` transition the contract's own diagram does not list.
- **Ownership conflict**: **not implemented, deliberately.** `POST /ownership/transfers` always resolves to `status: 'completed'` in the same request that creates it -- migration `0066`'s own docstring: "no bilateral confirmation step exists... `status` is left open rather than hard-coded," a design decision made in Task 8, not an omission here. There is consequently no state in which two transfers, or a transfer and a concurrent removal, are ever left in visible conflict for a user to resolve; the closest real state this system produces is the next item.
- **Member removal blocked**: `MembersPanel`'s `OWNED_RESOURCES_BLOCK_REMOVAL` handling (409) shows the exact resource-type/count breakdown from the error's own `details.owned_resources` payload plus an inline ownership-transfer form scoped to unblocking that specific removal, retried automatically once a transfer succeeds.

**Sharing previews exactly what becomes visible** (Task 5's own guarantee, reachable here for the first time): `SharingReview`'s `Confirm and share` button only ever appears once the *current* form has actually been previewed, gated on a signature match so a stale preview of an already-edited form can never be confirmed by accident.

**Destructive removal and broad grants require deliberate confirmation**: member removal (and self-removal -- see below) requires an explicit `Confirm removal` step naming the exact consequence ("ends their access immediately and revokes their active sessions. This cannot be undone."); a grant can never be created without first previewing it (`canPreview`/`previewMatchesForm` gating, Task 5), and a visibility-narrowing grant additionally surfaces `requires_narrow_visibility_confirmation` naming exactly who loses default access.

**Self-removal ("leave workspace") is implemented, not merely disclosed as a gap.** `membership_removal.py`'s own `remove_member_endpoint` docstring states a member may remove themselves regardless of role; `MembersPanel` exposes this via `GET /identity/me`'s `users_id` (the same identifier the backend's own `is_self` check compares against), rendering "Leave workspace" and self-specific confirmation copy on the caller's own row even when they hold no `owner`/`admin` role. An earlier draft of this component disclosed self-removal as unbuildable for lack of an identity endpoint; that gap closed once `/identity/me` was added (for `DelegationsPanel`'s own need to tell delegator from recipient), so the component was revisited rather than leaving a now-stale disclosure in place.

**Deliberately out of scope, disclosed rather than silently absent:**
- No notifications inbox UI. `ecc.platform.notifications`'s `GET /notifications`/`POST /notifications/{id}/read` (Task 7) have no frontend surface -- the plan's own Task 9 bullet names "delegation inbox, shared activity feed," not a separate notifications inbox, and `ActivityPanel`'s redacted feed already gives every workspace member visibility into the same underlying events.
- No delegation evidence-picker UI. `DelegationsPanel`'s propose form omits `evidence` entirely (sent as `[]`); a delegation's evidence list is otherwise read-only, rendered from whatever a future evidence-attachment mechanism would produce.
- No member-picker for `SharingReview`'s grantee field or `MembersPanel`'s transfer-to field -- both still take a raw account ID, exactly as Task 5's own disclosed gap already stated ("The component also has no member-picker"); `MembersPanel`'s member list (this task's own addition) makes the ID visible to copy from, but no UI resolves a name to an ID automatically.

**Tests.** 33 component-test cases across 5 files (`MembersPanel.test.tsx`, `DelegationsPanel.test.tsx`, `ActivityPanel.test.tsx`, `WorkspaceSwitcher.test.tsx`, plus the pre-existing `SharingReview.test.tsx` now exercised as part of this shell), covering every state above and its own failure path. One Playwright multi-identity browser-acceptance scenario, `multi-identity-collaboration-lifecycle.mjs` -- two real, independently-authenticated browser contexts (Alice and Bob) sharing one in-memory fixture store, driving invite -> accept -> share -> revoke -> delegate -> remove end to end through live UI actions, not pre-seeded terminal states, with `@axe-core/playwright` accessibility checks after every tab switch, asserting zero serious/critical WCAG violations.
