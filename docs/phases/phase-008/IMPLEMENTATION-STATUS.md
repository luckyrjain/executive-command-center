## Task 2 evidence

**Complete.** `docs/superpowers/plans/2026-08-01-phase-8-multi-user.md`'s Task 2: the `invitations` schema (migration `0062_phase8_invitations.py`) and `ecc.domains.identity.invitations` (`POST|GET /workspaces/{id}/invitations`, `POST /invitations/{id}/accept|reject|revoke`), plus `ecc.domains.identity.accounts`'s `POST /accounts` now requiring and validating a real invitation token. Full detail in `docs/phases/phase-008/DATA-MODEL.md`'s and `docs/phases/phase-008/API-SCHEMAS.md`'s own "Task 2 status" sections.

**A genuine design gap in the approval-gate document, resolved and disclosed, not silently papered over.** Decision 3 (`docs/superpowers/specs/2026-08-01-phase-8-multi-user-design.md`) describes `POST /invitations/{id}/accept` as requiring "an authenticated accounts session," but never actually resolves how a brand-new recipient (no account, no session, anywhere) reaches an authenticated call in the first place -- accepting is exactly what would grant them their first membership, so nothing exists yet to authenticate a separate `/accept` request against. Resolved by collapsing registration and acceptance into one transaction: `POST /accounts?token=...` (for a person with no existing account) creates the account, the `users`/`workspace_memberships` rows, marks the invitation accepted, and returns a live session, all atomically; `POST /invitations/{id}/accept` (this task's own new endpoint) instead serves an *existing* account with a session from some other workspace membership accepting a second invitation -- the case Decision 3's own token/expiry/terminal-state/email-match checks describe directly. This is a judgment call made where the approved design left a real gap, not an invented shortcut -- documented in both `accounts.py`'s and `invitations.py`'s own module docstrings.

**Concurrency-safety verified directly, not just asserted.** Two properties needed real proof beyond code review: (1) the "no second concurrently-pending invitation for the same recipient" rule -- since the design's own "pending" definition includes `expires_at > now()`, it cannot be a partial unique index (Postgres partial-index predicates must be IMMUTABLE; `now()` is only STABLE), so `create_invitation_endpoint` row-locks every existing `(workspace_id, email)` row before evaluating that predicate in application code; (2) "single-use, enforced by the same transaction, not by convention" -- `accept_invitation_endpoint`'s `SELECT ... FOR UPDATE` must make two simultaneous accept attempts against the same token resolve to exactly one success. Both verified with a real Python `threading` test against local Postgres 16 (two threads racing the identical row-lock-then-update sequence, a deliberate `sleep` widening the race window) -- confirmed exactly one thread wins, the other observes the row already resolved. The full happy-path transaction (`create_account_endpoint`'s exact SQL sequence) was separately verified end to end against real Postgres before relying on CI.

**Fixed: a real privilege-escalation gap in `membership_removal.py`'s `update_member_role_endpoint`.** The endpoint let any `owner`/`admin` set any member's role to anything, including `owner` itself -- meaning an `admin` could unilaterally promote themselves (or an accomplice) to co-owner with no existing owner ever approving it, unlike `invitations.py`'s own `create_invitation_endpoint`, which already restricts issuing an `owner`-role invitation to an existing `owner`. Fixed by mirroring that same restriction: only an existing `owner` may set `role: "owner"` on a `PATCH`.

**Fixed: the four original Phase 1 domains (`planning.tasks`, `communication.commitments`, `governance.risks`, `governance.recommendations`) were never wired to `authz`, despite already carrying the `visibility` column every other domain's authorization depends on.** Traced to the phase's own implementation plan (`docs/superpowers/plans/2026-08-01-phase-8-multi-user.md`), whose Task 3 migration bullet and Task 4 wiring bullet both literally enumerate "engineering, knowledge, attention, automation, AI runtime, calendar/scheduling" and never name the four original domains -- an unintentional gap in the plan's own task breakdown (the same migration gives those four tables a `visibility` column, so excluding them from wiring cannot have been deliberate), not a scope boundary worth preserving. All four now call `authz.require_role_action(...,"write")` before create, `authz.visible_resource_filter_sql(...)` in their list endpoints' `WHERE` clause, and the two-phase `authorize(...,"read")` -> 404, then `authorize(...,"write")` -> 403 pattern on get/update/lifecycle-action endpoints, exactly matching `calendar/events.py`'s own reference wiring.

**Fixed: `dashboard_briefs.py`'s aggregation queries bypassed visibility filtering entirely, including for domains (e.g. `meetings`) that are correctly wired at their own direct endpoints.** A member's dashboard could show schedule, overdue-commitment, waiting-on and risk rows for resources `authorize()` would deny them a direct `GET` on. Fixed for the title/content-bearing sections (`schedule_rows`, `commitment_rows`, `waiting_rows`, `risk_rows`) via a new `_namespaced_visibility_filter` helper (suffixes every `visible_resource_filter_sql` bind parameter so two calls can coexist in one `UNION`-based query without colliding). `top_priorities`/`attention_rows` and `recently_changed`/`changed_rows` are disclosed as a deliberately-not-fixed, lower-severity gap below.

**Fixed: `ai_runtime/prompts.py`'s `activate_policy` had no role gate at all** -- any active member, including a `viewer`, could activate an AI policy for the whole workspace. Fixed by requiring `owner`/`admin`, matching the same restriction this codebase already applies to other workspace-wide configuration actions.

**Fixed: a TOCTOU race in `authz.create_ownership_transfer_endpoint`.** The endpoint read `resource.owner_id` and then, without a lock, later used that same value to resolve the "from" account for the transfer record -- a concurrent second transfer (or the resource being re-owned) between the read and the write could record the wrong `from_account_id`. Fixed by adding a `SELECT ... FOR UPDATE` row lock on the resource immediately before use, and resolving `from_account_id` from the locked value.

**Fixed: `invitations.py`'s `accept_invitation_endpoint` could not let a previously-removed member rejoin.** Since `membership_removal.py` never deletes a `workspace_memberships` row (only sets `status='removed'`), and both `uq_users_workspace_account` and `uq_workspace_memberships_workspace_account` are unconditional unique constraints (confirmed by reading migration `0061_phase8_accounts_memberships.py` directly), a second, unconditional `INSERT` on re-acceptance was guaranteed to violate those constraints. Fixed by looking up any existing membership row for that `(workspace_id, account_id)` under `FOR UPDATE` first: an `active` row is rejected as `ALREADY_MEMBER` (409, unchanged behavior); a `removed` row is reactivated in place (`UPDATE ... SET status='active', role=..., removed_at=NULL`) instead of a doomed second `INSERT`.

**Fixed: `delegations.py`'s evidence-grant revocation over-revoked.** `_revoke_evidence_grants` matched only on `(workspace_id, resource_type, resource_id, granted_to)`, so a member with two independent, unrelated delegations naming the same evidence resource would have both grants revoked when only one delegation reached a terminal state. Fixed by adding a `delegation_id` column to `resource_grants` (new migration `0067`, nullable, FK to `delegations.id` `ON DELETE SET NULL` -- chosen over `CASCADE`/`RESTRICT` since a deleted delegation should not delete or block deletion of the grant it produced, only orphan the link) and filtering the revocation `UPDATE` by that column in addition to the pre-existing filters. Per this codebase's own established discipline against editing an already-merged migration in place, this landed as a new migration rather than a change to `0063`.

**Fixed: `MembersPanel.tsx`/`WorkspaceSwitcher.tsx`/`DelegationsPanel.tsx` frontend issues.** A self role-change or self-removal did not invalidate the `['identity','workspaces']` query cache or refresh the session, leaving stale role/membership state visible in the same tab (role-change now invalidates that query key when the caller changed their own role; self-removal now reloads the page, since the caller's session is revoked server-side and a stale-session refetch would only 401). `WorkspaceSwitcher.tsx` had a dead, unreachable `invalidateQueries` call left over from an earlier draft, removed along with its now-unused `useQueryClient` import. `DelegationsPanel.tsx` could render its member list with an empty-string `myAccountId` for one frame before `GET /identity/me` resolved; now the list renders only once `me.data` is available. `MembersPanel.tsx` did not surface `GET /identity/me`'s own loading/error states, silently behaving as if every member were "not me" while that request was in flight or failed; both states are now rendered.

**Disclosed, not fixed: `resource_grants.granted_by` goes stale after an ownership transfer.** The original owner retains unconditional revoke power over grants they issued even after `create_ownership_transfer_endpoint` moves ownership elsewhere -- `revoke_grant_endpoint`'s "the original granter may always revoke" rule (established back in Task 6) was never designed against ownership transfer (Task 8), which shipped four tasks later. Reassigning `granted_by` retroactively on transfer would itself misattribute history the same way the Task 6 bug this review already fixed once did; the correct fix is a design decision (does transfer revoke the former owner's grant authority, or not?) beyond this review's own mandate to fix mechanical gaps, not open new contract questions. MEDIUM, left for explicit product decision.

**Disclosed, not fixed: ownership transfers are invisible on `/shared/activity`.** Neither `create_ownership_transfer_endpoint`, `create_grant_endpoint` nor `revoke_grant_endpoint` writes an `audit_events` row, so none of them surface on the Task 7 activity feed the way every domain mutation does. MEDIUM -- a real observability gap, but adding audit-event writes to three endpoints outside this review's own touched-file set risked expanding scope past "fix what six reviewers actually verified" into a seventh task's worth of new work.

**Disclosed, not fixed: `ownership_transfers.initiated_by` uses `ON DELETE CASCADE` where its sibling actor-anchor columns (`invited_by`, `granted_by`) use `RESTRICT`.** Inconsistent, and `RESTRICT` is almost certainly correct here too (an ownership-transfer record should not vanish because the initiating user's row was deleted), but no code path in this system currently deletes a `users` row, making this latent rather than exploitable today. LOW-MEDIUM; a migration-only fix, deferred rather than bundled into `0067`'s unrelated change.

**Disclosed, not fixed: dashboard `top_priorities` (`attention_rows`) and `recently_changed` (`changed_rows`) still lack per-row visibility filtering.** Unlike the four sections fixed above, both surface only `entity_type`/`entity_id`/scores or timestamps -- no titles, no content -- so the exposure is metadata-only (a denied member can learn that *some* resource of a given type changed, not what it says). Left unfixed as a proportionate severity call; the fix shape is identical to the four already-applied (`_namespaced_visibility_filter` on each section's own query).

**Disclosed, not fixed: a test-coverage backlog surfaced by the dedicated coverage-review persona**, spanning `GET /identity/me`, `WorkspaceResponse.current`, `revoke_grant_endpoint`'s non-happy paths, `create_grant_endpoint`'s error branches, several invitation/membership/delegation error branches, and multiple frontend untested error paths (roughly 15 items). Real but low-frequency (requires a background refetch to land mid-edit), and mechanical to fix by the same established pattern -- left as follow-up rather than bundled into this pass's fixes, which prioritized correctness/security findings over this UX-polish class.

A second, independent deep-review pass, explicitly requested after the first round's PR (#110) merged. Six fresh reviewers (security/authz, migrations/data-integrity, frontend/a11y, cross-task integration, spec/contract consistency, test coverage) ran against the current `main` -- each instructed to read the first round's own findings first and report only what that round missed, not re-litigate what it already fixed or disclosed. **Fixed: a TOCTOU authorization gap in `create_ownership_transfer_endpoint` that survived the first review's own fix, found independently by two of this round's six reviewers.** The first round's fix added a `SELECT ... FOR UPDATE` lock so `from_account_id` would be accurate against the resource's current owner -- but the *authorization decision itself* (`_require_owner_admin_or_resource_owner`) still ran beforehand, against the earlier, unlocked read. A non-owner/admin caller who owned the resource at the moment of their own unlocked read, but no longer owned it by the time a concurrent transfer/grant committed first, could still pass the check and redirect a resource they no longer controlled. Fixed by adding `_load_resource_for_update` (a locked variant of the existing `_load_resource`) and reordering every affected endpoint to lock first, authorize against the locked value second: `create_ownership_transfer_endpoint`, `create_grant_endpoint` (which had no lock at all before this round -- the same TOCTOU class, unlocked, reproduced independently), and `revoke_grant_endpoint`'s resource-owner branch.

**Fixed: `admin` could unilaterally demote or remove an existing `owner`.** The first round's guard only stopped an `admin` from *promoting* someone to `owner`; nothing stopped the same `admin` from *demoting* or *removing* an existing owner instead -- the identical trust boundary, applied asymmetrically. Both `update_member_role_endpoint` and `remove_member_endpoint` now also reject any `admin`-initiated action whose *target*'s current role is `owner`, checked before the pre-existing last-owner-cannot-be-touched guard so the 403 fires first. Self-service is unaffected (an owner's own role always equals the target's current role when acting on themselves).

**Fixed: `GET /api/v1/audit` had no role gate at all.** This endpoint predates Phase 8 entirely (Phase 1's original "immutable audit query API," written before any concept of workspace roles or resource visibility existed) and was never revisited once Phase 8 made `private`/`shared_explicitly` visibility a real security boundary -- despite `notifications.py`'s own module docstring already describing it as "the unrestricted, workspace-wide admin audit log," the code never actually enforced the "admin" half of that description. Fixed by gating on `owner`/`admin`, matching the docstring's own existing characterization.

**Fixed: delegation evidence grants were never re-authorized against the delegator's *current* access at accept time, only checked once at proposal time.** `create_delegation_endpoint` checks the delegator's read access to every evidence item once; `_grant_evidence` (called later, when the recipient accepts -- `proposed` can sit for however long `due_at` allows) granted access unconditionally regardless of whether the delegator still had it. If a delegator's access to named evidence was revoked in the interim (e.g. its ownership was transferred away from them), the recipient would still receive a live grant on it at accept time, `granted_by` stamped with someone who no longer had access to grant. Fixed by re-running `authorize()` per evidence item against a fresh `AuthContext` for the delegator immediately before granting; an item that no longer passes is silently skipped (not failing the whole accept, since the delegation's other evidence and its underlying obligation may still be perfectly valid).

**Fixed: knowledge search never reflected a narrowed entity's real, current visibility -- a real content leak, not the metadata-only class of gap the first round found in `dashboard_briefs.py`.** `retrieval.py`'s `queue_retrieval_document` set `retrieval_documents.owner_id`/`.visibility` once, at write time, to a permanent placeholder (`WORKSPACE_ORIGINAL_OWNER_SQL`'s "workspace's first user", hardcoded `'workspace'`) based on its own docstring's claim that `pkos_nodes` "has no actor column of its own" -- a claim that was simply wrong: `pkos_nodes` has carried a real, per-row `owner_id` (the creating member) and real `visibility` since Task 3/4's own schema-wide migration, exactly like every other wired resource table. Fixed two ways, deliberately redundant: (1) `queue_retrieval_document` now derives both fields live from the source `pkos_nodes` row on every upsert (hand-verified against real Postgres: narrowing a row's visibility directly, then re-running the upsert's `ON CONFLICT` branch, correctly refreshed the mirrored value); (2) the search endpoint's own `visible_resource_filter_sql` call now checks `pkos_nodes` live via the `n` alias both query CTEs already join, rather than trusting the `retrieval_documents` mirror at all -- closing the residual staleness window between a grant/transfer and the next unrelated entity edit entirely, not merely narrowing it.

**Fixed: a removed member's in-flight automation kept executing indefinitely, attributed to someone no longer in the workspace.** `worker.py`'s own docstring already discloses, as a deliberate Task 4 design choice, that the dispatch loop has no caller `AuthContext` and never re-checks a run's authority per step -- but Task 8's `remove_member_endpoint`, which already force-cancels a removed member's pending/accepted delegations, cascaded nothing into automation at all. A removed member's still-running (or paused/awaiting-approval/needs-review) workflow run kept firing real external side effects -- a GitHub comment, an incident resolution -- attributed to them after removal. **Fixed: `workspace_memberships` had no index on `(workspace_id, users_id)`**, despite being the very first query `authorize()` runs on every single request across all ~69 wired resource tables (`_current_role`), and being queried the identical way in `accounts.py`/`invitations.py`. New migration `0068_phase8_membership_index.py` (partial, `WHERE status = 'active'`, matching the hot-path predicate exactly), applied/downgraded/re-applied against real Postgres.

**Fixed: `scripts/seed_phase1_acceptance.py`'s restore-verification checksum list omitted `workspace_memberships`** -- present since Phase 8's very first migration, seeded with real mutable content (`role`/`status`/`removed_at`) throughout, but never added to `_WORKSPACE_ID_TABLES` despite every later Phase 8 table getting exactly this treatment on landing (an eighteenth occurrence of the same recurring gap class this file's own comments already number). Without it, a restore that silently corrupted a column value on an existing row -- `role` downgraded from `'owner'` to `'viewer'`, `status` flipped from `'active'` to `'removed'`, both directly changing who authz treats as an active owner/admin -- would pass every one of `verify_restore.sh`'s existing generic checks (row counts, workspace-isolation presence) with nothing left to catch the corruption.

## Third whole-phase review

A third, independent deep-review pass, explicitly requested after the second round's PR (#111) merged. Six fresh reviewers ran against the current `main`, again instructed to read both prior rounds' own documented findings first and report only what those rounds missed. The dominant pattern this round surfaced: this activation's own established discipline of fixing one instance of a bug class (the `retrieval_documents` stale-visibility mirror, `delegations.py`'s accept-time re-authorization, `authz.py`'s lock-then-authorize TOCTOU ordering) tends to leave sibling instances of the *identical* class unfixed elsewhere in the codebase -- every `Fixed` item below closes one such sibling.

**Fixed: `attention_items` carried the identical stale-visibility-mirror bug `retrieval_documents` was fixed for last round, in the one place that gates a live read+write authorization decision rather than mere search relevance.** `attention.py`'s `_upsert_batch` stamped every row's `owner_id`/`visibility` from the same `WORKSPACE_ORIGINAL_OWNER_SQL` placeholder and hardcoded `'workspace'` literal `retrieval.py` used to, and never refreshed either on `ON CONFLICT`. Fixed by selecting the real `owner_id`/`visibility` from each of the four source tables (`tasks`/`commitments`/`risks`/`waiting_links`, all real `_RESOURCE_TABLES` entries with those columns already) alongside their existing columns, threading them through the batch's `jsonb` payload and `jsonb_to_recordset` schema, and adding both columns to the `ON CONFLICT DO UPDATE SET` list. Hand-verified against real Postgres, mirroring last round's own `retrieval_documents` verification exactly: seeded a `private`-visibility task's attention item, widened the task's visibility directly, re-ran the upsert's `ON CONFLICT` branch, confirmed the mirrored `attention_items.visibility` refreshed to `'workspace'`.

**Fixed: two concurrent owner-count-dependent membership mutations (demote/remove) could both pass the "another owner still exists" check and leave a workspace with zero owners.** `_is_sole_active_owner`'s own `SELECT count(*)` and the calling endpoint's `UPDATE` are two separate statements with no lock spanning them under Postgres's default READ COMMITTED isolation -- two concurrent transactions demoting or removing two *different* owners (with exactly two active) could each independently see "one other owner exists" and both proceed. Fixed by serializing every membership mutation for one workspace behind a single `pg_advisory_xact_lock`, acquired at the top of both `update_member_role_endpoint`'s and `remove_member_endpoint`'s transactions -- the identical technique `attention.py`'s own `regenerate_attention` already uses for an unrelated cross-statement race, not a new mechanism.

**Fixed: `_validate_team_entity` (`connector_accounts.py`) was the one call site that dropped the second half of the "existence + kind, checked at write time" pattern it claims to mirror.** `waiting.py`'s own `_counterparty_node_type` precedent re-checks `authz.authorize(..., action="read")` immediately after the raw existence query and folds a denial into the same 404 a nonexistent id returns -- `_validate_team_entity` only did the existence + kind check, never the authorization re-check, so a caller could confirm a `pkos_nodes` team-entity id's existence and assign a repository/work-item to it regardless of that node's own current visibility. Fixed by adding the identical `authz.authorize(..., resource_type="pkos_nodes", action="read")` check, folded into the same `TEAM_ENTITY_NOT_FOUND` 404 on denial.

**Fixed: an invitation's granted role was never re-verified against the inviter's *current* authority at accept time, only checked once at creation** -- the identical "re-authorize at use-time, not trust proposal-time" bug class fixed for `delegations.py`'s own evidence grants last round, present in both of this codebase's two accept-invitation call sites (`invitations.py`'s `accept_invitation_endpoint`, for an existing-account recipient; `accounts.py`'s `create_account_endpoint`, for a brand-new recipient). `create_invitation_endpoint`'s own guard stops a non-owner from *minting* an `owner`-role invitation, but an invitation can sit pending for up to seven days (`_INVITATION_MAX_AGE_SECONDS`) -- long enough for the inviting owner to be demoted or removed before the recipient ever accepts, after which accepting still minted a fresh co-owner nobody currently holding owner authority approved. Fixed by re-verifying, at both accept call sites, that an `owner`-role invitation's `invited_by` still holds active `owner` membership; a stale inviter now rejects with a new `409 INVITER_NO_LONGER_AUTHORIZED` rather than silently succeeding.

**Fixed: a schedule trigger authored by a since-removed member kept minting fresh automation runs forever, attributed to someone no longer in the workspace.** Last round's `cancel_runs_for_removed_member` only force-cancels a removed member's *already-enqueued* non-terminal runs at removal time -- it does nothing about runs a `schedule` trigger keeps creating afterward, since `scheduler.run_scheduler_once` passes `trigger.created_by` straight through to `worker.enqueue_run`'s `actor_id` with no check that `users_id` still holds active membership (`scheduler.py`'s own module docstring already discloses it has no caller `AuthContext` to re-check per tick).
