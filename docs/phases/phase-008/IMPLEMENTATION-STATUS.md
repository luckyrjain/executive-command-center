## Task 1 evidence

**Complete.** `docs/superpowers/plans/2026-08-01-phase-8-multi-user.md`'s Task 1: the `accounts`/`workspace_memberships` schema (migration `0061_phase8_accounts_memberships.py`) and `ecc.domains.identity.accounts` (`POST /accounts`, `POST /auth/login`, `POST /auth/select-workspace`, `GET|POST /workspaces`, `GET|PATCH /workspaces/{id}`). Full detail in `docs/phases/phase-008/DATA-MODEL.md`'s and `docs/phases/phase-008/API-SCHEMAS.md`'s own "Task 1 status" sections.

**Central design choice, verified in practice, not just asserted.** `users` keeps its exact pre-existing role as the composite `(workspace_id, id)` FK anchor every `owner_id`/`created_by`/`updated_by` column already points to; only a new `account_id` column was added. After running the real migration against local Postgres, all ~14 pre-existing composite FKs to `users.(workspace_id, id)` were directly inspected via `\d` and confirmed completely unaffected -- this migration does not touch them.

**Two deliberate, disclosed scope-narrowings for this task**, not silent gaps: (1) `POST /accounts` is genuine open self-registration -- no invitation gate exists yet, since Task 2 hasn't shipped the `invitations` table; (2) pre-auth endpoints (`POST /accounts`, `POST /auth/login`) skip `Idempotency-Key` support entirely -- `idempotency_records` is keyed on `(workspace_id, actor_id)`, which structurally does not exist yet at those call sites, and `accounts.email`'s own `UNIQUE` constraint already makes retrying account creation safe.

**Test-suite migration.** ~75 pre-existing `tests/*_postgres.py` files seeded their own fixture identity via an inline three-column `INSERT INTO users (id, workspace_id, email, password_hash, created_at)` that no longer matches the new schema. Rather than hand-edit each file, an AST-based transform script located every matching call (tolerant of `text`/aliased-`text` and whitespace variation) and replaced it with a call to a new shared `tests/identity_fixtures.py:create_identity` helper (which performs the new three-table `accounts`/`users`/`workspace_memberships` insert sequence), applied end-of-file-backwards using exact `lineno`/`col_offset` character-span splicing. Verified via dry-run diff before applying, then spot-verified against real Postgres (`test_workspace_isolation.py`, `test_personal_insight_tools_postgres.py`, and several others -- all passing, confirming the transform is correct and introduces no regression). `identity_fixtures.py` also exports `add_membership`, for tests that need one account holding active memberships in more than one workspace.

**New tests.** `tests/test_identity_accounts_postgres.py` (14 tests): account creation + duplicate-email rejection (case-insensitive) + short-password rejection; single-active-membership login auto-authenticates; wrong-password/no-active-membership/disabled-account login rejections; two-active-memberships login returns a `pending_login_token` and completes via `select-workspace`; `select-workspace` rejects a forged/expired pending token and a workspace the account has no membership in (cross-account isolation -- knowing a real `workspace_id` is not enough); the authenticated-session switch mode requires CSRF; `GET /workspaces` excludes suspended memberships; `POST /workspaces` makes the caller owner; `PATCH /workspaces/{id}` is role-gated (403 for a viewer); `GET /workspaces/{id}` 404s for a different workspace id; disabling an account revokes an already-issued session immediately.

**Verified.** `ruff check`/`ruff format --check` clean across `backend/`, `scripts/` and `tests/`. `mypy backend` clean (165 source files -- `tests/` is out of mypy's CI scope). Migration `upgrade head` / `downgrade -1` / `upgrade head` round-trip verified against real local Postgres 16, schema and backfilled data confirmed correct by direct `\d`/`SELECT` inspection. `tests/test_identity_accounts_postgres.py` itself could not run in this sandbox's Python 3.11 venv -- it imports `ecc.main.app`, which transitively hits the same pre-existing, unrelated Python-3.11-only `NameError` (a self-referencing return-type annotation without `from __future__ import annotations`, safe under the real Python-3.14-with-PEP-649 CI environment) already documented for other `TestClient`-based files in this repository; several transformed non-`TestClient` test files (`test_workspace_isolation.py`, `test_personal_insight_tools_postgres.py`, `test_automation_triggers_postgres.py`, `test_ai_runtime_tools_postgres.py`, `test_knowledge_rebuild_performance_postgres.py`) ran for real against Postgres and passed, confirming the schema/fixture migration itself is correct; the new file's own dynamic verification happened in CI (PR #100, all jobs green after one bugfix round).

**Adversarial review round (before merge).** A dedicated review pass of the full PR #100 diff found and this round fixed: (1) MEDIUM -- `require_auth_context` (`ecc/auth.py`, shared by every authenticated endpoint app-wide) never checked `accounts.disabled_at`, so a disabled account's already-issued sessions stayed valid for up to 7 days -- fixed by joining `sessions`->`users`->`accounts` and requiring `disabled_at IS NULL`, matching the design doc's own "revocation propagates by construction" promise; verified directly against real Postgres (a live session query returns a row before disabling the account, `NULL` immediately after) and by a new end-to-end test. (2) LOW -- `login_endpoint` returned near-instantly for a nonexistent email but paid the full Argon2id verify cost for a wrong password against a real account, both returning the identical `INVALID_CREDENTIALS` body -- an email-enumeration timing side-channel; fixed by always paying the verify cost against a fixed dummy hash when no account matches. (3) LOW -- migration `0061`'s backfill normalized `email.casefold()` without `.strip()`, unlike the runtime `_normalize_email`'s `.strip().casefold()` -- a legacy row with incidental whitespace could have silently evaded the `UNIQUE` constraint's collision check; fixed to match. (4) LOW -- an unused `_ROLES` frozenset left over from an earlier draft; removed. One further gap (`create_identity`'s test fixture accounts are never deleted by most of the ~75 pre-existing tests' own cleanup helpers) was assessed and consciously not fixed: it is a real but harmless resource leak (CI's Postgres is a fresh container per job; `accounts.email` is UUID-derived and never collides), and a 75-file mechanical patch for a cosmetic local-dev-only concern was judged disproportionate to the risk it closes.

**Post-merge fix (`luckyrjain/executive-command-center#101`, found while starting Task 2).** `POST /workspaces` and `PATCH /workspaces/{id}` shipped with no CSRF protection at all -- no `CsrfDep`, and this codebase has no global CSRF middleware (`require_csrf` is opt-in per endpoint, like every other mutating route). The module's own top-of-file docstring incorrectly claimed both endpoints "carry the standard idempotency-key plus CSRF protection," which masked the gap on re-read; the existing tests for both endpoints only ever sent a *valid* CSRF header, so neither test would have failed even with the check entirely absent -- a false-negative test design, not just a missing test. Fixed by adding `_csrf: CsrfDep` to both endpoints, correcting the docstring to state plainly that neither endpoint uses `Idempotency-Key` (for two different, already-locally-documented reasons) while both now genuinely require CSRF, and adding two new tests (`test_create_workspace_requires_csrf`, `test_patch_workspace_requires_csrf`) that call each endpoint with no CSRF header and assert `403 CSRF_TOKEN_REQUIRED`, mirroring the pattern `test_authenticated_switch_requires_csrf` already established.

## Task 2 evidence

**Complete.** `docs/superpowers/plans/2026-08-01-phase-8-multi-user.md`'s Task 2: the `invitations` schema (migration `0062_phase8_invitations.py`) and `ecc.domains.identity.invitations` (`POST|GET /workspaces/{id}/invitations`, `POST /invitations/{id}/accept|reject|revoke`), plus `ecc.domains.identity.accounts`'s `POST /accounts` now requiring and validating a real invitation token. Full detail in `docs/phases/phase-008/DATA-MODEL.md`'s and `docs/phases/phase-008/API-SCHEMAS.md`'s own "Task 2 status" sections.

**A genuine design gap in the approval-gate document, resolved and disclosed, not silently papered over.** Decision 3 (`docs/superpowers/specs/2026-08-01-phase-8-multi-user-design.md`) describes `POST /invitations/{id}/accept` as requiring "an authenticated accounts session," but never actually resolves how a brand-new recipient (no account, no session, anywhere) reaches an authenticated call in the first place -- accepting is exactly what would grant them their first membership, so nothing exists yet to authenticate a separate `/accept` request against. Resolved by collapsing registration and acceptance into one transaction: `POST /accounts?token=...` (for a person with no existing account) creates the account, the `users`/`workspace_memberships` rows, marks the invitation accepted, and returns a live session, all atomically; `POST /invitations/{id}/accept` (this task's own new endpoint) instead serves an *existing* account with a session from some other workspace membership accepting a second invitation -- the case Decision 3's own token/expiry/terminal-state/email-match checks describe directly. This is a judgment call made where the approved design left a real gap, not an invented shortcut -- documented in both `accounts.py`'s and `invitations.py`'s own module docstrings.

**Concurrency-safety verified directly, not just asserted.** Two properties needed real proof beyond code review: (1) the "no second concurrently-pending invitation for the same recipient" rule -- since the design's own "pending" definition includes `expires_at > now()`, it cannot be a partial unique index (Postgres partial-index predicates must be IMMUTABLE; `now()` is only STABLE), so `create_invitation_endpoint` row-locks every existing `(workspace_id, email)` row before evaluating that predicate in application code; (2) "single-use, enforced by the same transaction, not by convention" -- `accept_invitation_endpoint`'s `SELECT ... FOR UPDATE` must make two simultaneous accept attempts against the same token resolve to exactly one success. Both verified with a real Python `threading` test against local Postgres 16 (two threads racing the identical row-lock-then-update sequence, a deliberate `sleep` widening the race window) -- confirmed exactly one thread wins, the other observes the row already resolved. The full happy-path transaction (`create_account_endpoint`'s exact SQL sequence) was separately verified end to end against real Postgres before relying on CI.

**Verified.** `ruff check`/`ruff format --check` clean across `backend/`, `scripts/` and `tests/`. `mypy backend` clean (167 source files). Migration `upgrade head` / `downgrade -1` / `upgrade head` round-trip verified against real local Postgres 16; the `ck_invitations_terminal_states_mutually_exclusive` `CHECK` constraint confirmed to actually reject a row with two terminal timestamps set, by direct SQL. The concurrent-accept race and the full happy-path account-creation transaction were verified directly against real Postgres (see above), independent of the TestClient-based test suite. `tests/test_identity_invitations_postgres.py` (14 tests: create role-gating, already-active-member rejection, duplicate-pending rejection, list role-gating, the new-recipient registration-and-auto-join path, invalid/expired/email-mismatched token rejections at account creation, the existing-account accept path across two workspaces, wrong-token rejection at accept, reject-then-accept-fails, revoke-then-register-fails, revoke role-gating, cross-workspace revoke isolation, and the concurrent-accept race) could not run in this sandbox's Python 3.11 venv for the same pre-existing, unrelated, documented reason as Task 1's own test file (imports `ecc.main.app`); dynamic verification happens in CI, watched and driven to green the same way every prior PR in this activation has been.
