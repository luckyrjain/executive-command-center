HTTP client shape mirrors `ecc.domains.ai_runtime.ollama_client.OllamaAdapter`'s precedent (injectable `transport` for tests, no new dependency -- `httpx.MockTransport` is part of the already-pinned `httpx` package). Implements: `authorize` (`GET /user`, parses `X-OAuth-Scopes`), repository backfill/incremental sync (paginated via the `Link` header; incremental sync stops once a page's `updated_at` falls at or before the prior cursor, since GitHub's repository-list endpoint has no `since` parameter), bounded rate-limit retry (`403`/`429` + `X-RateLimit-Remaining`/`Retry-After`/`X-RateLimit-Reset`, one bounded wait, `partial` status beyond it), `refresh_permissions`, and a no-op `disconnect` (a personal access token has no revocation API a connector can call).
- **Pool-exhaustion fix (Task 1's own disclosed blocker for this task, resolved)**: `sync_connector_endpoint` (`connector_accounts.py`) restructured into three phases across two pooled connections -- validate/reserve on the request's own session, explicitly `session.close()` before the adapter call, then record the outcome on a fresh `SessionFactory()` session. No pooled connection is held during a real provider's HTTP call. `create_connector_endpoint` received the identical restructuring around `adapter.authorize()`, the same real-network-call risk this fix originally addressed only for `/sync`. See that function's and the module's own docstrings for the full detail.
- **Review-fix (PR #75, this task): the pool-exhaustion restructuring above initially reintroduced three races**, since closing the pooled connection between phases also released the guarantees a single held transaction used to provide across the whole handler: a genuine same-Idempotency-Key retry could double-execute the adapter call instead of returning the cached response; the audit trail's `version` was computed from phase 1's now-stale in-memory snapshot instead of the database's actual post-update value; and two concurrent `/sync` calls for the same account could race the `sync_cursors` UPSERT (a lost-update race the old, handler-spanning `FOR UPDATE` lock used to prevent by itself). Fixed by making "start a sync" itself atomic instead of trying to extend a lock across the slow phase: `uq_sync_runs_running_per_account` (migration `0046`, a partial unique index mirroring `uq_workflow_versions_active_per_workflow`'s established idiom) makes phase 1's `INSERT INTO sync_runs (...status='running'...)` the serialization point, returning `409 CONNECTOR_SYNC_IN_PROGRESS` on conflict; phase 3's `connector_accounts` UPDATEs now guard `AND status != 'disconnected'` (so a concurrent `/disable` always wins) and read the account's actual version via `UPDATE ... RETURNING version` (`_finalize_account_version`) rather than the stale snapshot. See `connector_accounts.py`'s module and function docstrings for the full mechanism.
- **Tests** (`tests/test_engineering_github_sync_postgres.py`, 22 cases after the review-fix round below, plus one existing Task 1 test updated since `github` is no longer an unsupported provider): `authorize` success/401/non-200/network-error/missing-required-scope-rejection/fine-grained-PAT-accepted-with-empty-scopes; repository backfill single-page and multi-page (`Link` header pagination, including a `next` URL containing a comma); incremental-sync stop-at-cursor and no-cursor-behaves-like-backfill; non-repository resource types are a zero-item no-op; rate-limit retry succeeding after a bounded wait, giving up beyond it (`partial`), and giving up the same way when the one retry is itself still rate-limited; the `_MAX_PAGES_PER_CALL` bound reporting `partial` rather than a silent `succeeded`; `refresh_permissions`/`disconnect`/`handle_webhook` contract coverage; end-to-end through the real `/sync` endpoint with a mocked GitHub transport proving `repositories` rows are actually written, an incremental sync only upserts genuinely-newer rows, and a rate-limited sync reports `partial` without moving the connector account to `error`. `tests/test_engineering_connectors_postgres.py` (33 cases after the same round, later 38 -- see this file's own module docstring for the further review round that added 4 more, closing gaps a second review round of this task's own fixes found: two-concurrent-syncs conflict, a stale-vs-recent `running` sync-run reap test pair, and an idempotent-retry-racing-phase-3 replay test; this later round was never itself narrated here until the whole-phase review caught the stale count): the `CONNECTOR_SYNC_IN_PROGRESS` conflict, audit `aggregate_version` matching the account's real post-update version on both the sync-success and sync-failure paths, and `_finalize_account_version`'s disconnected-account guard. - **Correctness (Medium-High) -- `insufficient_coverage` metrics could still expose a real numeric value.** `metrics.py`'s `_compute_work_ageing`/`_compute_blocked_work`/`_compute_review_latency` compute `coverage_status` and `value`/`numerator`/`denominator`/`details` independently -- nothing nulled the latter once coverage regressed below the 50% floor, unlike the three deployment-dependent metrics (which always use `_insufficient_coverage_snapshot`).
