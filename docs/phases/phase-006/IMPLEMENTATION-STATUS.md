## Task 2 evidence — GitHub read sync (repositories only)

- **Scope**: real GitHub REST API backfill/incremental sync for `repository` resources only. `engineering_work_items`/`changes`/`reviews`/`deployments` (`DATA-MODEL.md`) are explicitly deferred to a Task 2 follow-up, disclosed in `github_adapter.py`'s own module docstring and `docs/phases/phase-006/DATA-MODEL.md`/`API-SCHEMAS.md`, not silently absent. Webhook ingestion (`GitHubAdapter.handle_webhook`) implements the parsing/upsert logic the `ConnectorAdapter` contract asks for, but has no receiving HTTP route or webhook-secret storage yet -- also disclosed, not wired to a public endpoint.
- **Migration `0045_phase6_repositories.py`**: `repositories` -- workspace-scoped, FK'd to `connector_accounts`. Verified `alembic upgrade head`/`downgrade -1` against a real PostgreSQL 16 database.
- **`ecc.domains.engineering.github_adapter.GitHubAdapter`**: the first real, non-sandbox `ConnectorAdapter`, registered into the shared production registry alongside `sandbox.github`. HTTP client shape mirrors `ecc.domains.ai_runtime.ollama_client.OllamaAdapter`'s precedent (injectable `transport` for tests, no new dependency -- `httpx.MockTransport` is part of the already-pinned `httpx` package). Implements: `authorize` (`GET /user`, parses `X-OAuth-Scopes`), repository backfill/incremental sync (paginated via the `Link` header; incremental sync stops once a page's `updated_at` falls at or before the prior cursor, since GitHub's repository-list endpoint has no `since` parameter), bounded rate-limit retry (`403`/`429` + `X-RateLimit-Remaining`/`Retry-After`/`X-RateLimit-Reset`, one bounded wait, `partial` status beyond it), `refresh_permissions`, and a no-op `disconnect` (a personal access token has no revocation API a connector can call).
- **Pool-exhaustion fix (Task 1's own disclosed blocker for this task, resolved)**: `sync_connector_endpoint` (`connector_accounts.py`) restructured into three phases across two pooled connections -- validate/reserve on the request's own session, explicitly `session.close()` before the adapter call, then record the outcome on a fresh `SessionFactory()` session. No pooled connection is held during a real provider's HTTP call. `create_connector_endpoint` received the identical restructuring around `adapter.authorize()`, the same real-network-call risk this fix originally addressed only for `/sync`. See that function's and the module's own docstrings for the full detail.
- **Review-fix (PR #75, this task): the pool-exhaustion restructuring above initially reintroduced three races**, since closing the pooled connection between phases also released the guarantees a single held transaction used to provide across the whole handler: a genuine same-Idempotency-Key retry could double-execute the adapter call instead of returning the cached response; the audit trail's `version` was computed from phase 1's now-stale in-memory snapshot instead of the database's actual post-update value; and two concurrent `/sync` calls for the same account could race the `sync_cursors` UPSERT (a lost-update race the old, handler-spanning `FOR UPDATE` lock used to prevent by itself). Fixed by making "start a sync" itself atomic instead of trying to extend a lock across the slow phase: `uq_sync_runs_running_per_account` (migration `0046`, a partial unique index mirroring `uq_workflow_versions_active_per_workflow`'s established idiom) makes phase 1's `INSERT INTO sync_runs (...status='running'...)` the serialization point, returning `409 CONNECTOR_SYNC_IN_PROGRESS` on conflict; phase 3's `connector_accounts` UPDATEs now guard `AND status != 'disconnected'` (so a concurrent `/disable` always wins) and read the account's actual version via `UPDATE ... RETURNING version` (`_finalize_account_version`) rather than the stale snapshot. See `connector_accounts.py`'s module and function docstrings for the full mechanism.
- **Tests** (`tests/test_engineering_github_sync_postgres.py`, 22 cases after the review-fix round below, plus one existing Task 1 test updated since `github` is no longer an unsupported provider): `authorize` success/401/non-200/network-error/missing-required-scope-rejection/fine-grained-PAT-accepted-with-empty-scopes; repository backfill single-page and multi-page (`Link` header pagination, including a `next` URL containing a comma); incremental-sync stop-at-cursor and no-cursor-behaves-like-backfill; non-repository resource types are a zero-item no-op; rate-limit retry succeeding after a bounded wait, giving up beyond it (`partial`), and giving up the same way when the one retry is itself still rate-limited; the `_MAX_PAGES_PER_CALL` bound reporting `partial` rather than a silent `succeeded`; `refresh_permissions`/`disconnect`/`handle_webhook` contract coverage; end-to-end through the real `/sync` endpoint with a mocked GitHub transport proving `repositories` rows are actually written, an incremental sync only upserts genuinely-newer rows, and a rate-limited sync reports `partial` without moving the connector account to `error`. `tests/test_engineering_connectors_postgres.py` (33 cases after the same round): the `CONNECTOR_SYNC_IN_PROGRESS` conflict, audit `aggregate_version` matching the account's real post-update version on both the sync-success and sync-failure paths, and `_finalize_account_version`'s disconnected-account guard. All pass against a real PostgreSQL 16 database. Verified via `ruff check`/`ruff format --check`/`mypy --strict` (all clean).
- **Known sandbox-environment limitation (unchanged from Task 1, same root cause)**: this container still cannot execute the committed test files unmodified (same pre-existing Python-3.11/PEP-649 import-chain issue); verified instead through the same faithful smoke-harness technique Task 1 used, now also including a copy of `response_contract_middleware` so error-envelope-shaped assertions are checked locally too (a real gap Task 1's own first harness missed, caught only by real CI -- see the two commits fixing PR #74 after its first review pass for the full account).
