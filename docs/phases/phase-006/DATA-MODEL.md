# Phase 6 Data Model

Core projections: `connector_accounts`, `sync_cursors`, `sync_runs`, `repositories`, `engineering_work_items`, `changes`, `reviews`, `deployments`, `incidents`, `engineering_decisions`, `service_links`, `delivery_metric_snapshots` and `source_tombstones`.

The "every projection stores provider, external ID, source URL, observed/updated times, permission/freshness state and raw-content hash" rule below governs synced-content projections specifically (`repositories` onward) -- `connector_accounts`/`sync_cursors`/`sync_runs` are connector-platform bookkeeping tables, not synced-content records with their own external business identity, so they do not carry a `source_url` or content-hash column; they are scoped instead by `(workspace_id, provider, external_account_id)` and `(workspace_id, connector_account_id, resource_type)` respectively (`backend/migrations/versions/0044_phase6_connector_platform.py`).

**Task 7 status**: no new table. `github.add_issue_comment`/`gitlab.add_note`/`jira.add_comment` (`ecc.domains.engineering.write_actions`) are Phase 5 `ActionAdapter`s, not projections -- a dispatch's own record lives entirely in Phase 5's existing `workflow_run_steps`/`audit_events`/`event_outbox` tables, unchanged by this task. No "comments" table was added; a created comment's identity is returned in `workflow_run_steps.output` (never persisted as its own row here), disclosed in that module's own docstring alongside why (a comment is deliberately the one write action needing no synced-projection lifecycle of its own).

**Task 1-6 status**: `connector_accounts`, `sync_cursors`, `sync_runs` (migration `0044`), `repositories` (migration `0045`), `engineering_work_items` (migration `0047_phase6_work_items.py`), `changes`/`reviews`/`delivery_metric_snapshots` (migration `0048_phase6_delivery_metrics.py`), and `incidents`/`engineering_decisions` (migration `0049_phase6_decisions_incidents.py`) are all implemented. Task 3 (GitLab) populated `repositories` with `provider = 'gitlab'` rows -- no new migration, since the table's own `ck_repositories_provider` CHECK constraint already named `gitlab` alongside `github`/`jira`/`sandbox`. Task 4 (Jira) adds `engineering_work_items`, mirroring `repositories`' shape (provider/external ID/source URL/observed-updated times/permission-freshness state/content hash) plus work-item-specific `item_type`/`status`/`reporter_external_id`/`assignee_external_id` columns -- the latter two store raw, unresolved Jira `accountId` strings; resolving them against Phase 2 `Person` entities is explicit Task 6 scope, not this task's. Task 5 adds `changes`/`reviews` (GitHub only this task -- see `github_adapter.py`'s own module docstring for why GitLab changes/reviews sync is deferred to a Task 5 follow-up), each mirroring `repositories`' shape plus resource-specific fields (`changes.repository_id`/`reviews.change_id` are real FKs, never ambiguous the way a Jira reporter is; `changes.author_external_id`/`reviews.reviewer_external_id` are left unresolved for the identical Task 6 reason as work items), and `delivery_metric_snapshots` (`DELIVERY-INTELLIGENCE-CONTRACT.md`'s field list made concrete, plus a `details_json` column for the two metrics -- `work_ageing` and `blocked_work` -- whose own contract definitions are each more than a single scalar). Task 5 also adds `engineering_work_items.provider_created_at` (same migration), a genuine Task 4 gap `work_ageing` exposed -- see that migration's own docstring. Task 6 adds `incidents`/`engineering_decisions` -- unlike every projection above, neither is synced-content: both are workspace-authored (an operator captures "we had an incident"/"we decided X"), so neither carries a `provider`/`external_id`/`source_url`/`content_hash` column at all, the same shape Phase 2's own knowledge-capture tables (`notes`, `knowledge_claims`) already use, plus the `version`/`created_by`/`updated_by` optimistic-concurrency shape `connector_accounts` established since these rows are human-editable. Correlation to `changes` is a real join table (`incident_changes`/`decision_changes`), not an array column; correlation to `deployments`/work items, and resolving the raw provider-identifier columns above against Phase 2's identity-resolution machinery, are both explicitly deferred -- see migration `0049`'s own docstring and `decisions_incidents.py`'s. `deployments`, `service_links` and `source_tombstones` do not exist yet and remain unassigned to any task, matching Phase 5's own precedent of adding tables task-by-task rather than all upfront.

Every projection stores provider, external ID, source URL, observed/updated times, permission/freshness state and raw-content hash. Unique keys are workspace/provider/account/external-ID scoped. Raw provider payload retention is minimized. People link to Phase 2 entities; ambiguous identities remain unresolved. Metric snapshots store definition/version, population, window, numerator, denominator and coverage.

**Team linkage status (migration `0050_phase6_team_linkage.py`)**: `repositories` and `engineering_work_items` each gain two columns -- `team_entity_id` (nullable, composite FK to `pkos_nodes(workspace_id, id)`, mirroring `commitments.counterparty_person_id`'s own nullable-link precedent) and `suggested_team_name` (plain text, no FK). Only the *first* is a link; the second is a sync-refreshed hint a human reads before confirming, following `docs/phases/phase-002/DATA-MODEL.md`'s own "team" entry's "hybrid: auto-suggest, human confirms" design for closing its disclosed "no cross-domain linkage exists yet" gap. `changes`/`reviews` get no column of their own -- they inherit their owning team transitively through the real FKs they already have (`changes.repository_id`, `reviews.change_id`), so a second copy of the same link would just be another place a reassignment has to remember to update. `delivery_metric_snapshots` also gets no column here: the metrics engine (`metrics.py`) does not read either new column yet, so its `aggregation_scope = 'team'` enum value (migration `0048`) remains as unreachable after this migration as before it -- see `DELIVERY-INTELLIGENCE-CONTRACT.md`'s updated "Task 5 status" for that disclosed, separate follow-up. See migration `0050`'s own docstring for the full column-by-column design, and `CONNECTOR-CONTRACT.md`'s new "Team linkage status" section for what each provider adapter actually writes into `suggested_team_name`.
