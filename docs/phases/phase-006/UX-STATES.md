# Phase 6 UX States

**Task 1 status**: no frontend surface existed yet as of Task 1 -- this document's states were the approved target for Task 8. Task 1 delivered only the backend connector platform these surfaces consume.

Surfaces: engineering overview, delivery, reliability, repositories, incidents, decisions, connector health and source coverage. Required states include first sync, backfill, partial permissions, stale connector, rate limited, disconnected, provider unavailable and conflicting identities.

Charts always show definition, window, coverage and evidence drill-down. Never display person rankings or shame language. Accessible tables accompany visualizations; core workflows meet WCAG 2.2 AA.

**Task 8 status: complete.** `frontend/src/features/engineering/` implements all eight named surfaces as one tabbed `EngineeringWorkspace` (mirrors `AutomationWorkspace.tsx`'s own roving-tabindex shell): `EngineeringOverview`, `DeliveryPanel`, `ReliabilityPanel`, `RepositoriesPanel`, `IncidentsPanel`, `DecisionsPanel`, `ConnectorHealthPanel`, `CoveragePanel`. Every required state is covered:

- **First sync** / **backfill**: `ConnectorHealthPanel` renders `pending`-status connectors with zero sync-run history distinctly from a connector whose first backfill is already `running` (its own sync-run row shown as "in progress") -- these are two genuinely different states, not one collapsed into the other (a real bug the browser-acceptance run itself caught and closed: a `pending` connector with an already-running backfill must not also claim "no sync has ever run").
- **Partial permissions**: `permission_lost` at the connector-account level (`ConnectorHealthPanel`) is genuinely reachable and tested. The per-repository/per-work-item `permission_state` field (`RepositoriesPanel`/`WorkItemsPanel`) is correctly *rendered* when populated, but a whole-phase review found no adapter, for any of the four providers, ever writes anything other than `'active'` to this column on any of the seven content-projection tables it exists on -- there is no "no-longer-visible row" detection anywhere in the sync path. This means the "some repositories lost permission while others stay active" scenario this bullet describes cannot occur in practice today; a real permission-loss narrows only to the connector-account level. Disclosed here rather than left implied by dead-but-present frontend handling; see `CONNECTOR-CONTRACT.md`'s matching "Accepted limitation" entry.
- **Stale connector**: derived client-side from `last_synced_at`'s own age (`ConnectorHealthPanel`, a disclosed 24-hour heuristic since this activation has no periodic freshness monitor) and from the per-row `freshness_state` column (`RepositoriesPanel`/`WorkItemsPanel`).
- **Rate limited** / **disconnected** / **provider unavailable**: map directly onto `ConnectorAccountResponse.status`'s `rate_limited`/`disconnected`/`error` values (`ConnectorHealthPanel`), the last paired with the real `last_error` detail.
- **Conflicting identities**: `CoveragePanel` discloses unresolved `reporter_external_id`/`assignee_external_id` values as a sample list with an explicit note that no identity-resolution mechanism exists for engineering data in this activation (unlike Phase 2's `resolution_candidates`) -- a disclosure, not an interactive merge flow, since no backend resolution machinery exists to back one.

**Two disclosed additive query endpoints** (`GET /engineering/repositories`, `GET /engineering/work-items`) were added as part of this task -- see `API-SCHEMAS.md`'s own "Task 8 status" note. **Charts always show definition/window/coverage/evidence**: `MetricCard.tsx` (shared by Delivery and Reliability) renders all four together for every metric snapshot, including the `insufficient_coverage` case, which shows "not yet available" rather than a misleading number. **No person rankings**: verified structurally -- no metric card, panel, or endpoint in this feature carries a `person_id`/engineer-scoped field at all.

**Work items panel (later addition, a real gap this task's own line above already claimed was closed).** `GET /engineering/work-items` and its `POST .../team` confirm endpoint existed since migration `0050_phase6_team_linkage.py`, but until now had no per-item list surface at all -- only `CoveragePanel`'s own unresolved-identity rollup ever read the response. This line's own "per-work-item" `permission_state` claim above was true only of the data model, not of anything a user could actually see. `WorkItemsPanel.tsx` closes this, mirroring `RepositoriesPanel.tsx` exactly (permission/freshness disclosure, team-assignment dropdown, `suggested_team_name` hint), as a ninth `EngineeringWorkspace` tab beyond this document's original eight-surface list. Both `RepositoriesPanel`/`WorkItemsPanel` also gained a read-only "filter by team" select (a second, separate real gap: the backend's own `?team_entity_id=` filter existed on both list endpoints since migration `0050`, but the only place either panel consumed a team entity at all was the write-side assignment dropdown -- there was no way to view just one team's repositories or work items).

Verified via component tests (105 cases across 10 files -- the 9 panels plus the `EngineeringWorkspace` shell -- covering every state above, after several post-merge review-fix rounds, the `WorkItemsPanel`/team-filter addition, and the whole-phase review's own coverage fixes -- e.g. `EngineeringOverview`'s incidents/decisions/metrics `isError` paths, the Datadog provider/resource-type options; see `IMPLEMENTATION-STATUS.md`'s Task 8, "Final whole-phase review" and "Five-persona review of the entire Phase 6 body of work" sections and `TEST-PLAN.md`'s Task 8 status for the full breakdown) and two Playwright browser-acceptance scenarios (`engineering-connector-states.mjs`, `engineering-lifecycle.mjs`) with `@axe-core/playwright` accessibility checks after every tab switch, asserting zero serious/critical WCAG violations.

**Team suggestions panel (later addition, a tenth `EngineeringWorkspace` tab, migration `0072_team_suggestion_dismissal.py`).** The write-side team-assignment dropdown already existed inline, one row at a time, in `RepositoriesPanel`/`WorkItemsPanel` -- there was no dedicated page showing every pending suggestion across a workspace, grouped so several repositories/work items sharing one suggested name could be resolved in a single action. `TeamSuggestionsPanel.tsx` closes this: one row per distinct `suggested_team_name`, each showing its repository/work-item counts and a sample of matching items, with per-group **Confirm** (via the existing team picker), **Dismiss**, and a later-addition third path, **Create & confirm** -- a text input pre-filled with the suggested name (editable) that creates a new team entity and confirms the group against it in one action, for the case where no matching team exists yet. A teams-query load failure is disclosed distinctly from a suggestions-query load failure ("Confirm is unavailable until this loads -- Create & confirm and Dismiss still work"), since Create & confirm does not depend on the team list at all. The existing per-row `TeamAssignment` control in `RepositoriesPanel`/`WorkItemsPanel` is unaffected and stays as-is -- this panel is a bulk-action sibling, not a replacement. 12 cases in `TeamSuggestionsPanel.test.tsx` (a new file), bringing the engineering feature-test total from 105 across 10 files to 119 across 11.

**Connector-create form, per-provider fields (later addition, found via real-workspace review).** `ConnectorHealthPanel`'s "Connect" form originally took one generic password-style "Credential" input for every provider, relying on a placeholder hint (GitLab only) to explain that the field's real shape was `host|token`, `site|email|api_token`, or `site|api_key|app_key` for GitLab/Jira/Datadog respectively -- an operator had to hand-assemble the pipe-delimited string correctly with no field-level guidance for two of the three multi-part providers at all. Fixed: the form now shows each part as its own labeled field per provider (GitHub: Personal access token; GitLab: Host, pre-filled `gitlab.com`, plus Personal access token; Jira: Site, Email, API token; Datadog: Site -- a `<select>` of Datadog's own six real regional API hosts, not free text -- plus API key and Application key; Sandbox: a single generic Credential field, unchanged, dev/test only), joined into the one opaque `credential` string each adapter's own `_parse_credential` expects only at submit time (`buildCredential`). Switching provider resets every field rather than carrying a stale value into a different shape (`selectProvider`), and Connect stays disabled until every field the selected provider actually requires is filled (`isCredentialComplete`) -- not merely "the credential field is non-empty," which previously let an incomplete Jira/Datadog submission reach the backend and fail with a generic authorization error instead of being caught client-side. No backend change -- the assembled `credential` string is byte-for-byte identical to what a correctly hand-typed one would have been. `ConnectorHealthPanel.test.tsx` grows from 22 to 28 cases (per-provider field-to-`credential` join proofs for GitHub/GitLab/Jira/Datadog, the Datadog site options list, the provider-switch reset, and the completeness-gated Connect button), bringing the engineering feature-test total from 119 across 11 files to 125.
