## Task 1 evidence

**Complete.** `docs/superpowers/plans/2026-08-04-phase-10-gmail-connector.md`'s Task 1: `OAuth2ConnectorAdapter` Protocol extension (`ecc.domains.engineering.connectors`), `GmailAdapter` (`ecc.domains.personal.gmail_adapter`), the OAuth initiate/callback endpoints (`ecc.domains.personal.gmail_oauth`), migration `0069_phase10_gmail_connector.py`, and `email` added to `ecc.domains.personal.domains`'s `DomainKey`/classification map at `high_stakes`.

**Protocol split, not a widened shared Protocol.** Adding `get_authorization_url`/`handle_oauth_callback` directly to the existing `ConnectorAdapter` Protocol would have broken `ConnectorRegistry.register`'s own `isinstance()` check for every already-registered adapter (`github`/`gitlab`/`jira`/`sandbox`/`datadog`), none of which implement OAuth2 -- confirmed with a live Python test before proceeding, not merely assumed from Protocol semantics. `OAuth2ConnectorAdapter` is instead a separate, additive Protocol only `GmailAdapter` satisfies. Widening `backfill()` with an optional `since` parameter is signature-sensitive under mypy's static Protocol structural typing (unlike `isinstance`'s presence-only check), so all five existing adapters' `backfill` signatures were mechanically updated to accept and ignore it.

**Registration composition-root workaround, disclosed.** `GmailAdapter` cannot be registered inside `connectors.py` itself the way every other adapter is (a same-package relative import) -- it lives in `ecc.domains.personal`, which already imports `ecc.domains.engineering.connectors`; registering the other direction would be a circular import. Registered from `main.py` instead, guarded by a membership check (`if "gmail" not in engineering_connector_registry:`) so `tests/test_production_security.py`'s `importlib.reload(ecc.main)` -- which re-executes this module's top-level code against the same persistent, never-reloaded registry singleton -- doesn't raise `AdapterAlreadyRegistered` on a second reload. Found by this task's own first CI run, not by review alone.

**Reconnecting a disconnected account reactivates it, rather than silently discarding a freshly obtained credential.** `uq_connector_accounts_workspace_provider_external_id` means a second real OAuth consent for the same Google account after a `disable`/`disconnected`/`permission_lost`/`error` state hits the callback's own `IntegrityError` handler. A naive "already connected, return the existing row" response for every conflict would silently discard the just-exchanged, allowlist-checked, valid credential -- for a `disconnected` row specifically, one whose old refresh token `GmailAdapter.disconnect()` already revoked at Google, permanently stranding the account with no reactivate/PATCH endpoint anywhere in `connector_accounts.py` to recover it. Found by a dedicated adversarial review pass (not the original implementation), fixed by branching on the existing row's `status`: an `active` row still returns as-is (the genuine passive-replay case); any other status is `UPDATE`d with the new credential, scopes and display name, `status` reset to `active`, and a `connector_account.reconnected` audit event is written. Verified directly against real Postgres via a standalone script (connect, disconnect, reconnect with a second, distinct token pair, confirm the stored credential is the new one and exactly one `reconnected` audit event exists) -- this sandbox's Python environments cannot run the `TestClient`-based test suite itself (see below).

**Revoking on every post-exchange rejection, not just some of them.** `handle_oauth_callback` has up to six distinct rejection points after a successful token exchange (missing access/refresh token, missing required scope, non-numeric `expires_in`, profile-lookup network error or non-200 status, missing `emailAddress`, non-allowlisted account) -- each one means Google has already granted a live OAuth credential that this callback goes on to reject and never persists a `connector_accounts` row for, so `disconnect()` (which needs a persisted row) can never be reached to revoke it later. An initial fix (found necessary by a dedicated adversarial security review pass, not the original implementation) added a per-branch `self._revoke_best_effort(refresh_token)` call before two of the six `raise` statements -- a second, later review pass found this incomplete: the other four branches still leaked a live, ECC-unrecorded grant. Fixed by restructuring the entire post-token-exchange body into a single `try: ... except Exception: self._revoke_best_effort(refresh_token or ""); raise` block wrapping all six branches (plus the initial presence check itself, in case a real `refresh_token` came back alongside a missing `access_token`), so the guard is structural -- any future rejection branch added inside it automatically revokes on reject, rather than depending on each new branch remembering to call it individually. Verified directly via a standalone script asserting all six rejection scenarios (plus the "no refresh_token at all" and "access_token missing but refresh_token present" edge cases) call `/revoke` with the correct token, and that the happy path does not call it at all.

**The same revoke-on-discard gap, relocated to the router's own reconnect-race handling.** `handle_oauth_callback`'s revoke-on-rejection fix above only covers grants the *adapter itself* rejects. Round 4 review found the same bug class one layer up: `gmail_oauth_callback_endpoint`'s `IntegrityError` handler (see the reactivation paragraph above) discarded/overwrote a real Google grant in two places without revoking it -- its `active`-row branch returned the existing row and dropped the just-obtained new grant on the floor; its reactivate branch overwrote `encrypted_credentials` without revoking the prior stored grant it was replacing (only guaranteed already-revoked for a `disconnected`/`permission_lost` row, not for `error`/`rate_limited`). Fixed by calling `_adapter.disconnect(...)` (best-effort, never raises) on whichever credential is being dropped in each branch -- the new grant in the `active` case, the row's own pre-update credential (decrypted for this one purpose) in the reactivate case. Verified via `test_oauth_callback_revokes_the_discarded_grant_when_racing_an_active_row` (a genuinely distinct second consent, its own new token pair, while the row stays `active`) and an added assertion on `test_oauth_callback_reactivates_disconnected_account` (the prior stored token is revoked on reactivation), both asserting the correct token reaches `/revoke` via the mocked transport's `revoked_tokens` capture.

**Round 5 hardening: the shape `_unpack_credential` was trusted to return, and one untested fallback path.** Round 5 review found two smaller gaps in round 4's own diff. First, `GmailAdapter.disconnect()` (and `refresh_permissions()`, sharing the same helper) only caught `(ValueError, TypeError)` around `_unpack_credential`; valid-JSON-but-non-object input (a list, `null`, a bare number) decoded successfully and then raised an uncaught `AttributeError` on the first `.get(...)` -- unreachable through this codebase's own `_pack_credential` writer, but round 4's two new bare `_adapter.disconnect(...)` call sites in `gmail_oauth.py` (unlike `disable_connector_endpoint`'s existing broad `except Exception` wrapper) would have let that propagate as an unhandled 500 mid-transaction, with a `FOR UPDATE` lock held. Fixed by having `_unpack_credential` itself validate the decoded shape and raise `TypeError` on a mismatch, so both existing callers' narrow `except` already covers it -- no call-site changes needed. Second, the reactivate branch's own `except Exception: old_credential = None` fallback (an undecryptable stored credential must not block reactivation) had no test, despite `disable_connector_endpoint` already having dedicated coverage for the identical scenario (`test_disable_succeeds_when_credential_cannot_be_decrypted`). Added `test_oauth_callback_reactivates_even_when_prior_credential_cannot_be_decrypted`, mirroring that precedent.

**Round 6 hardening: the same "shape trusted without validation" gap, one call earlier.** Round 6 review found `handle_oauth_callback`'s `body = response.json(); access_token = body.get(...)` (the token-exchange response) sat *ahead* of the revoke-on-reject `try` guard, not inside it -- a 200 response with a non-JSON body (`response.json()` raising `json.JSONDecodeError`, a `ValueError`) or a JSON body that isn't an object (`body.get(...)` then raising `AttributeError`) would have escaped uncaught past both the guard (skipping revoke-on-reject for whatever grant Google may have actually issued) and the router's `AdapterAuthorizationError`-only catch (surfacing as an unhandled 500 outside the app's structured error envelope) -- the identical bug class round 5 closed for `_unpack_credential`, one call earlier in the same method. Fixed by moving the parsing inside the existing guard and validating the decoded shape is a `dict`, raising `AdapterAuthorizationError` (not letting the underlying exception type escape) on either failure; the same treatment was applied proactively to the profile-lookup response body for consistency, though review had judged that one already covered by the guard's exception handling (only its own envelope-shape gap was new). Verified via four new tests (non-JSON and non-object token responses, non-object profile response, `revoked_tokens` asserted where a token had already been exchanged). The same round found two smaller gaps: `_unpack_credential`'s round-5 `TypeError` branch was untested through its real callers (`refresh_permissions`/`disconnect`), only in isolation, and `authorize`'s single-line unconditional raise had no test at all -- both closed with dedicated tests. It also found `gmail_oauth.py`'s 422 error response reinvented its own `[:500]` truncation instead of reusing `connector_accounts.py`'s already-established `_sanitize_adapter_error` (a `300`-char cap the codebase already applies to every other adapter-derived error string surfaced to a client) -- switched to the shared helper for consistency; no functional/security change (adapter error text is contractually never supposed to contain credentials either way).
