## Task 1 evidence

**Complete.** `docs/superpowers/plans/2026-08-04-phase-10-gmail-connector.md`'s Task 1: `OAuth2ConnectorAdapter` Protocol extension (`ecc.domains.engineering.connectors`), `GmailAdapter` (`ecc.domains.personal.gmail_adapter`), the OAuth initiate/callback endpoints (`ecc.domains.personal.gmail_oauth`), migration `0069_phase10_gmail_connector.py`, and `email` added to `ecc.domains.personal.domains`'s `DomainKey`/classification map at `high_stakes`.

**Protocol split, not a widened shared Protocol.** Adding `get_authorization_url`/`handle_oauth_callback` directly to the existing `ConnectorAdapter` Protocol would have broken `ConnectorRegistry.register`'s own `isinstance()` check for every already-registered adapter (`github`/`gitlab`/`jira`/`sandbox`/`datadog`), none of which implement OAuth2 -- confirmed with a live Python test before proceeding, not merely assumed from Protocol semantics. `OAuth2ConnectorAdapter` is instead a separate, additive Protocol only `GmailAdapter` satisfies. Widening `backfill()` with an optional `since` parameter is signature-sensitive under mypy's static Protocol structural typing (unlike `isinstance`'s presence-only check), so all five existing adapters' `backfill` signatures were mechanically updated to accept and ignore it.

**Registration composition-root workaround, disclosed.** `GmailAdapter` cannot be registered inside `connectors.py` itself the way every other adapter is (a same-package relative import) -- it lives in `ecc.domains.personal`, which already imports `ecc.domains.engineering.connectors`; registering the other direction would be a circular import. Registered from `main.py` instead, guarded by a membership check (`if "gmail" not in engineering_connector_registry:`) so `tests/test_production_security.py`'s `importlib.reload(ecc.main)` -- which re-executes this module's top-level code against the same persistent, never-reloaded registry singleton -- doesn't raise `AdapterAlreadyRegistered` on a second reload. Found by this task's own first CI run, not by review alone.

**Reconnecting a disconnected account reactivates it, rather than silently discarding a freshly obtained credential.** `uq_connector_accounts_workspace_provider_external_id` means a second real OAuth consent for the same Google account after a `disable`/`disconnected`/`permission_lost`/`error` state hits the callback's own `IntegrityError` handler. A naive "already connected, return the existing row" response for every conflict would silently discard the just-exchanged, allowlist-checked, valid credential -- for a `disconnected` row specifically, one whose old refresh token `GmailAdapter.disconnect()` already revoked at Google, permanently stranding the account with no reactivate/PATCH endpoint anywhere in `connector_accounts.py` to recover it. Found by a dedicated adversarial review pass (not the original implementation), fixed by branching on the existing row's `status`: an `active` row still returns as-is (the genuine passive-replay case); any other status is `UPDATE`d with the new credential, scopes and display name, `status` reset to `active`, and a `connector_account.reconnected` audit event is written. Verified directly against real Postgres via a standalone script (connect, disconnect, reconnect with a second, distinct token pair, confirm the stored credential is the new one and exactly one `reconnected` audit event exists) -- this sandbox's Python environments cannot run the `TestClient`-based test suite itself (see below).

**Revoking on every post-exchange rejection, not just some of them.** `handle_oauth_callback` has up to six distinct rejection points after a successful token exchange (missing access/refresh token, missing required scope, non-numeric `expires_in`, profile-lookup network error or non-200 status, missing `emailAddress`, non-allowlisted account) -- each one means Google has already granted a live OAuth credential that this callback goes on to reject and never persists a `connector_accounts` row for, so `disconnect()` (which needs a persisted row) can never be reached to revoke it later. An initial fix (found necessary by a dedicated adversarial security review pass, not the original implementation) added a per-branch `self._revoke_best_effort(refresh_token)` call before two of the six `raise` statements -- a second, later review pass found this incomplete: the other four branches still leaked a live, ECC-unrecorded grant. Fixed by restructuring the entire post-token-exchange body into a single `try: ... except Exception: self._revoke_best_effort(refresh_token or ""); raise` block wrapping all six branches (plus the initial presence check itself, in case a real `refresh_token` came back alongside a missing `access_token`), so the guard is structural -- any future rejection branch added inside it automatically revokes on reject, rather than depending on each new branch remembering to call it individually. Verified directly via a standalone script asserting all six rejection scenarios (plus the "no refresh_token at all" and "access_token missing but refresh_token present" edge cases) call `/revoke` with the correct token, and that the happy path does not call it at all.

**The same revoke-on-discard gap, relocated to the router's own reconnect-race handling.** `handle_oauth_callback`'s revoke-on-rejection fix above only covers grants the *adapter itself* rejects. Round 4 review found the same bug class one layer up: `gmail_oauth_callback_endpoint`'s `IntegrityError` handler (see the reactivation paragraph above) discarded/overwrote a real Google grant in two places without revoking it -- its `active`-row branch returned the existing row and dropped the just-obtained new grant on the floor; its reactivate branch overwrote `encrypted_credentials` without revoking the prior stored grant it was replacing (only guaranteed already-revoked for a `disconnected`/`permission_lost` row, not for `error`/`rate_limited`). Fixed by calling `_adapter.disconnect(...)` (best-effort, never raises) on whichever credential is being dropped in each branch -- the new grant in the `active` case, the row's own pre-update credential (decrypted for this one purpose) in the reactivate case. Verified via `test_oauth_callback_revokes_the_discarded_grant_when_racing_an_active_row` (a genuinely distinct second consent, its own new token pair, while the row stays `active`) and an added assertion on `test_oauth_callback_reactivates_disconnected_account` (the prior stored token is revoked on reactivation), both asserting the correct token reaches `/revoke` via the mocked transport's `revoked_tokens` capture.

**Round 5 hardening: the shape `_unpack_credential` was trusted to return, and one untested fallback path.** Round 5 review found two smaller gaps in round 4's own diff. First, `GmailAdapter.disconnect()` (and `refresh_permissions()`, sharing the same helper) only caught `(ValueError, TypeError)` around `_unpack_credential`; valid-JSON-but-non-object input (a list, `null`, a bare number) decoded successfully and then raised an uncaught `AttributeError` on the first `.get(...)` -- unreachable through this codebase's own `_pack_credential` writer, but round 4's two new bare `_adapter.disconnect(...)` call sites in `gmail_oauth.py` (unlike `disable_connector_endpoint`'s existing broad `except Exception` wrapper) would have let that propagate as an unhandled 500 mid-transaction, with a `FOR UPDATE` lock held. Fixed by having `_unpack_credential` itself validate the decoded shape and raise `TypeError` on a mismatch, so both existing callers' narrow `except` already covers it -- no call-site changes needed. Second, the reactivate branch's own `except Exception: old_credential = None` fallback (an undecryptable stored credential must not block reactivation) had no test, despite `disable_connector_endpoint` already having dedicated coverage for the identical scenario (`test_disable_succeeds_when_credential_cannot_be_decrypted`). Added `test_oauth_callback_reactivates_even_when_prior_credential_cannot_be_decrypted`, mirroring that precedent.

**Round 6 hardening: the same "shape trusted without validation" gap, one call earlier.** Round 6 review found `handle_oauth_callback`'s `body = response.json(); access_token = body.get(...)` (the token-exchange response) sat *ahead* of the revoke-on-reject `try` guard, not inside it -- a 200 response with a non-JSON body (`response.json()` raising `json.JSONDecodeError`, a `ValueError`) or a JSON body that isn't an object (`body.get(...)` then raising `AttributeError`) would have escaped uncaught past both the guard (skipping revoke-on-reject for whatever grant Google may have actually issued) and the router's `AdapterAuthorizationError`-only catch (surfacing as an unhandled 500 outside the app's structured error envelope) -- the identical bug class round 5 closed for `_unpack_credential`, one call earlier in the same method. Fixed by moving the parsing inside the existing guard and validating the decoded shape is a `dict`, raising `AdapterAuthorizationError` (not letting the underlying exception type escape) on either failure; the same treatment was applied proactively to the profile-lookup response body for consistency, though review had judged that one already covered by the guard's exception handling (only its own envelope-shape gap was new). Verified via three new tests at the time (non-JSON and non-object token responses, non-object profile response, `revoked_tokens` asserted where a token had already been exchanged) -- round 7 found this paragraph and the test file's own docstring had both overstated that as "four"/"either endpoint", when the non-JSON-profile-response cell was actually still missing; see the round-7 paragraph below for the fix. The same round found two smaller gaps: `_unpack_credential`'s round-5 `TypeError` branch was untested through its real callers (`refresh_permissions`/`disconnect`), only in isolation, and `authorize`'s single-line unconditional raise had no test at all -- both closed with dedicated tests. It also found `gmail_oauth.py`'s 422 error response reinvented its own `[:500]` truncation instead of reusing `connector_accounts.py`'s already-established `_sanitize_adapter_error` (a `300`-char cap the codebase already applies to every other adapter-derived error string surfaced to a client) -- switched to the shared helper for consistency; no functional/security change (adapter error text is contractually never supposed to contain credentials either way).

**Round 7 hardening: `scope`/`emailAddress` were the two response fields with no type guard, unlike every sibling field.** Round 7 review found `granted_scope_str = body.get("scope", "")` and `email_address = profile_body.get("emailAddress")` (checked only via `if not email_address:`) were the sole fields in the token/profile response bodies never validated for shape, unlike `access_token`/`refresh_token`/`expires_in` (all explicitly checked) and the response bodies themselves (round 6). `.get(key, default)`'s default only applies when the key is *absent* -- a `"scope": null` response (key present, value `None`) reached `.split()` uncaught; a non-string truthy `emailAddress` (e.g. a JSON number) passed the bare falsiness check and reached `is_account_allowed`'s own `.strip()` uncaught. Both are inside the revoke-on-reject guard (so revocation still fired correctly) but the bare `raise` re-raised the original `AttributeError`, unconverted, past the router's `AdapterAuthorizationError`-only catch -- the identical envelope-bypass failure mode rounds 5-6 closed for the response bodies' own shape, one field deeper. Fixed with explicit type checks raising `AdapterAuthorizationError` on either mismatch. The same round also found and closed the test-completeness gap noted in the round-6 paragraph above (the missing non-JSON-profile-response test).

**Round 7, second pass: the one branch of the reconnect-race handler not revoking its discarded credential.** `gmail_oauth_callback_endpoint`'s `IntegrityError` handler has three branches (see the reactivation and round-4 paragraphs above): `existing is None` (re-`SELECT` after the failed INSERT finds no row), `existing["status"] == "active"`, and the reactivate `UPDATE`. The latter two both revoke whichever credential they discard/overwrite (round 4); the `existing is None` branch raised its `409` without ever revoking `authorization.credential` -- the same bug class, in the one place it was still open. Not currently reachable in production (nothing in this codebase hard-deletes a `connector_accounts` row, and Postgres guarantees the conflicting row's own transaction already committed before the `IntegrityError` fires, so the re-`SELECT` should always find it), so this closes a defense-in-depth gap rather than a live leak -- but the fix costs nothing and removes a branch that would silently regress the moment any future admin/cleanup path adds a delete. Fixed by adding the same `_adapter.disconnect(...)` call before the `409`. Not independently tested (the branch requires a row to vanish mid-transaction, not reproducible through the real HTTP flow without directly manipulating another session's uncommitted state); correctness follows by the same pattern already dynamically verified for its two sibling branches. (Round 12 replaced this branch's own standalone `disconnect(...)` call, along with every other statement-specific revoke call in the `IntegrityError` handler, with one wide guard around the entire handler -- see that round's own paragraph below; round 14 review found this paragraph had gone stale describing an implementation detail round 12 removed, though the underlying guarantee -- this branch's discarded grant is still revoked -- was never actually broken.)

**Round 8: an infinite/huge `expires_in` skipped revoke-on-reject entirely, not merely the error envelope.** Round 8 review found `float(expires_in)` (validated for presence and numeric-coercibility, inside the revoke-on-reject guard) accepts `inf`/`nan` (`json.loads` itself accepts the non-strict `Infinity`/`NaN` literals by default) or any ordinary huge integer without complaint -- but the resulting Unix timestamp then made `datetime.fromtimestamp(...)` raise `OverflowError`/`ValueError` at `_pack_credential`'s call site on line ~360, which (unlike every other value this method validates) sits on the *success* path, after the guard has already exited normally. This is a step beyond the recurring "escapes the error envelope" bug class rounds 5-7 closed: here the guard's own revoke-on-reject never fires at all, silently leaking the just-obtained grant, in addition to the uncaught-exception-type problem. Fixed by performing the same `datetime.fromtimestamp` conversion once, speculatively, inside the guard right after computing `expires_at`, converting `OverflowError`/`OSError`/`ValueError` into `AdapterAuthorizationError` there -- using the exact call that will run for real later, not a separately-chosen numeric bound that could itself drift out of sync with what `fromtimestamp` actually accepts. The same round also found and corrected an overclaim in the test file's own docstring (item 3 previously implied every post-exchange rejection branch had a dedicated route-level test; only two representative branches ever did, which is sufficient since the router's `except AdapterAuthorizationError` clause is generic, not branch-specific) -- added one more route-level test (missing required scope) and reworded the claim to state the actual, sufficient intent. Verified directly: mocked `/token` responses with `expires_in` set to `float("inf")` and to `999999999999999999999` both now raise `AdapterAuthorizationError` and correctly call `/revoke` with the real refresh token, and the happy path is unaffected. The same round's architecture pass found `access_token`/`refresh_token` were the last two fields in the token response still checked only for truthiness rather than type, unlike `scope`/`emailAddress` (round 7) -- closed for consistency (this pair never actually crashed anywhere, unlike those two; a non-string value would just be silently embedded in the `Bearer` header and persisted credential).

**Round 9: the last field-typing gap, `expires_in` accepting a JSON boolean.** `bool` is a subtype of `int` in Python, so `"expires_in": true`/`false` passed both the presence check and `float(expires_in)`'s numeric coercion silently (`float(True) == 1.0`) -- the one field in the token-response body still not rejecting a wrong-but-truthy type after rounds 7-8 closed `scope`/`emailAddress`/`access_token`/`refresh_token`. Fixed with an explicit `isinstance(expires_in, bool)` rejection alongside the existing presence check. Review also raised, as a non-blocking style observation rather than a finding, that the now-repeated `isinstance(x, str) or not x` shape across three fields could be consolidated into a shared helper -- not applied, since the diff cost of a refactor this late in the review loop outweighs the marginal benefit on a module this size. Verified directly: a mocked `/token` response with `expires_in: true` now raises `AdapterAuthorizationError` and correctly calls `/revoke`.

**Round 10: two issues in `gmail_oauth.py` outside the field-typing pattern rounds 5-9 exhausted, both found by broadening the review's focus deliberately.** First, `gmail_oauth_callback_endpoint` called `session.rollback()` (not `.close()`) before `handle_oauth_callback`'s two slow, sequential outbound Google HTTP calls (up to ~20s combined) -- `rollback()` ends the transaction but does not release the connection back to the app-wide pool (`pool_size=5 + max_overflow=10 = 15` total), so this endpoint held a pooled connection idle for that whole window, then opened a *second* connection (`SessionFactory()`) for the DB write while the first was still checked out. This directly contradicted an established, explicitly-documented sibling fix in the same module family -- `connector_accounts.py`'s `create_connector_endpoint` calls `session.close()` before its own analogous slow adapter call specifically to avoid "the exact pool-exhaustion risk `/sync` was restructured to avoid" (that function's own docstring) -- which `gmail_oauth.py` never adopted for its own slow external call. A modest handful of concurrent/slow Gmail OAuth completions (a team onboarding rollout, or simply Google's API being briefly slow -- a real, non-adversarial third-party dependency risk) could exhaust the pool and fail every other endpoint in the app, not just this one. Fixed by replacing `session.rollback()` with `session.close()`, mirroring the sibling fix exactly (`session` is never referenced again after that point in the function). Second, the `INSERT`'s `except IntegrityError:` handler (three branches, all revoking correctly -- see the round-4/7 paragraphs above) had no sibling catching any *other* exception during that same `INSERT`: a dropped connection, a deadlock, or the app's own 5-second `statement_timeout` firing under transient load would propagate uncaught, orphaning the just-obtained, never-persisted Google grant without revoking it -- the same "obtained but never revoked" bug class, in a spot the field-typing-focused rounds never examined. Fixed with a sibling `except Exception:` that revokes `authorization.credential` before re-raising (Python's exception-handling semantics mean this cannot double-fire for the `IntegrityError` branch's own already-correct revokes, since an exception raised from within an `except` clause does not re-enter that same `try` statement's other `except` clauses). Both verified directly against real Postgres via standalone scripts (the first, by re-running every existing reconnect-race/reactivation scenario end to end and confirming unchanged behavior; the second, by monkeypatching `Session.execute` to raise `OperationalError` mid-`INSERT` and confirming the grant is revoked and no row is persisted). At the time, neither was given a dedicated pytest test -- disclosed rather than silently left uncovered, reasoning that the second would need "a mocking pattern this codebase's test suite doesn't otherwise use." Round 12 review found that reasoning didn't actually hold once tried: `monkeypatch.setattr` on `sqlalchemy.orm.Session.execute` is the exact same module-level-swap idiom this file already uses repeatedly for `_adapter`, just applied one layer lower -- see `test_oauth_callback_revokes_new_grant_when_insert_raises_unexpected_error` in the test file, added in round 12. The `session.close()` pool-release fix remains standalone-script-only; a real pytest proof of *that* one genuinely does need connection-pool contention under concurrency (the `_SlowAdapter`/`threading.Event` pattern `test_engineering_connectors_postgres.py` already establishes), which was deliberately not added given the real timing-flakiness risk that adds in this CI environment -- a considered trade-off, not an oversight.

**Round 11: the reactivation branch's own subsequent writes were the one surface round 10's `except Exception:` fix couldn't reach.** Round 10's fix revokes on any exception raised inside the `try:` that wraps the `INSERT` itself -- but Python's except-clause matching only applies to exceptions raised in the *associated* `try:` body, so once `except IntegrityError:` starts executing, nothing raised from *within* that block (including the reactivation branch's own `UPDATE`/re-`SELECT`/audit-write sequence, which persists `authorization.credential` -- the new grant -- after the old one is already revoked) is ever re-matched against that outer sibling. A failure anywhere in that sequence (the same dropped-connection/deadlock/`statement_timeout` classes round 10 named, now including a concurrent `/disable` or `/sync` holding a lock on the same row) would orphan the new grant exactly like the round-10 gap did for the `INSERT`, undetected by round 10's own fix because it lives one exception-handling layer deeper. The other two branches (`existing is None` and `existing["status"] == "active"`) don't have this gap -- both revoke the credential they discard *before* any further DB call, so a later failure in either has nothing left to leak. Fixed with a second, nested `try/except` scoped to just the reactivation branch's write sequence, revoking `authorization.credential` before re-raising. Verified via the same monkeypatch-`Session.execute` technique against real Postgres, this time failing the reactivation `UPDATE` specifically: both the old credential (revoked correctly, unaffected) and the new orphaned one are revoked, and the row rolls back cleanly to its prior `disconnected` state rather than being left half-updated. (Round 12 replaced this nested `try/except`'s narrower scope with one wide guard around the entire `IntegrityError` handler -- see that round's own paragraph below -- and round 12 also gave this exact scenario a dedicated pytest test, `test_oauth_callback_revokes_new_grant_when_reactivation_update_raises`, superseding the "standalone script only" state described above.)

**Round 12: two more unprotected statements in the same `IntegrityError` handler, closed by widening the guard instead of patching a fourth spot.** Two independent review passes, run in parallel, each found a distinct remaining gap in the exact "obtained but never revoked" bug class rounds 4/7/10/11 had been closing here piece by piece. First: the handler's own initial re-`SELECT ... FOR UPDATE` (the very first statement inside `except IntegrityError:`, before any of its three branches runs) had never been wrapped by anything -- not round 10's guard (scoped to the `INSERT`, a sibling `try`) and not round 11's (scoped only to the reactivation branch's own follow-on writes) -- so a failure there orphaned `authorization.credential` before any branch's own revoke logic had even run. Second: the plain first-time-connect success path's own tail (`get_connector_account` + `_write_side_effects`, run only when the `INSERT` succeeds with no `IntegrityError` at all) is a sibling of the whole `try`/`except` construct, guarded by neither -- unlike the reactivation branch, which round 11 gave its own guard for the structurally identical "persist a row, build a response, write an audit event" shape, the primary create path never received the same treatment. Both are as realistic as every prior round's own justification: `connector_accounts.py` uses the identical `FOR UPDATE` locking pattern for `/disable`/`/sync` on this same table, so a concurrent call holding the lock, or the app's own `statement_timeout`, can trigger either. Fixed two ways: the `IntegrityError` handler was restructured into one wide `try` wrapping the re-`SELECT` and every branch's own logic, closing with a single `except Exception:` that revokes `authorization.credential` -- deliberately one guard covering the whole handler rather than a fourth statement-specific patch, since three consecutive rounds each finding "one more unprotected statement" here is itself evidence that approach doesn't converge; and the success-path tail got its own matching `try/except Exception:` guard, mirroring the reactivation branch's own shape. Both verified directly against real Postgres via standalone scripts (failing the re-`SELECT` during an active-row race, and failing the audit-event write on the plain success path) -- and, per the round-10 paragraph's update above, real pytest coverage for the re-`SELECT` case was added in the same round (`test_oauth_callback_revokes_new_grant_when_integrity_error_handler_reselect_raises`). Round 13 review found the success-path-tail case had been left without its own test on the (weaker than it first appeared) reasoning that it "exercises the identical guard shape the other three tests already prove correct" -- that reasoning verifies the shared mechanism, not that this specific guard is correctly wired at this specific call site. Closed with `test_oauth_callback_revokes_new_grant_when_success_path_tail_raises`, failing `_write_side_effects`'s own `INSERT INTO audit_events` statement (the one write unique to this path among the four now-tested guards, since only the reactivation and plain-success paths ever call it and each test exercises only one).

**Round 15: the callback endpoint's own mutations were invisible to the app's mutation rate limiter.** `backend/ecc/http_security.py`'s `mutation_rate_limit_middleware` treats `GET` requests as free/unlimited reads by default -- correct for nearly every route, since CSRF already blocks the cross-site vector for state-changing requests -- with a single documented, narrow exception: `_MUTATING_GET_PATHS`, an explicit allow-list of `GET` routes that genuinely do mutate (previously just `/api/v1/engineering/metrics`, a Phase 6 review finding). `gmail_oauth_callback_endpoint` is unavoidably a `GET` (Google's OAuth2 authorization-code-grant redirect leaves no other option) but performs real writes on every call -- an `INSERT`/`UPDATE` on `connector_accounts`, an `INSERT` on `audit_events`, an `INSERT` on `event_outbox` -- and two real outbound HTTPS calls to Google, yet was never added to `_MUTATING_GET_PATHS`, making it invisible to the only rate limiter registered in the app. Because `_verify_state` (CSRF protection for this endpoint) checks the `state` value's HMAC signature and expiry but never marks it consumed -- only Google's own single-use `code` is -- a same-origin, authenticated, Gmail-allowlisted caller holding one still-valid `state` (10-minute TTL) could loop `GET /oauth/callback?code=garbage&state=<that state>` unbounded: each call reaches `GmailAdapter.handle_oauth_callback`'s real, blocking, up-to-10-second `httpx` call to Google's token endpoint, and since the endpoint is a plain `def` (not `async def`), enough concurrent slow requests can starve the shared AnyIO threadpool that every other synchronous route in the app also depends on, and/or draw enough traffic against Google's token endpoint from the backend's own `client_id`/egress IP to risk Google-side throttling of legitimate future exchanges -- the identical "mutating GET invisible to the mutation rate limiter" bug class the codebase's own Phase 6 review already found and fixed once, reopened here for a second endpoint. Fixed by adding `/api/v1/personal/gmail/oauth/callback` to `_MUTATING_GET_PATHS`, with an explanatory comment mirroring the existing metrics-endpoint entry's style. Verified statically (`py_compile`/`ruff check`/`ruff format --diff` all clean) and by inspection of `_is_mutation_route`'s exact-path-match logic against the router's actual mounted path (`APIRouter(prefix="/api/v1/personal/gmail")` + `@router.get("/oauth/callback")`); checked the existing test suite for interaction effects -- no test in `tests/test_gmail_connector_postgres.py` calls the callback endpoint more than twice within a single test, far under the shared `RATE_LIMIT_MAX_REQUESTS = 40`-per-60s threshold, so no existing test needed changes. Architecture review run in parallel the same round reported zero findings.
