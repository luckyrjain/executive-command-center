## Task 3 evidence

**Complete.** `travel` is `standard`-classified, identical in enablement/CRUD to `habits`/`learning` -- no new table or migration. What Task 3 actually added: `travel` is the design doc's own "first domain with meaningfully time-ranged records" -- `domain_records.effective_at` already existed per record, but nothing previously let a caller query by it. `GET /personal/records` (`ecc.domains.personal.domains.list_records_endpoint`) gains two optional query parameters, `effective_from`/`effective_until` (inclusive on both bounds), filtering on `effective_at` -- generic on the endpoint, not `travel`-specific, matching this activation's existing "a caller names a `domain_key`, never a domain-specific code path" convention. `tests/test_personal_travel_postgres.py` (5 tests) proves enable/independent-domain isolation, the `trip` `record_type` convention (create/list/get/patch), the new date-range filter (a range covering only one trip, an inclusive exact-instant boundary match, from-only/until-only bounds, and an empty-result range), and whole-domain export/delete. `docs/phases/phase-007/DATA-MODEL.md`'s "Task 3 status" section documents the `trip` `record_type` payload convention and clarifies retention itself is unchanged (`standard` classification stays retained indefinitely -- "retention-by-date-range" means the record's own date range is now queryable, not that records expire on a timer). `docs/phases/phase-007/API-SCHEMAS.md`'s own Task 3 section has the endpoint-level detail.

**Verified.** `ruff check`/`ruff format --check`/`mypy backend` clean. `tests/test_personal_travel_postgres.py` + `tests/test_personal_learning_postgres.py` + `tests/test_personal_domains_postgres.py` -- 36 passed against real PostgreSQL, confirming the date-range filter addition does not regress either prior standard domain's own CRUD/export/delete paths.

## Task 4 evidence

**Complete.** `relationships` is `sensitive`-classified -- the first domain to actually populate `ecc.domains.personal.crypto` (Fernet, `ECC_PERSONAL_DATA_ENCRYPTION_KEY`, mirroring `ecc.domains.engineering.crypto`'s shape but `str`-typed since `domain_records.payload` is JSONB) rather than leave it deferred. `_ENCRYPTED_FIELD_NAMES_BY_RECORD_TYPE` (structurally present since Task 1, exercised against nothing until now) gains real entries: `contact`/`interaction` record types' own `notes` field. `_encrypt_payload`/`_decrypt_payload` wrap encryption immediately before `INSERT`/`UPDATE` and decryption only for single-record response paths (create/get/patch), leaving `list_records_endpoint`'s pre-existing `_redact_payload` untouched for list/summary views.

**Two real gaps found and fixed before this was correct, not merely functional.** (1) `export_domain_endpoint` (`export_deletion.py`) read `domain_records.payload` directly, bypassing decryption -- for `relationships` this would have exported ciphertext instead of the human-readable export `DOMAIN-PRIVACY-CONTRACT.md` requires; fixed by decrypting each record's payload before it enters the export response (an explicit, user-initiated export of the owner's own data is exactly the "single-purpose request" design doc Decision 3 means). (2) The idempotency cache (`idempotency_records.response_body`) would otherwise have persisted the decrypted `notes` value verbatim on every create/update, defeating encryption-at-rest for that table entirely -- fixed by building the response stored via `store_idempotency` from the still-encrypted row, decrypting only the copy actually returned to the caller (and any later cache-hit replay, decrypted at read time, never written back).

**Settings validation.** `ecc.config.Settings.personal_data_encryption_key` (`ECC_PERSONAL_DATA_ENCRYPTION_KEY`) added, structurally validated outside development by a new `_validate_personal_data_encryption_key`, mirroring `_validate_connector_token_encryption_key`'s exact checks (missing/placeholder/malformed-base64/wrong-decoded-length). `tests/test_production_security.py`'s shared production-settings fixture updated with a valid key so existing tests keep passing, plus four new dedicated rejection tests for the new key and a fix to `_reload_main`/`restore_main_module` (three real-app-reload tests were failing because the reloaded app now requires this key in a production-classified environment).

**Tests.** `tests/test_personal_relationships_postgres.py` (9 tests) proves: enable/independent-domain isolation; `contact`/`interaction` record CRUD; `notes` is genuinely ciphertext in `domain_records.payload` at rest (verified via direct SQL against the table, not just the API response shape); list responses redact `notes` to a placeholder while get/create/patch return it decrypted; a PATCH re-encrypts new `notes` content; an idempotent replay returns the correct decrypted content to the caller while the persisted `idempotency_records` row itself never holds the decrypted value (verified via direct SQL); whole-domain export returns decrypted `notes` and deletion still removes the encrypted records.

**Verified.** `ruff check` clean (this sandbox's globally-installed `ruff` is newer than the repo's pinned 0.12.3 and has a real formatter bug that corrupts a multi-exception `except` clause under `ruff format` -- verified the affected line by hand and confirmed `ruff check`, which CI actually runs, passes cleanly). `mypy backend` clean (155 source files). `tests/test_personal_relationships_postgres.py` + `tests/test_personal_domains_postgres.py` + `tests/test_personal_learning_postgres.py` + `tests/test_personal_travel_postgres.py` + `tests/test_production_security.py` -- 92 passed, 2 skipped. Full backend suite (excluding the two live-Ollama files and the known pre-existing sandbox-load-sensitive performance-budget test files) -- 1423 passed, 9 skipped, no failures outside that already-documented flaky category.

## Task 5 evidence (part 2 of 2)

**Complete: `personal.generate_insight`, the third Phase 4 task type, the first real consumer of Task 5 part 1's grants.** `personal.get_insight_sources` (`ecc.domains.personal.insight_tools`, new module) is the task's own required-input tool: refuses to read any requested source domain that is not both currently enabled and covered by an active, non-revoked, non-expired grant (`purpose='insight_generation'`) -- missing either for even one requested domain fails the whole call, never a partial read. `granted_categories` further narrows which `record_type`s are readable per domain; every returned record's payload is decrypted (`domains.decrypt_record_payload`), never the list-view redaction placeholder.

**`validator.PersonalInsightOutput`** (`kind: Literal["trend", "correlation"]`, `title`, `explanation_text`, `cited_record_ids`, `source_period`, `missing_data`, `confidence`, `limitations`, `professional_referral_note`) mirrors `ExplainItemOutput`'s strict, `extra="forbid"` shape. `check_personal_insight_grounding` layers two checks: ordinary citation grounding (identical pattern to the other two task types), plus a second, conditional check -- `professional_referral_note` must be non-empty whenever any source domain the tool returned is `high_stakes`-classified (`GroundingFailure.reason` widened with a second value, `missing_professional_referral`, rather than a new type). No numeric score/ranking field exists anywhere on the schema -- `INSIGHT-CONTRACT.md`'s "no relationship-health score" holds by omission.

**Wiring**: `runtime.py` (`TASK_PORTS["personal.generate_insight"]`, tool input/output models, `_prepare_personal_insight_request`, widened `_check_grounding`/`_evidence_of`), `router.py` (`TASK_REQUIREMENTS["personal.generate_insight"]`, initial conservative `timeout_seconds=40.0`/`max_output_tokens=600`, disclosed as not yet tuned against a live-model measurement history the way `meeting.prep_summary`'s own numbers are), `evaluation.py` (`_OUTPUT_TEXT_FIELD`, `_LATENCY_P95_CEILING_SECONDS_BY_TASK_TYPE`, a third `run_evaluation` synthetic-source branch with its own per-example insert/delete helpers -- necessary because `personal_domains`' `UNIQUE(workspace_id, owner_id, domain_key)` would otherwise conflict across this dataset's four examples that reuse `domain_key='habits'`), `prompts.py` (`_GATED_PROMPT_IDS`/`_GATED_PROMPT_ID_TASK_TYPES`).

**Migrations**: `0057_phase7_insight.py` (tool/prompt/routing-policy rows, mirroring `0034_phase4_meeting_prep.py`'s template), `0058_phase7_insight_eval.py` (the 10-example evaluation dataset, mirroring `0035_phase4_meeting_eval.py`'s template -- no deterministic-id assignment step needed, since this task type's grounding check validates against real `uuid4()` ids assigned at insertion time, not predetermined ones), `0059_phase7_insight_feedback.py` (`personal_insights.professional_referral_note`, the new `personal_insight_feedback` table, `personal_insights`' own new `UNIQUE(workspace_id, id)` constraint). **Real bug caught locally, not by CI**: the first draft of these three revision id strings (`0058_phase7_personal_insight_eval`, `0059_phase7_personal_insight_feedback`) exceeded `alembic_version.version_num`'s `VARCHAR(32)` column, surfaced immediately by a real `alembic upgrade head` run against local Postgres (`psycopg.errors.StringDataRightTruncation`) -- fixed by shortening both (and the sibling `0057` id, for a consistent naming scheme) to fit, verified by a full `upgrade head` -> `downgrade -1 -1 -1` -> `upgrade head` round-trip.

**Production call site**: `POST /personal/insights/generate` (`ecc.domains.personal.ai_insights`, new module), gated behind `config.py:personal_ai_insight_generation_enabled` (default `False`). Fail-open, mirroring `meeting_prep.py:_compute_enrichment`'s identical discipline. `source_period_start`/`source_period_end` are computed from the real `effective_at` of the cited `domain_records`, never taken from the model's own free-text `source_period` field, so a hallucinated date range can never reach the DB's `NOT NULL` structural columns. `POST /personal/insights/{id}/feedback` (`ecc.domains.personal.habits`) writes only to `personal_insight_feedback`, which has no `kind` column -- structurally incapable of rewriting an insight's own `kind`.

## Task 6 evidence

**Complete: `health` domain, the first `high_stakes`-classified domain onboarded.** No new table or migration -- `health` reuses Task 1's generic `domain_records`/consent/grant framework exactly like every prior domain, with `RETENTION-*` and `professional_referral_note` mechanisms that were previously only structurally present (an unenforced column since Task 1's migration `0054`, a conditional-schema field since Task 5 part 2) now genuinely exercised end to end for the first time against real data instead of synthetic evaluation fixtures.

**Per-record retention acknowledgement enforced for real.** `RecordCreateRequest` gains `retention_acknowledged: bool = false`; `create_record_endpoint` rejects a `high_stakes`-domain record with no acknowledgement (`422 RETENTION_ACKNOWLEDGEMENT_REQUIRED`) before any write, and sets `retention_acknowledged_at` on the inserted row only when the caller acknowledged. Generic on the endpoint, not `health`-specific, matching this package's own "a caller names a `domain_key`, never a domain-specific code path" convention -- `standard`-classified domains (`habits` proven directly) accept the field but never require it, and `finance` (Task 7) will pick up the identical enforcement automatically once its `domain_key` is registered as `high_stakes`.

**Second real field-level encryption domain.** `_ENCRYPTED_FIELD_NAMES_BY_RECORD_TYPE` gains `vital_reading` (`notes`) and `symptom_log` (`symptom_description`, `notes`) -- `symptom_description` deliberately matches `DOMAIN-PRIVACY-CONTRACT.md`'s own worked example, named in that contract before any `health`-domain code existed, rather than an independently invented field name. Structured/low-sensitivity fields on the same records (reading type, value, unit, severity) stay plaintext, matching Task 4's "encrypt the narrative, not the whole row" precedent.

**First genuine end-to-end proof the `professional_referral_note` mechanism fires for real data, not just the evaluation harness's adversarial fixtures.** Task 5 part 2 built `requires_professional_referral` generically from a source domain's `high_stakes` classification and proved it against `personal.generate_insight`'s synthetic evaluation dataset; Task 6 is the first task to exercise it against a real enabled `health` domain, a real active `insight_generation` grant, and a real cited `domain_records` row -- confirming a mocked model response omitting the note is rejected (`missing_professional_referral` grounding failure, `available=false`) and an otherwise-identical response including it persists successfully with the note attached to the stored `personal_insights` row.

**Tests.** `tests/test_personal_health_postgres.py` (8 tests): domain enable/independent-domain isolation; record creation without acknowledgement rejected with zero rows written; record creation with acknowledgement sets `retention_acknowledged_at`; `habits` (`standard`) unaffected by the new requirement; `symptom_log.symptom_description` genuinely ciphertext in `domain_records.payload` at rest (direct SQL) and redacted in list views; whole-domain export/delete; the two real-grant `professional_referral_note` proofs described above.

**Verified.** `ruff format --check`/`ruff check` clean (pinned `ruff==0.12.3`). `mypy backend` clean. Direct-SQL verification against real local Postgres confirmed the `domain_records` INSERT's 14-column list/order matches the live schema exactly (`retention_acknowledged_at` included) before any test-suite run. **Local pytest execution remained impossible in this sandbox** for the same reason disclosed in Task 5 part 2's evidence above (the only available Python 3.14 interpreter is a pre-release build incompatible with the repo's pinned `pydantic`/`typing_extensions`, breaking any Pydantic model construction) -- static verification plus direct-SQL schema/insert checks is what this evidence section relies on locally; the real test suite run happens in CI, watched and driven to green the same way every prior PR in this activation has been.
