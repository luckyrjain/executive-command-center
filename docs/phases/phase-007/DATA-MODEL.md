# Phase 7 Data Model

Core records: `personal_domains`, `domain_consents`, `domain_records`, `domain_sources`, `goals`, `routines`, `check_ins`, `cross_domain_grants`, `personal_insights` and `deletion_jobs`.

Each record includes domain, classification, provenance, effective time and retention policy. Sensitive payloads use field-level encryption where defined. Cross-domain grants name source domain, target purpose, fields/categories and expiry. Insights are derived, versioned and deletable; source records remain authoritative.

## Domain/classification/schema (resolved)

`personal_domains.domain_key`: closed enum `habits|learning|travel|relationships|health|finance`. `personal_domains.classification`: closed enum `standard|sensitive|high_stakes` -- `habits`/`learning`/`travel` are `standard`, `relationships` is `sensitive`, `health`/`finance` are `high_stakes`. Every domain is disabled (`enabled=false`) by default, per user, independently of every other domain.

`domain_records.payload` (JSONB) holds per-`record_type` fields; sensitive/high_stakes-classified fields inside `payload` are individually Fernet-encrypted (`DOMAIN-PRIVACY-CONTRACT.md`'s "Encryption fields (resolved)"), not the whole column -- a `standard`-classified field on an otherwise `sensitive` record (e.g. a `relationships` record's `contact_name`) stays plaintext/queryable. `domain_sources.source_type`: `manual|imported_file` this activation -- no connector-based personal-domain source exists yet.

## Retention (resolved)

`standard`: retained until the user deletes the record or the design doc's own export/deletion mechanism runs -- disabling a domain never deletes its data by default. `sensitive`: same indefinite default, plus a non-blocking keep/export/delete nudge after 18 months of no access to a record. `high_stakes`: same nudge at 12 months, plus every `high_stakes` `domain_records` row requires `retention_acknowledged_at` set at creation time (consent affirmed per record, not only once at domain enablement).

## Task 1 status

Ships `personal_domains`, `domain_consents`, `domain_records`, `domain_sources`, `goals`, `routines`, `check_ins`, `deletion_jobs`, scoped to the `habits` reference domain (`standard` classification) only. `cross_domain_grants` and `personal_insights` beyond deterministic (non-model-call) kinds are added by the task that first needs them (`docs/superpowers/specs/2026-07-31-phase-7-personal-intelligence-design.md`, Decision 1, item 5).

## Task 2 status

**No new table, migration or endpoint.** `learning` is `standard`-classified, identical to `habits` -- Task 1's own domain-enablement and generic `domain_records` CRUD (`ecc.domains.personal.domains`) take `domain_key` as a runtime value already validated against the closed `DomainKey` enum, not a `habits`-specific code path. Verified directly (`tests/test_personal_learning_postgres.py`): enabling `learning`, creating/listing/patching/exporting/deleting `domain_records` under it all work unmodified. This is the concrete confirmation the design doc's own "why `habits` first" reasoning (Decision 1: prove the generic framework before a `sensitive`/`high_stakes` domain needs it) was aiming for -- a second `standard` domain onboarded with zero new backend code, not merely asserted to be possible.

`learning`'s own `domain_records.record_type` conventions (documented here since nothing else fixes them): `course` (`payload`: `title`, `provider`, `url` optional, `progress_pct` integer 0-100 optional, `completed_at` optional), `resource` (`payload`: `title`, `resource_type` string e.g. `"book"`/`"article"`/`"video"`, `url` optional, `notes` optional). No `goals`/`routines`/`check_ins` convention is defined for `learning` in this task -- those three tables are proven domain-agnostic by schema (no FK or CHECK constraint ties them to `habits`), but `learning`'s own natural shape (course progress, not a repeating daily/weekly/monthly cadence) is better served by `domain_records.payload.progress_pct` directly than by forcing a `routines`/`check_ins` pair onto content that isn't actually a recurring habit -- not attempted here without a real UI/usage need driving it.

## Task 3 status

**No new table or migration -- one small, generic API addition.** `travel` is `standard`-classified, identical in enablement/CRUD to `habits`/`learning`. What Task 3 actually needed: `travel` is the design doc's own "first domain with meaningfully time-ranged records, exercising retention-by-date-range" -- a single `domain_records.effective_at` timestamp already exists per record, but nothing previously let a caller *query* by it. `GET /personal/records` (`ecc.domains.personal.domains.list_records_endpoint`) gains two optional query parameters, `effective_from`/`effective_until` (inclusive on both bounds), filtering on `effective_at` -- generic on the endpoint, not `travel`-specific, matching this activation's existing "a caller names a `domain_key`, never a domain-specific code path" convention (`API-SCHEMAS.md`'s Task 3 section has the endpoint-level detail). Retention itself is unchanged from the "Retention (resolved)" section above -- `standard` classification is still retained indefinitely until the user deletes it; "retention-by-date-range" here means the record's own effective date range is now queryable, not that records expire on a timer.

`travel`'s own `domain_records.record_type` convention: `trip` (`payload`: `destination`, `start_date` (ISO date string), `end_date` optional, `notes` optional; `effective_at` is set to the trip's `start_date` at creation, per the module's existing `effective_at` parameter on `POST /personal/records`). No `goals`/`routines`/`check_ins` convention is defined for `travel` in this task, for the same reason as `learning`'s own Task 2 finding above -- a trip is not a recurring habit.

## Task 4 status

**No new table or migration -- the first domain to populate `ecc.domains.personal.crypto` for real.** `relationships` is `sensitive`-classified, the first domain the design doc's Decision 3 field-level encryption mechanism actually encrypts a field for (`habits`/`learning`/`travel` are all `standard`, so `_ENCRYPTED_FIELD_NAMES_BY_RECORD_TYPE` was empty and structurally unexercised before this task). Enablement/CRUD is otherwise identical to every prior domain -- no `relationships`-specific route.

`relationships`' own `domain_records.record_type` conventions: `contact` (`payload`: `contact_name` (plaintext, structured), `relationship_type` optional plaintext e.g. `"friend"`/`"family"`/`"colleague"`, `notes` optional -- **encrypted**), `interaction` (`payload`: `contact_record_id` optional plaintext (no FK enforced -- `domain_records` has none per-domain, matching every other `record_type` here), `interaction_type` optional plaintext e.g. `"call"`/`"coffee"`/`"message"`, `notes` optional -- **encrypted**). `notes` is the free-text field on both record types most likely to contain real sensitive content, matching Decision 3's "encrypt the narrative, not the whole row" split -- `contact_name`/`relationship_type`/`interaction_type` stay plaintext/queryable. No `goals`/`routines`/`check_ins` convention defined, same reasoning as `learning`/`travel`'s own findings above -- neither record type is a recurring habit.

**Encryption mechanism, concrete.** `ecc.domains.personal.crypto.encrypt_field`/`decrypt_field` (Fernet, a dedicated `ECC_PERSONAL_DATA_ENCRYPTION_KEY`, distinct from the connector-token key, mirroring `ecc.domains.engineering.crypto`'s shape but `str`-typed rather than `bytes`-typed since `domain_records.payload` is JSONB). `ecc.domains.personal.domains._encrypt_payload`/`_decrypt_payload` wrap those around `_ENCRYPTED_FIELD_NAMES_BY_RECORD_TYPE`'s per-`record_type` field list: encryption happens immediately before `INSERT`/`UPDATE` (the plaintext form is never itself persisted); decryption happens only for single-record response paths (create/get/patch) and the whole-domain export -- `list_records_endpoint` keeps returning a redacted placeholder via the pre-existing `_redact_payload`, per Decision 3's "only a single-record fetch returns the decrypted value." The idempotency cache (`idempotency_records.response_body`) is treated as a persisted store the decrypted value must never reach either -- the response built for `store_idempotency` uses the still-encrypted row; only the copy actually returned to the caller (and a later cache-hit replay, decrypted at read time) ever holds plaintext. Verified directly against real Postgres (`tests/test_personal_relationships_postgres.py`): `notes` is genuinely ciphertext in `domain_records.payload` at rest (not merely absent from the API response), list responses redact it, single-record/export responses decrypt it, and the idempotency-records row itself never holds the decrypted value across a replayed request.

## Task 5 status (part 1 of 2, schema/grants)

**Repository-owner directed split, disclosed rather than silently narrowed.** Task 5 as originally scoped (Decision 1 item 5) bundles `cross_domain_grants` with the first AI-generated insight types (`trend`/`correlation`) behind a brand-new Phase 4 evaluated task type -- a materially larger, riskier unit than Tasks 2-4 each were. The repository owner directed this split into two PRs: part 1 (this section) ships the `cross_domain_grants` schema and grant lifecycle only, with **no consumer reading a grant yet**; part 2 (a separate, later PR) adds the evaluation dataset, safety-rubric adversarial fixture set, and the `trend`/`correlation` insight-generation logic that actually checks a grant before combining domains.

**Schema, resolving this document's own top-line description into concrete columns.** This document's intro line ("Cross-domain grants name source domain, target purpose, fields/categories and expiry") names a target *purpose*, not a second domain -- `cross_domain_grants.purpose` is a closed, extensible enum (one value this task defines: `'insight_generation'`, the only consumer Decision 1 item 5 names) rather than a `target_domain_key` column. `source_domain_key` (closed enum, same six `domain_key` values) names whose data the grant covers; `granted_categories` (JSONB array of strings, non-empty) names which categories of that domain's data (loosely typed, matching how `domain_records.record_type` itself has no closed enum either). `expires_at` is nullable (an indefinite grant is valid); when set, it time-bounds the grant the same way `domain_consents` are already described as "time-bound and revocable." Lifecycle mirrors `domain_consents` exactly (grant once, later only ever flip `revoked_at`) -- no `version`/`updated_at`/`created_by` columns, the same shape `domain_consents` itself already has for the identical reason (`owner_id` already identifies the granting actor for single-user-owned personal data).

`GET|POST /personal/grants`, `POST /personal/grants/{id}/revoke` (`ecc.domains.personal.grants`, new module) -- create requires `source_domain_key` already be an enabled domain (`require_enabled_domain`, the same check every `domain_records` write already uses); list supports optional `source_domain_key`/`active_only` filters (`active_only` excludes both revoked and expired grants); revoke is idempotent (a no-op, not an error, on an already-revoked grant). `tests/test_personal_grants_postgres.py` (9 tests) covers create requiring an enabled source domain, list with both filters, revoke idempotency, unknown-grant 404, and cross-workspace isolation.

`scripts/seed_phase1_acceptance.py` updated for the new workspace-scoped table (the now-familiar class of gap this document's own Task 1 section already found and closed for the first nine Phase 7 tables) -- one indefinite `insight_generation`-purposed grant against `habits` per acceptance workspace, verified locally (exactly 2 rows).

## Task 5 status (part 2 of 2, AI-generated insights)

**The third Phase 4 task type, `personal.generate_insight` (migration `0057_phase7_insight.py`), consuming Task 5 part 1's grants for the first time.** `personal.get_insight_sources` (`ecc.domains.personal.insight_tools`, new module) -- the task's own required-input tool -- refuses to read any requested source domain that is not currently enabled *and* does not have an active, non-revoked, non-expired grant naming it for `purpose='insight_generation'`; missing either for even one requested domain fails the whole call (`ToolNotFound`), never a partial read. `granted_categories` further narrows which `domain_records.record_type`s are actually readable per domain. Every returned record's payload is decrypted (`domains.decrypt_record_payload`, the same path a single-record fetch/export already uses), never the list-view redaction placeholder.

**No new `personal_insights`/`cross_domain_grants` columns needed for the schema itself** -- `personal_insights.kind`'s CHECK constraint has allowed `trend`/`correlation` since Task 1's own migration (`0054_phase7_personal_domains.py`), unexercised until now. One new nullable column, `personal_insights.professional_referral_note` (migration `0059_phase7_insight_feedback.py`), plus a new `personal_insight_feedback` table (`id`, `workspace_id`, `owner_id`, `insight_id`, `useful` boolean, `comment` nullable text, `created_by`, `created_at` -- append-only, not upserted, since a user may leave feedback on the same insight more than once) with no `kind` column of its own, so `POST /personal/insights/{id}/feedback` is structurally incapable of rewriting an insight's own `kind` (`INSIGHT-CONTRACT.md`'s own requirement). `personal_insights` also gains `UNIQUE(workspace_id, id)` purely so `personal_insight_feedback` can foreign-key to it via the composite `(workspace_id, insight_id)` pair every other cross-table reference in this package already uses.

**Evaluation dataset (migration `0058_phase7_insight_eval.py`, `tests/fixtures/phase7_evaluation_personal_insight.py`)**: 10 examples at the 100%-floor adversarial rigor `INSIGHT-CONTRACT.md`'s safety rubric requires before promotion -- see that document's own Task 5 part 2 section for the full breakdown. Unlike `meeting.prep_summary`'s dataset, no deterministic id assignment is needed: `personal.generate_insight`'s grounding check validates citations against whatever real `domain_records.id` values `evaluation.py`'s own synthetic-source insertion helper assigns at insert time (random `uuid4()`s, matching `attention.explain_item`'s own convention), not a predetermined id the fixture and migration must independently agree on.

**Production call site**: `POST /personal/insights/generate` (`ecc.domains.personal.ai_insights`, new module), gated behind `config.py:personal_ai_insight_generation_enabled` (default `False`, mirroring `meeting_prep_ai_enrichment_enabled`'s identical "deterministic core, AI optional and gated" pattern). `source_period_start`/`source_period_end` (the DB's `NOT NULL` `DateTime` columns) are computed from the real `effective_at` values of the `domain_records` the model actually cited, never taken from the model's own free-text `source_period` field -- a hallucinated date range must never reach a structural column. A cross-domain insight's `domain_key` column records the first requested source domain (a deliberate simplification; the genuinely cross-domain evidence lives in `evidence`, not lost by this single-value column).

## Task 6 status

**No new table or migration -- `health` is the first domain to actually exercise two mechanisms Task 1/5 part 2 already built structurally but had nothing real to bind against.** `personal_domains.classification = 'high_stakes'` for `health` has been in place since Task 1's own migration; `domain_records.retention_acknowledged_at` has existed as a nullable column since the same migration, unwritten by any endpoint until now.

**Retention acknowledgement, enforced at write time.** `POST /personal/records`'s `RecordCreateRequest` gains one field, `retention_acknowledged: bool = False` -- when the target domain's classification is `high_stakes`, `create_record_endpoint` rejects the request with `422 RETENTION_ACKNOWLEDGEMENT_REQUIRED` unless it is `true`, matching this document's own "Retention (resolved)" section: "every `high_stakes` `domain_records` row requires `retention_acknowledged_at` set at creation time (consent affirmed per record, not only once at domain enablement)". `standard`/`sensitive` domains accept the field but never require it -- `habits`'/`relationships`' own existing tests are unaffected. `retention_acknowledged_at` is set to the request's own timestamp when acknowledged, `NULL` otherwise (never backfilled or inferred).

**`health`'s own `domain_records.record_type` conventions**: `vital_reading` (`payload`: `metric` (e.g. `"resting_heart_rate"`, `"weight"`, `"blood_pressure"`), `value`, `unit` optional, `notes` optional -- **encrypted**), `symptom_log` (`payload`: `symptom_description` -- **encrypted**, the exact field name `DOMAIN-PRIVACY-CONTRACT.md`'s own "Encryption fields (resolved)" section already named as this domain's worked example; `severity` optional plaintext e.g. `"mild"`/`"moderate"`/`"severe"`). `_ENCRYPTED_FIELD_NAMES_BY_RECORD_TYPE` (`ecc.domains.personal.domains`, populated for real by `relationships` in Task 4) gains both entries -- `metric`/`value`/`unit`/`severity` are structured and low-narrative-risk, so they stay plaintext/queryable per Decision 3's "encrypt the narrative, not the whole row" split, matching `relationships`' own precedent exactly. No `goals`/`routines`/`check_ins` convention defined, same reasoning as every prior `standard`-domain finding above.

**The first real, non-synthetic proof that `professional_referral_note`'s conditional requirement (Task 5 part 2) fires for an actual `high_stakes` domain.** `tests/test_personal_health_postgres.py` exercises the full path against a real `health` domain, a real grant, and a real `domain_records` row (not the evaluation harness's synthetic fixtures): a mocked model response omitting `professional_referral_note` fails the run as `grounding_failed`; one supplying it succeeds -- confirming `requires_professional_referral`'s computation (`runtime.py:_prepare_personal_insight_request`, driven by the `personal.get_insight_sources` tool's own per-source `classification`) is genuinely keyed off `high_stakes` classification in general, not anything `health`-specific hardcoded into Task 5 part 2's own implementation.
