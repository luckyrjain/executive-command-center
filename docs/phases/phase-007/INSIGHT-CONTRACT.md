# Personal Insight Contract

Insights must be evidence-backed, proportionate and non-manipulative. Types are `observation|trend|correlation|reminder|planning_suggestion`. Each shows source period, missing data, confidence and limitations.

The system does not diagnose, prescribe, promise financial outcomes or infer sensitive traits. High-stakes decisions direct the user to qualified professionals. Cross-domain insight requires an active grant covering every source. Feedback cannot silently turn correlation into causation.

## Safety rubric (resolved)

`source period`/`missing data`/`confidence`/`limitations` are Pydantic-required fields on the insight output schema, not a prompt-only instruction -- an insight response omitting one fails schema validation and is never returned, mirroring `attention.explain_item`'s `ExplainItemOutput` guarantee. Before any `health`/`finance`-domain prompt version is promoted, it must clear a dedicated adversarial fixture set (diagnostic claims, prescriptive treatment language, guaranteed-return language, credit/employment/insurance-decision language, sensitive-trait inference) at the same 100%-floor rigor `EVALUATION-CONTRACT.md` holds `attention.explain_item`'s `must_not_state` probe to. No insight `kind` computes or surfaces a numeric relationship-health score, ranking or frequency leaderboard -- a hard schema-level constraint on the `kind` enum, not a UI convention. `health`/`finance`-classified insights require a non-empty `professional_referral_note` field (absent on other domains' insights). `POST .../feedback` never rewrites an insight's own `kind` -- only separate feedback metadata, so feedback cannot upgrade a `correlation` into something that reads as a settled `observation`.

## Task 1 status

Zero AI-generated insights this activation -- every `habits`-domain insight is deterministic (a direct threshold computation, e.g. a check-in gap), no model call. `trend`/`correlation` kinds (the only ones a model generates) are deferred to the task that adds `cross_domain_grants` (`docs/superpowers/specs/2026-07-31-phase-7-personal-intelligence-design.md`, Decision 1, item 5), once this rubric has an approved target to build against.

## Task 5 status (part 2 of 2)

**This rubric's approved target, built.** `personal.generate_insight` (`ecc.domains.ai_runtime`) is the third Phase 4 task type this activation registers, gated on Task 5 part 1's `cross_domain_grants` mechanism: its own required-input tool, `personal.get_insight_sources` (`ecc.domains.personal.insight_tools`), refuses to read any source domain that lacks a currently-enabled `personal_domains` row *and* an active, non-revoked, non-expired grant naming it for `purpose='insight_generation'` -- missing either for even one requested domain fails the whole call, matching this document's own "Cross-domain insight requires an active grant covering every source."

**The four required output fields, Pydantic-required, not prompt-only.** `validator.PersonalInsightOutput` (`kind: Literal["trend", "correlation"]`, `title`, `explanation_text`, `cited_record_ids`, `source_period`, `missing_data`, `confidence`, `limitations`, `professional_referral_note`) declares `source_period`, `missing_data`, `confidence` and `limitations` as required fields with `extra="forbid"` -- a model response omitting one fails schema validation and is never returned, exactly like `attention.explain_item`'s `ExplainItemOutput` already does for its own required fields. No numeric score/ranking/leaderboard field exists anywhere on this schema -- "No insight kind computes or surfaces a numeric relationship-health score" is true by omission, not by a runtime check a later edit could accidentally bypass.

**`professional_referral_note`, conditional, checked after schema validation.** Optional (`None`-able) at the schema level, since whether it must be non-empty depends on which domains actually contributed to a given insight -- information the schema itself cannot know. `check_personal_insight_grounding` (`validator.py`) enforces the conditional requirement: `runtime.py`'s `_prepare_personal_insight_request` computes `requires_professional_referral` from the `personal.get_insight_sources` tool's own per-source `classification` field (`any(... == "high_stakes" and source["records"] ...)` -- a `high_stakes` domain contributes zero records is not enough to require the note, since there is then no `high_stakes` content actually grounding the insight), and a response failing that check surfaces as a `grounding_failed` run, never a `completed` one -- the same `GroundingFailure` dataclass `attention.explain_item`/`meeting.prep_summary`'s citation checks already use, widened with a second `reason` value (`missing_professional_referral`) rather than a new, parallel type.

**Adversarial fixture set, at the 100%-floor rigor this document requires before promotion.** `tests/fixtures/phase7_evaluation_personal_insight.py` (migration `0060_phase7_insight_eval_v2.py`'s seeded duplicate, version 2 -- the five `health`/`finance`-anchored examples were rewritten to use the real `record_type`/payload conventions Tasks 6/7 actually shipped, superseding version 1's `0058_phase7_insight_eval.py` seed) is 10 examples: a single-domain trend, a two-`standard`-domain correlation, a `sensitive`-domain correlation, a sparse trend (exercises `missing_data`), five dedicated adversarial examples -- one per required category (diagnostic claims, prescriptive treatment, guaranteed-return language, credit/employment/insurance-decision language, sensitive-trait inference) -- each anchored in a `health`/`finance` source so it also exercises the `professional_referral_note` conditional check alongside its own `must_not_state` probe, and one genuine two-`high_stakes`-domain correlation spanning both `health` and `finance` sources in a single insight, the only example proving the conditional note fires correctly when more than one `high_stakes` source contributes. Built now, not deferred until Tasks 6/7 "officially" land: `cross_domain_grants.source_domain_key` has accepted `health`/`finance` since Task 1 (both are valid `DomainKey` values with real classification mappings already), so a user could already grant either domain today.

**Feedback, structurally incapable of rewriting `kind`.** `POST /personal/insights/{id}/feedback` (`ecc.domains.personal.habits`) writes to a separate `personal_insight_feedback` table (migration `0059_phase7_insight_feedback.py`) with no `kind` column of its own -- there is no column for this endpoint to write a `kind` value to, regardless of what its own code does or doesn't choose to do, matching this document's "`POST .../feedback` never rewrites an insight's own `kind` -- only separate feedback metadata."

**Production call site, opt-in, not on every list-view fetch.** `POST /personal/insights/generate` (`ecc.domains.personal.ai_insights`, gated behind `config.py:personal_ai_insight_generation_enabled`, default `False`) is an explicit, caller-requested action -- unlike `habits.py`'s deterministic insights (recomputed on every `GET`, no model call), an AI-generated insight is never recomputed implicitly on a list-view fetch, avoiding a real model call becoming an implicit cost/latency regression on a read endpoint. Fail-open by construction, mirroring `meeting_prep.py:_compute_enrichment`'s identical discipline: any non-`completed` run surfaces as `available=false` carrying that run's own `error_code`, never an HTTP error for a well-formed request.
