Written at design time as part of Phase 5's Task 0 design pass (`docs/superpowers/specs/2026-07-25-phase-5-automation-design.md`, `docs/adr/ADR-0013-durable-workflow-execution.md`); every claim in this document is now a real, tested property of `worker.py` (`tests/test_automation_worker_postgres.py`, `tests/test_automation_kill_switches_postgres.py`), not a forecast. **Scope:** what "worker restarts recover durable state within 60 seconds locally" (`PHASE-005-automation.md`'s own non-functional requirement) means in practice, and what an operator (the repository owner, running ECC locally) does — and explicitly does not need to do — when the automation worker process crashes or restarts.

## Correction from the design-time draft: the reclaim predicate covers `running`, not only `leased`

Decision 3's original SQL sketch reclaimed only `status = 'leased' AND leased_until < now()`. `DATA-MODEL.md`'s own run-state vocabulary separately requires a `running` state (a run actively dispatching steps, as opposed to `leased`: claimed but not yet past its first step) — restricting the reclaim predicate to `leased` alone would silently fail to reclaim a run that crashed *after* it started running its steps, which is the crash timing that matters most in practice. `worker.py`'s actual `claim_next_run` therefore reclaims `status IN ('leased', 'running') AND leased_until < now()` — both are lease-bearing states, renewed by the identical heartbeat, so this is a one-word-wider generalization of Decision 3's SQL, not a second code path. `tests/test_automation_worker_postgres.py::test_crash_recovery_mid_run_resumes_from_checkpoint_not_from_scratch` exercises exactly this: a run that already completed step 1, left `running` with an expired lease, is reclaimed and resumes at step 2, not restarted at step 0. Every other claim below (the lease-bearing states are renewed identically, the reclaim query is the same statement every worker runs on every poll, no separate recovery code path exists) holds for both states equally.

## What recovery means

Every `workflow_runs` row a worker is actively executing is claimed via a **lease** (`docs/superpowers/specs/2026-07-25-phase-5-automation-design.md` Decision 3): `status='leased'` (transitioning to `status='running'` immediately before the first step dispatches), `leased_by=<worker id>`, `leased_until=<now + 30s>`, renewed once per step by `renew_lease` while the run is actively dispatching steps (`HEARTBEAT_INTERVAL_SECONDS = 10` is a declared constant, not a timer — a single `execute()` call slower than the 30s lease is not heartbeated while in flight, and its run becomes reclaimable mid-step; the `action_digest` gate and the `leased_by` ownership predicate on every run-state write are what keep that bounded rather than unsafe, `EXECUTION-CONTRACT.md`). A worker that crashes simply stops renewing its leases. There is no separate "detect the crash and trigger recovery" step — **recovery is the same lease-expiry reclaim logic every worker already runs on every poll cycle**, not a distinct disaster-recovery code path that could itself have its own bugs or go untested.

Concretely, after a crash:

1. The crashed worker's leases stop being renewed. Within 30 seconds (the lease duration), each affected `workflow_runs` row's `leased_until` passes.
2. Any live worker's next poll cycle (every 2 seconds) picks up rows matching `status IN ('leased', 'running') AND leased_until < now()` — the identical query used for normal `queued`-row claiming, just a different `WHERE` branch of the same statement.
3. The claiming worker resumes the run from its last durably persisted checkpoint: `current_step_index` plus whichever `workflow_run_steps` rows already have a persisted `action_digest`. A step whose digest was persisted but whose adapter never confirmed completion is not blindly retried — it is marked `unknown` and the run moves to human review (design doc Decision 3), exactly the same outcome an `unknown` external result produces in normal operation, not a recovery-specific behavior.

**Recovery-time budget:** 30s (lease timeout) + 2s (poll interval) + a small constant for the claim query and step resumption itself comfortably clears the 60-second target. This is a property of the lease numbers chosen in Decision 3, not a separately-tuned recovery parameter — there is nothing to configure differently for "recovery mode" versus normal operation. `worker.py`'s `POLL_INTERVAL_SECONDS`/`LEASE_DURATION_SECONDS`/`HEARTBEAT_INTERVAL_SECONDS` constants are `2`/`30`/`10` — unchanged from Decision 3's own numbers.

## What an operator does on a worker crash (local ECC deployment)

**If ECC's process supervisor (`docker compose`) restarts the worker automatically** (the expected case — the worker runs as a service in the same Compose stack as `backend`, restarted on failure the same way `backend` itself already is): nothing. The restarted worker process begins polling immediately; any runs it or a sibling worker previously held leases on are reclaimed via the mechanism above within the 60-second budget. No manual intervention, no manual query, no manual "resume" action.

**If the operator needs to manually confirm recovery happened** (e.g. after an unusual crash, or before trusting the system unattended): query `workflow_runs` for any row with `status IN ('leased', 'running') AND leased_until < now() - interval '90 seconds'` (a 90-second, not 30-second, threshold deliberately gives margin over the reclaim budget before treating a stuck lease as a genuine anomaly rather than a false alarm from checking too early; both lease-bearing states are checked, per the correction noted above). A non-empty result after that margin indicates every worker in the deployment is down, not merely one — the fix is to bring at least one worker process back up, not to manually intervene in the lease table.

**If a run's step outcome is genuinely `unknown`** after recovery (the crash landed between digest-persisted and adapter-confirmed): this is not a worker-availability problem and is not fixed by restarting anything. It surfaces in the approval/run-history UI (`UX-STATES.md`) as requiring human review — the operator inspects the target system (whatever the adapter's `execute()` was acting on) to determine whether the side effect actually happened, then explicitly resolves the run (mark the step's true outcome, or trigger its compensation if one is declared, design doc Decision 9). This is intentionally a human decision, not an automated guess — automating "did the side effect happen" for an arbitrary adapter is exactly the blind-retry risk `PHASE-005-automation.md`'s own functional requirement exists to prevent.

## What recovery does not require

- **No manual database surgery.** The reclaim query is a normal part of the worker's own poll loop; an operator never needs to hand-write an `UPDATE` to un-stick a lease under normal crash-recovery conditions (only the diagnostic read query above, and only to confirm, never to force a claim).
- **No workflow re-authorization.** A recovered run continues under the exact policy version and approval state it already had — recovery never re-prompts for an approval that was already granted, and never silently grants one that wasn't.
- **No data loss for a properly-persisted step.** Any step whose `action_digest` was persisted before the crash retains that record regardless of whether the crash happened before or after the underlying side effect — the `unknown`-outcome path above exists precisely so ambiguity is surfaced, not silently resolved either direction.

## Kill switches and their recovery interaction

A global or per-workflow kill switch (`PHASE-005-automation.md`'s Rollback plan) sets a flag the worker's claim query itself checks — a killed workflow's rows are never claimed, reclaimed, or resumed regardless of lease state, including across a crash/restart cycle. Re-enabling a previously-killed workflow does not automatically resume its paused runs; per the phase's own rollback plan, in-flight runs under a kill switch "stop at safe checkpoints or enter review," which the operator explicitly resolves the same way an `unknown` outcome is resolved above, not implicitly on re-enable.

**Implemented Task 6, real evidence, not a forecast:** `ecc.domains.automation.kill_switches` (`automation_kill_switches`, an append-only-ish audit table — see `docs/phases/phase-005/DATA-MODEL.md`) is the flag this section describes. `worker._CLAIMABLE_PREDICATE` — the *same* single statement every ordinary claim and every crash-recovery reclaim already goes through (this document's own "What recovery means" section) — gained two correlated `NOT EXISTS` subqueries against this table (global scope, `workflow_id IS NULL AND active`; per-workflow scope, `workflow_id = workflow_runs.workflow_id AND active`), so a killed workflow's row is mechanically unreachable by either path, not merely by convention. `worker.process_claimed_run`'s per-step loop additionally checks `kill_switches.is_workflow_killed` at the identical point its `cancel_requested_at`/`pause_requested_at` checks already run, stopping a run mid-dispatch via `needs_review` — reusing the existing terminal-until-human-action state. `worker.enqueue_run` also checks before creating any row at all, so a killed workflow accumulates no *new* `queued` backlog behind the switch. `tests/test_automation_kill_switches_postgres.py` proves the crash/restart claim-blocking property directly: a run claimed, force-expired (simulating an unrenewed lease past a real worker crash), then a kill switch activated — a subsequent `claim_next_run` call never returns it, though the identical sequence *without* the kill switch does.

**Correction to this section's own "by construction" claim, from the run-state audit.** This section previously argued that "re-enabling does not implicitly resume" held for free, on the grounds that a killed run lands in `needs_review` and `needs_review` was never in `_CLAIMABLE_PREDICATE`'s claimable set. That reasoning covered only the runs a worker happened to be actively dispatching and therefore *observed* being killed (`process_claimed_run`'s own per-step check). It did not cover two other ways a run can be in flight when a switch activates, and for those the guarantee was simply false:

1. **Runs already sitting in `'queued'`** when the switch activated. `enqueue_run`'s kill-switch rejection blocks only *new* rows; it never touched rows already queued.
2. **Retry-pending runs**, which `run_step`'s bounded-retry path deliberately parks back in `'queued'` with a `next_attempt_at`.

Both sat quietly in `'queued'` for the whole incident — invisible as anything needing review, since a killed workflow's rows are unclaimable but not *marked* — and the instant the switch was deactivated the very next poll cycle claimed and dispatched them with zero operator review. **Fix:** `kill_switches.activate_kill_switch` now performs one extra, explicit step at **activation** time (`_park_queued_runs_for_review`), transitioning every currently-`'queued'` run in the affected scope (global → every workflow in the workspace; per-workflow → that one workflow) straight to `'needs_review'`, in the same unit of work as the switch row itself. That restores "by construction" for real, in the strong sense: after activation no run is left in any state a later deactivation could silently resume from, so deactivation itself remains a pure kill-switch-row mutation that touches no run at all. Deliberately scoped to `'queued'` only — a `'leased'`/`'running'`/`'compensating'` run is lease-bearing and actively owned by some worker (that worker's own per-step check parks it), a `'paused'` run already requires an explicit `resume_run`, and `waiting_approval`/terminal runs are not resumable by a poll cycle at all.

**Operational consequence for an operator working an incident:** activating a kill switch does not leave a silent queue behind it. Every run that was queued in scope shows up in `needs_review` immediately, alongside any run a worker parked there mid-dispatch — one uniform queue to work through, so the diagnostic question after deactivation is "which `needs_review` runs do I want to re-run?" rather than "did anything resume behind my back?"

**One disclosed gap this task introduces, not present before it: compensation dispatch is not crash-resumable, and this runbook's own diagnostic query does not yet cover it.** A run transitioning to `status = 'compensating'` (Task 6's own new state, entered when a failed step has at least one qualifying compensation to run) deliberately keeps its lease rather than releasing it — but `_CLAIMABLE_PREDICATE`'s expired-lease branch was *not* widened to include `'compensating'` alongside `'leased'`/`'running'` (see `worker.py`'s own module docstring, "Task 6: a disclosed, real scope boundary", for the full reasoning: doing so correctly needs the same crash-safety rigor `run_step` itself received in Task 2's review, which this task's own required test list did not name and did not build). **Concrete consequence:** a worker crash while a run is `status = 'compensating'` leaves it permanently stuck — its lease eventually expires, but no reclaim predicate ever picks it up again. The "manually confirm recovery happened" diagnostic query above (`status IN ('leased', 'running') AND leased_until < now() - interval '90 seconds'`) does not catch this case as written; an operator suspecting a stuck compensation should additionally query `status = 'compensating' AND updated_at < now() - interval '90 seconds'` and, if found, treat it the same way this document treats a genuinely `unknown` outcome — a human decision, not an automated guess — since the compensation ledger (`compensation_steps`) shows exactly which of the run's qualifying compensations already succeeded and which remain, letting the operator resume manually or re-run the remainder by hand. Flagged here as a concrete next step for a later task, not silently left implicit.

## Backup/restore interaction

`workflow_runs`/`workflow_run_steps`/`workflow_versions`/`policies` are ordinary PostgreSQL tables within the same database Phase 0's backup/restore procedure already covers (`docs/runbooks/PHASE-1-DEPLOYMENT.md`'s backup/restore section) — Phase 5 introduces no new stateful service and therefore no new backup/restore procedure, only new tables inside the existing one. A restore to a backup taken mid-run leaves that run's rows in whatever state the backup captured (typically `leased` with a `leased_until` that has since passed) — the same lease-expiry reclaim path above resumes it identically to a live crash, with the same `unknown`-outcome-requires-review caveat, since a restore is, from the worker's perspective, indistinguishable from "time passed and this lease expired."
